# PWM TUI: целевая спецификация MVP и профили интерфейса

Связь с планом: [MVP-checklist.md](MVP-checklist.md) §6. Этот документ фиксирует **конечный замысел** TUI и отделяет его от **внутреннего** режима отладки.

UX baseline для форм/диалогов и визуально-интерактивных паттернов: [TUI_DESIGN_SPEC_v1.md](TUI_DESIGN_SPEC_v1.md).
Security-режимы wallet (`plaintext_dev` vs `encrypted`): [WALLET_SECURITY_MODES.md](WALLET_SECURITY_MODES.md).

---

## 1. Два профиля

| Профиль | Назначение | Аудитория |
|---------|------------|-----------|
| **Public** | Привычный кошелёк / обзор сети без «сырого» JSON и без низкоуровневых полей. | Пользователь, демо |
| **Debug** (опционально) | Просмотр сырого JSON, полный hex, служебные поля; аналог вкладки *Debug console*. | Разработчик |

В публичной поставке по умолчанию включается **Public**. Режим Debug — флаг запуска (например `PWM_TUI_DEBUG=1` или подкоманда), чтобы не смешивать сценарии.

## 2. Public MVP: панели и роли (целевой дизайн)

- **Левая панель — «владелец» (мой кошелёк):** адреса и **каталоги** (группы), в будущих версиях раскрытие до inputs/UTXO. В MVP достаточно дерева/списка каталогов и адресов с кратким отображением.
- **Правая панель — получатели:** та же идея каталогов, удобных пользователю (контакты, недавние, зоны и т.д. — по мере появления данных на бэкенде).
- **Фокус:** активный курсор может **переключаться между панелями** (например Tab / отдельные клавиши); выделенная строка определяет контекст действий.
- **F6 — отправка средств:** всплывающая форма; в минимальном MVP достаточно ввести **сумму** (источник и получатель берутся из текущего выделения в левой/правой панели).
- **F3 — контекстный Unlock/Lock для encrypted-кошелька:** если кошелёк заблокирован — открывается модалка Unlock (passphrase); если уже разблокирован — выполняется немедленный Lock без отдельного подтверждения.
- **F4 — шифрование / смена passphrase:** модалка с полями **passphrase** и **confirm** (маскирование как в F3); **Enter** записывает на диск, **Esc** отмена. Для `plaintext_dev` — перевод в `encrypted` (KDF+AEAD как в CLI). Для уже `encrypted` — **re-key** только если в сессии есть расшифрованный payload (см. политику ниже).
- **F5 — сжигание марок / токенов** (когда появится в протоколе и RPC): аналогично модальное окно с минимальным вводом.
- **Доп. окна:** история транзакций по выбранному адресу (отдельный модальный слой или панель).

Все действия отправки/подписи в конечном счёте идут через **тот же RPC**, что и у CLI (TUI не дублирует криптологику в обход ноды/кошелька).

## 3. Public MVP: таблица счетов (обязательный минимум)

До полноценных двух панелей «владелец / получатели» и модалок достаточно **одной читаемой таблицы**:

| Колонка | Смысл |
|---------|--------|
| Address | User-facing адрес (pretty), при выборе деталь `init/nonce` остаётся в нижней строке |
| PWM | Баланс монеты |

Источник данных: существующий `GET /v1/accounts` (агрегат по сети). Это **не** замена левой/правой панели кошелька, но **приемлемый публичный** вид вместо JSON.

Когда появится API «мои адреса» / локальное хранилище ключей в TUI, таблица может показывать подмножество или расширяться второй панелью по §2.

## 4. Текущая реализация в коде (Sprint 1C)

Исторически первый прототип был ближе к **Debug**: список id + JSON детали. Это сознательно **не** целевой публичный интерфейс.

Реализовано в `pwm-tui`:
- Парсинг шапки кошелька YAML: тип `pwm_core::WalletReadHeader` (единый с `pwm-core` набор полей identity + `address_book` + KDF-метаданные для TUI; при расширении формата править core и TUI вместе).
- Две панели (Owner/Receivers) с переключением `Tab`, навигация стрелками.
- Таблицы в обеих панелях по умолчанию compact: только колонки `Address` и `PWM` (служебные `Staked/Marks/Init` скрыты для раннего публичного UX).
- В таблицах panels используется пропорция `Address` значительно шире `PWM`.
- Отображение user-facing адресов в текущем primary strict pretty формате (`pwm1-...-f...-t...`).
- При загрузке wallet owner-адрес вычисляется из truth-source (`master_seed_hex + derivation_path` или эквивалентно `signing_key_hex + derivation_index`); `account_id_human`/`account_id_hex` считаются кеш-полями и нормализуются на лету.
- Legacy mismatch `account_id_human/account_id_hex` больше не блокирует загрузку, если owner восстанавливается из truth-source.
- `F6` открывает рабочую форму отправки c полями `from/to/amount/fee/confirm`: `from` всегда фиксирован, `to` фиксируется по выбранному получателю в правой панели.
- История операций доступна по `H` в отдельной модалке `Operations History` (read-only, latest-first).
- Источник истории в Phase 1 — локальный in-memory кэш отправок из существующего send-flow (`POST /v1/tx`): при submit запись создаётся как `pending`, по RPC-ответу обновляется в `ok`/`error`.
- Для истории реализованы базовые состояния UX: пустой список (`No operations yet`), статус `pending/ok/error` и текст последней ошибки submit (где доступно).
- В правой панели первая строка — псевдо-получатель `New Recipient`: при его выборе в `F6` поле `to` пустое и редактируемое, иначе `to` read-only.
- Навигация вниз по правой панели доходит до последней строки (включая граничный случай off-by-one с `New Recipient` + последний адрес).
- В `F6` визуально подсвечивается только зона значения у editable-полей (тёмно-серый фон), label (`amount:`, `fee:` и т.д.) остаётся без фоновой подсветки; fixed-поля без editable-подсветки.
- В `F6` активное editable-поле показывает видимый caret `|`; доступны inline-операции редактирования: `Left/Right`, `Home/End`, вставка символа в позицию курсора, `Backspace/Delete` внутри строки.
- Блокирующие ошибки валидации/submit внутри `F6` подсвечиваются красным.
- Локальная проверка формы перед submit (`from/to` parse, `amount > 0`, `fee >= 0`, `confirm == yes`).
- Runtime policy для user-input адреса в `F6/to`: ambiguous legacy pretty без `/LO` (пример `pwm1-CY-f...`) отклоняется с явной подсказкой использовать strict pretty `pwm1-LABEL/XX-f...-t...` или canonical bech32dx `pwm1...`.
- `domain_lo == 00` валиден и не фильтруется: получатели вида `.../00` остаются selectable наравне с другими low-byte.
- Поля `amount` и `fee` принимают decimal PWM (`12`, `12.34`, `0.001`); scale фиксирован: **1 PWM = 1_000_000 base units**, максимум 6 знаков после точки, округление не применяется (over-precision -> reject).
- Submit выполняется в `POST /v1/tx`; статус/ошибка показывается в модалке.
- Nonce для submit: политика как в CLI — если `GET /v1/account/:id` вернул non-success (включая `404`) или невалидный JSON, используется fallback `nonce=0`; блокирующая ошибка остаётся только для offline/timeout.
- Источник owner identity: **wallet-first** (`--wallet` или `PWM_TUI_WALLET`); если wallet не передан явно, но в **текущей рабочей директории** есть файл `default.yml`, он подхватывается как wallet автоматически; иначе — fallback на `PWM_TUI_MASTER_SEED`; в UI постоянно показывается жёлтая строка предупреждения: `FALLBACK MODE: wallet not provided, owner derived from seed/default path`.
- Список **получателей** (правая панель): активная книга хранится в wallet как canonical-only (`bech32dx`). В UI адреса рендерятся в pretty на лету.
- Legacy pretty-записи в `address_book` при загрузке игнорируются (не источник истины); TUI продолжает работу и показывает счётчик игнорированных записей в статусе.
- Даже если список получателей пуст, UX остаётся стабильным: строка `New Recipient` остаётся доступной как entry point для `F6`.
- Все HTTP-запросы TUI к RPC используют **единый таймаут** (по умолчанию 3s): переменная `PWM_TUI_RPC_TIMEOUT_MS` (1…120000). При таймауте в строке ошибки показывается `head: timeout` / `accounts: timeout` вместо бесконечного ожидания.
- Архитектура I/O: RPC polling (`/v1/head`, `/v1/accounts`), debug account fetch и send submit (`nonce + POST /v1/tx`) выполняются в отдельном worker-потоке; основной UI-loop не делает блокирующие HTTP-вызовы и сохраняет отзывчивость при offline/timeout.
- Runtime polling/input: keyboard loop обрабатывается с коротким poll-интервалом, а debug `GET /v1/account/:id` дросселируется и кэшируется (не запрашивается на каждый кадр).
- Send lifecycle неблокирующий: в `F6` при submit сначала показывается промежуточный статус (`submitting tx...`), UI продолжает принимать ввод, финальный успех/ошибка приходит асинхронно из worker.
- Нижняя status line сохраняет подсказки по клавишам, `PWM_RPC`, опционально `PWM_TUI_DEBUG` и заметку identity; длинное поле `tip=` из `GET /v1/head` в строке статуса укорачивается middle-ellipsis (первые и последние символы хэша), чтобы не вытеснять остальной текст на узком терминале.
- Критические сигналы (`RPC offline`/`RPC timeout` красным, а также текст ошибок опроса `head:`/`accounts:`) выводятся **в начале** status line, чтобы оставаться видимыми при узкой ширине; красный индикатор RPC сохранён.
- Encrypted wallet: можно запускать **без** `--wallet-passphrase` / `PWM_TUI_WALLET_PASSPHRASE` — TUI загружает identity и адресную книгу, signing key остаётся заблокирован до **F3 Unlock** (ввод passphrase в модалке). Passphrase **не логируется**; ошибки Unlock показываются в санитизированном виде без секретных значений. Альтернатива: передать passphrase при старте (как раньше) — ключ разблокируется сразу, действует тот же таймер авто-блокировки.
- **F4 / re-key (политика):** чтобы сменить passphrase уже зашифрованного кошелька **без повторного ввода старого passphrase в отдельном поле**, процесс использует **кэш расшифрованного JSON-секрета** в памяти (тот же объём данных, что внутри AEAD-блоба). Кэш появляется при успешной расшифровке: старт с `--wallet-passphrase` / `PWM_TUI_WALLET_PASSPHRASE` **или** успешный **F3 Unlock**. Кэш **сбрасывается вместе с signing key** при авто-блокировке и при явном **F3 Lock**. Пока кэша нет, F4 для `encrypted` показывает подсказку разблокировать или задать passphrase при старте. После успешного re-key процесс обновляет **in-memory** `PWM_TUI_WALLET_PASSPHRASE` эквивалент (аргументы `Args`) на новую строку в рамках текущего процесса, чтобы перезагрузка identity не ломалась; переменные окружения ОС пользователь должен обновить сам при следующем запуске.
- Запись YAML при F4: **временный файл + rename** в каталоге кошелька (на Windows при необходимости удаление целевого файла перед rename), содержимое `fsync` перед заменой; passphrase в логи не пишется.
- После разблокировки (F3 или CLI/env passphrase при старте) signing key автоматически сбрасывается по таймеру (по умолчанию **300 с**): `PWM_TUI_WALLET_UNLOCK_SECS` или флаг `--wallet-unlock-secs` (диапазон 1…604800). По истечении — ключ из памяти убран, в статусной строке видно `wallet: LOCKED` / счётчик оставшихся секунд при активной сессии.
- При нажатии **F3** в состоянии unlocked выполняется немедленный Lock: signing key удаляется из памяти, очищается кэш расшифрованного payload для re-key, сбрасывается unlock timer и связанный статус.
- Для **plaintext** кошелька F3 показывает пояснение, что unlock не требуется.
- После on-load auto-upgrade plaintext wallet в статусе остаётся напоминание; шифрование выполняется через **F4 Encrypt**.

`F5` остаётся заглушкой до отдельной задачи burn-flow.

## 5. Клавиатура (целевое)

| Клавиша | Действие (цель) |
|---------|------------------|
| Tab | Переключение фокуса левая ↔ правая панель |
| F5 | Модалка сжигания (пока TODO) |
| F6 | Модалка перевода (from/to/amount/fee/confirm, submit в `POST /v1/tx`) |
| F6 + Left/Right/Home/End | Перемещение caret внутри активного editable-поля |
| F6 + Backspace/Delete/Char | Редактирование строки в позиции caret |
| F3 | Контекстный toggle для encrypted wallet: LOCKED -> Unlock modal (passphrase, Enter/Esc), UNLOCKED -> мгновенный Lock (очистка ключа/кэша/таймера) |
| F4 | Encrypt `plaintext_dev` wallet (новый passphrase + confirm) или **re-key** `encrypted` при наличии кэша расшифровки (см. §4); Enter=применить, Esc=отмена |
| H | Открыть/закрыть модалку истории операций (локальный timeline последних submit) |
| F10 / q | Выход |
| Стрелки | Навигация в активной панели / таблице |

Нижняя строка экрана: краткие подсказки по F-клавишам (как в mc).

## 7. Запуск (wallet-first)

Рекомендуемый запуск:

```powershell
cargo run -p pwm-tui --bin pwm-tui -- --wallet .\tmp\wallet-cy.yaml --wallet-passphrase "<PASSPHRASE>"
```

Запуск encrypted **без** passphrase на CLI (разблокировка только через F3 в TUI):

```powershell
cargo run -p pwm-tui --bin pwm-tui -- --wallet .\tmp\wallet-cy.yaml
```

Таймер авто-блокировки после unlock (секунды, по умолчанию 300):

```powershell
cargo run -p pwm-tui --bin pwm-tui -- --wallet .\tmp\wallet-cy.yaml --wallet-unlock-secs 600
# или
$env:PWM_TUI_WALLET_UNLOCK_SECS="600"
```

Эквивалент через env (в т.ч. с passphrase при старте):

```powershell
$env:PWM_TUI_WALLET=".\tmp\wallet-cy.yaml"
$env:PWM_TUI_WALLET_PASSPHRASE="<PASSPHRASE>"
cargo run -p pwm-tui --bin pwm-tui
```

Автоподхват wallet: если `PWM_TUI_WALLET` / `--wallet` не заданы, но в **cwd** есть `default.yml`, TUI использует его как wallet (тот же формат, что и для `--wallet`).

Опционально для автоматизации и медленных сетей:

```powershell
$env:PWM_TUI_RPC_TIMEOUT_MS="8000"
```

Dev fallback (только отладка, без wallet и без `default.yml`):

```powershell
$env:PWM_TUI_MASTER_SEED="<MASTER_SEED_HEX>"
cargo run -p pwm-tui --bin pwm-tui
```

## 6. Зависимости от бэкенда

- Таблица счетов: уже есть `GET /v1/accounts`, `GET /v1/account/:id`.
- Панели «мой кошелёк / контакты»: нужны **локальный профиль** (файл конфигурации) и/или новые RPC.
- История tx (расширенная, адресная/чейн-история): для следующего этапа нужен индексер или метод ноды вроде `GET /v1/account/:id/txs`; в Phase 1 используется локальный кэш submit-операций.

Документ обновлять по мере появления API и реализации панелей.
