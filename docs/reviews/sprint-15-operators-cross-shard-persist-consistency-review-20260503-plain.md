## Мини-словарь

| Термин | Простыми словами |
|--------|------------------|
| **Персист / сохранить на диск** | Записать состояние узла в файл (`pwm-data.json`) или в БД так, чтобы после выключения питания оно не пропало. |
| **Снапшот** | Сохранённый «снимок»: балансы, учёт импортов/экспортов, иногда блоки. |
| **Seal (запечатывание блока)** | Узел собрал транзакции из очереди, оформил **новый блок** и поднял высоту цепочки **в оперативной памяти**. |
| **Checkpoint** | Периодическая **полная** запись summary на диск (чаще, чем каждый блок); «якорь», к которому хотелось бы откатиться при сбое — но **автоотката к нему сейчас нет**. |
| **Degraded / ready_degraded** | Узел **продолжает отвечать** по HTTP как «готовый», но программа **знает**: последнее сохранение на диск **не удалось** (или снапшот при старте не загрузился). Ошибка часто лежит в `snapshot_error` в статусе. |
| **`is_ready` (готовность для API)** | Внутренний флаг: «можно ли считать узел запущенным». Сейчас он **зелёный и для нормы, и для degraded** — это важный нюанс. |
| **Handoff (передача доказательств)** | Целевой шард узнаёт про экспорт не «магией», а через регистрацию provenance (HTTP `handoff_register` и т.д.). |
| **Relay Import** | Импорт выполнен на **другом** узле/шарде через relay; на **исходном** узле остаётся только пометить в памяти «импорт доставлен» и **дописать облегчённый снапшот** (`save_tip_summary`). |
| **RAM vs диск** | Блок и состояние могут уже **измениться в памяти**, а файл на диске — **ещё старый или битый**. После рестарта узел читает **диск**, не «память вчерашнего дня». |
| **Durability (долговечность)** | Обещание «если API ответил успех — это уже не потеряется при падении». Сейчас это обещание **не везде** соблюдается. |

## Три ваших вопроса — ответы и маленькие сценарии

### 1) Почему «сброс» похож на ноль, а не на «ближайший чекпоинт»?

**Как есть:** в программе **нет кнопки** «отмотать только до последнего удачного чекпоинта на диске». Чекпоинты — это то, что **пишется** при штатной работе, а не автоматический **откат** при ошибке.

**Мини-сценарий A — не загрузился снапшот при старте**  
Узел поднялся из genesis в памяти, файл прочитать не смог или он битый → узел помечается degraded. В памяти вы видите **пустую или начальную** цепочку — **как после нуля**, хотя на диске могли лежать старые блоки. Программа **не** подставляет автоматически «последний хороший чекпоинт».

**Мини-сценарий B — вы руками удалили данные**  
Вы стёрли `pwm-data.json` / папку `epochs/` чтобы «вылечить» — следующий старт закономерно с нуля (genesis-only). Это не откат к чекпоинту, а **новая жизнь**.

**Вывод:** «Откат к ближайшему чекпоинту» — это **желаемая** функция восстановления; в текущей версии её нет как автоматики.

---

### 2) Почему при проблеме узел сам не почистил битые файлы перед рестартом?

**Как есть:** режим degraded **только помечает** «с сохранением что-то не так». Он **не удаляет** и не переименовывает файлы в каталоге состояния.

**Мини-сценарий**  
Диск был полный / права сбились / запись оборвалась на половине файла. Узел поставил degraded и пишет в лог ошибку. Вы перезапускаете процесс — **те же поломанные файлы** снова на месте. Программа их **не выкидывает**, чтобы не уничтожить единственную копию данных без решения человека.

**Вывод:** очистка или восстановление из бэкапа — **ручная** операция оператора (или отдельный инструмент позже).

---

### 3) Почему деградацию не поймали *до* того, как «закрепились» блоки / состояние после импорта?

Здесь несколько **разных дорожек** в коде; из-за этого ощущение «один узел всё делает одинаково» обманчиво.

**Мини-сценарий A — relay после межшардового импорта (исходный узел)**  
1. На целевом шарде импорт уже в блоке.  
2. На исходном узле relay говорит: «импорт доставлен» → программа **сначала меняет память** (пометка в roaming).  
3. Потом пытается **лёгкое сохранение** (`save_tip_summary`).  
4. Если диск отказал → память уже «импорт учтён», файл — нет → **degraded**, **отката памяти назад нет**.  
После рестарта узел читает старый диск — расхождение с тем, что «кажется уже сделанным».

**Мини-сценарий B — регистрация handoff на целевом узле**  
1. В память добавили запись «откуда пришёл экспорт, кому, сколько».  
2. Потом сохранение снапшота.  
3. Ошибка сохранения → клиент может получить **500**, но **запись в памяти уже осталась** — отдельного отката как в некоторых других API здесь нет.

**Мини-сценарий C — фоновый seal (новые блоки)**  
Каждые пару секунд узел может **запечатывать блок**, если считает себя «готовым». В режиме degraded он **тоже** считается готовым для этого. Блок в памяти **уже вырос**, запись на диск не удалась → снова degraded, **высоту блока назад не откатывает**.

**Вывод:** нет единого правила «пока диск не записал — считаем, что высота цепочки и регистры не изменились». Отсюда полевая боль: **память уехала вперёд**, **диск отстал или сломан**, после рестарта начинаются ошибки сохранения и рассинхрон.

## Таблица пробелов G1–G5 — «что это значит для меня»

| Код | Что ломается для оператора | После исправлений (идея, без сроков) |
|-----|---------------------------|-------------------------------------|
| **G1** | Блок уже «добавили в голове», на диск не записали — узел продолжает жить и расти. | Либо **не поднимать высоту**, пока диск не ок; либо **остановить запись новых блоков** до починки персиста. |
| **G2** | Handoff уже записан в память, файл не сохранился — повторный запрос может вести себя странно. | Либо **откат памяти**, либо журнал «неподтверждённых» операций до успешной записи. |
| **G3** | Как сценарий A выше: «импорт доставлен» в RAM, файла нет. | То же: откат или явный «ожидает записи» статус без ложного успеха. |
| **G4** | API и мониторинг видят узел «готов», хотя персист сломан — можно слать транзакции в уже больную систему. | Разделить: **«жив для чтения»** vs **«принимаю опасные записи»**. |
| **G5** | Нет штатного «откатиться к последнему якорю» — только ручные костыли. | Инструмент восстановления или автоматический rewind (отдельная задача). |
