# MVP V7 / Фаза 4: Внедрение CometBFT (Черновик плана спринта)

> **Статус документа:** Черновик. Создан для проработки ТЗ и вариантов реализации до открытия спринта и утверждения плана.  
> **Связь с головным планом:** См. `mvp_v7.md` § V7-6 (ADR-gate) и § Post-V7 / Фаза 4. Кодовая замена `Chain::seal` планируется после принятия ADR.

## 1. Техническое задание (ТЗ)

### Цель миграции
Заменить текущий встроенный консенсус (`pwm-core::Chain::seal` + round-robin / RFC16 кластерная аттестация) на **CometBFT** (бывший Tendermint) как полноценный BFT-движок.

### Основные требования
- **BFT-свойства:** Safety (2f+1) и Liveness при ≤ f византийских валидаторах.
- **Интерфейс:** Использовать ABCI (или ABCI++) для связи между CometBFT и PWM state machine. Текущий монолитный `Chain::seal` должен быть разложен на независимые хуки, которые можно вызывать из ABCI-колбэков. (См. подготовительную работу "State machine decoupling" выше.)
- **Сохранение семантики (принцип минимальных изменений):**
  - Формат блоков, транзакций, состояний (Account, policy, cross-shard EXPORT/IMPORT, conservation, Mode B escrow) по возможности остаётся совместимым или эволюционирует аддитивно.
  - Существующий `pwm-core` state machine (`apply_tx_with_ctx`, policy evaluation, lazy marks, emission, staking) переиспользуется с минимальными обёртками.
- **Валидаторы и экономика:**
  - Динамический набор валидаторов через staking (поверх V6 incremental PoS admission).
  - Сохранение PWM-экономики (rewards, marks, conservation delay) внутри ABCI-хук'ов.
- **Производительность и масштабирование:**
  - Не хуже текущего пути (с учётом работы по pipeline и worker pool в Sprint 1 + будущих оптимизаций).
  - Поддержка geo-sharding и cross-shard фактов (зависит от того, насколько чисто вынесены cross-shard факты до начала спринта).
- **Совместимость и миграция:**
  - Graceful / fork-совместимая миграция с текущего devnet (V6/V7 seal path).
  - Возможность rollback или параллельного запуска в переходный период.
  - Snapshot и persistence форматы должны позволять переключение консенсус-бэкендов.
- **Инструментарий:** Сохранить/адаптировать CLI (`tx-*`, `account-info`), TUI, RPC (/v1/*), block timing, ramp harness.

### Принципы дизайна интерфейсов (часть ТЗ)

Новые абстракции на границе консенсуса **обязаны** следовать правилам простоты:

- Максимум **4 аргумента** у функций и методов.
- **Лаконичные имена**.
- Минимизация глубоких вложений контейнеров (Option в Result в Vec и т.п.).
- Предпочтение **чётких сущностей с состояниями** (трейты + enum состояний) вместо функциональных "мешков" параметров.

Эти правила применяются ко всем preparatory рефакторингам и коду самого спринта.

### Out of scope (для первого спринта внедрения)
- Полная замена PQC (отдельная фаза).
- Полная переработка cross-shard протокола и bridge под CometBFT (если не критично для первого cut).
- Production slashing / evidence (может быть частично через CometBFT Evidence module + PWM stubs).
- Полная замена текущего RFC16 attestation на чистый CometBFT (можно держать как временный bridge).

**Дизайн-констрейнт:** любые новые интерфейсы должны соответствовать принципам (≤4 аргумента, лаконичность, ясные сущности с состояниями).

## 2. Вводные: почему и зачем миграция

### Обоснование из существующих документов

- **ADR 0001 (Consensus and node stack):**  
  Первоначально выбран собственный PoA-узел на Rust для скорости вывода MVP и контроля лицензий. Явно зафиксировано: «позже возможна замена движка консенсуса на внешний BFT (CometBFT) с сохранением формата состояния — отдельный ADR».

- **CONCEPT_ROADMAP.md:**
  - Текущий путь = Option A (incremental PoA → PoS поверх `Chain::seal` + RFC16 cluster).
  - V6/V7 = подготовка (stake-gated admission, address flags runtime, Mode B escrow, conservation, pipeline work).
  - V7 = **ADR-gate** по выбору BFT (CometBFT / custom Rust BFT / продолжение Option A).
  - Кодовая замена `Chain::seal` — **Фаза 4** после принятого ADR.
  - Тектоника слоёв явно отделяет Layer 8 (BFT replacement) от предыдущих.

- **mvp_v7.md и mvp_v6.md:**
  - V6 сознательно не трогал `Chain::seal`.
  - V7-6 — только решение и границы миграции (что меняет seal, RFC16-compat, rollback strategy, validator set interface).
  - Явное признание: текущий кластер (RFC16) — это промежуточный шаг, а не финальный BFT.

### Почему сейчас (контекст 2026)
- Phase 4 public testnet и реальные ставки требуют production-grade BFT (не PoA + кастомная аттестация).
- Команда накопила опыт с текущим путём (pipeline + worker pool в Sprint 1, state machine, cross-shard, V6 PoS admission).
- Есть Rust-реализация CometBFT (cometbft-rs и родственные порты), что позволяет заимствовать код, хотя и не исключает значительных адаптаций под PWM-модель (account-based state, geo-sharding, dumb contracts, conservation queue, Mode B escrow).
- Откладывание дальше увеличивает технический долг и риск несоответствия Whitepaper (BFT-элементы).

### Текущая модель консенсуса (что именно нужно будет заменить)

Текущий `Chain::seal` (в `pwm-core`) владеет:
- Выбор продюсера (на базе active_validator_indices из V6).
- Применение батча транзакций (`apply_tx_with_ctx`).
- Epoch transitions, reward, conservation drain, lock refunds.
- Вычисление state_root и tx_root.
- Подпись блока и верификация (Ed25519 от валидатора).

RFC16 добавляет:
- Кластерную аттестацию (proposer + 1–2 attesters).
- Failover при пропуске.

CometBFT возьмёт на себя:
- Networking, mempool gossip (частично), voting, evidence, block production, validator set updates.

**Критическая развязка**, которая должна быть сделана **до** CometBFT-спринта:
- State transitions должны быть вызываемы независимо от блочной финальности.
- Validator set и продюсер selection должны иметь чистый интерфейс (максимум 4 аргумента, лаконичные имена).
- Mempool / tx ingress должен уметь работать с внешним BFT-движком.

### Принципы дизайна будущей границы консенсуса

При проектировании интерфейсов, которые заменят `Chain::seal`, мы придерживаемся следующих правил (чтобы избежать типичных Rust-антипаттернов и обеспечить ясность):

- **Не более 4 аргументов** у публичных функций и методов.
- **Лаконичные имена** сущностей и методов (избегать длинных описательных названий).
- **Избегать матрёшек-контейнеров**: минимизировать глубокое вложение `Option`, `Result`, `Vec` внутри друг друга. Предпочитать плоские структуры или dedicated типы.
- **Предпочтение ООП-стиля**: когда возможно — использовать трейты (аналог наследования) и ясные абстракции сущностей, обладающих **состояниями** (например, enum `ConsensusPhase` или структура с внутренним состоянием `ProducingBlock`, `Committing` и т.д.).
- **Ясная абстракция сущности**: вместо "мешка параметров" — выделять сущности с чёткой ответственностью и жизненным циклом (ConsensusDriver, BlockProducer, ValidatorSetManager и т.п.).
- **Debug-friendly parallelism**: поскольку миграция на CometBFT + предшествующая работа по pipeline является большим шагом в параллелизм, дизайн обязан обеспечивать воспроизводимую отладку. Основной механизм — **общий interlocked-point-id** (монотонно возрастающий идентификатор, назначаемый атомарно при ключевых событиях). Это позволяет восстанавливать глобальный порядок событий в логах даже при многопоточности.

**Анализ текущего `Chain::seal`**: 
Монолитный метод с большим количеством ответственности, неявными состояниями и потенциально сложными вложенными структурами. Это классический кандидат на разбиение на сущности с состояниями.

Эти принципы должны учитываться уже на этапе preparatory работ. Подготовка должна включать прототипы новых абстракций (даже если они сначала будут тонкими обёртками над текущим кодом).

### Риски текущего пути (без миграции)
- Ограниченная отказоустойчивость (кластер 2-of-2 / 2-of-3).
- Сложность доказательства BFT-свойств.
- Сложность добавления новых валидаторов и slashing.

### Зависимости и подготовительные работы для предыдущих спринтов

Чтобы CometBFT-спринт не превратился в большой рефакторинг ядра, следующие вещи желательно подготовить **до** его открытия:

| Область | Что нужно подготовить заранее | Где можно делать (примерно) | Почему важно для CometBFT |
|---------|-------------------------------|-----------------------------|-----------------------------|
| **State machine decoupling** | Чистый интерфейс для применения транзакций и хуков (`apply_batch`, `on_begin_block`, `on_end_block`, `on_commit`) без знания о `Chain::seal` | Sprint 1 (pipeline) + последующие | ABCI требует отдельные колбэки вместо монолитного seal |
| **Validator set** | Стабильный интерфейс `active_validator_indices` + staking-based updates (уже частично в V6) | V6 + V7-3 / V7-5 | CometBFT сам управляет validator set; PWM должен уметь его обновлять |
| **Block / Header abstraction** | Абстракция заголовка блока, корней, подписей (чтобы можно было подставлять CometBFT-формат) | Sprint 1 + текущий | Изменится формат блока и доказательств |
| **Mempool / Ingress** | Pipeline, который может кормить как внутренний seal, так и внешний BFT (CheckTx / DeliverTx) | Sprint 1 (уже в работе) | CometBFT имеет собственный mempool |
| **Epoch / Reward / Conservation hooks** | Отдельные функции, вызываемые по высоте блока, а не только внутри seal | V6-8 (conservation) + V6-3 (epoch) | Должны вызываться из `BeginBlock`/`EndBlock` |
| **Snapshot / Persistence** | Стабильный формат, который не зависит от конкретного консенсус-движка | V6 + последующие | Нужно уметь загружать state после смены движка |
| **Тестирование** | Harness, позволяющий запускать один и тот же сценарий с разными консенсус-бэкендами (ramp, CY cluster, e2e) | Sprint 1 + V7-5 | Критично для миграции и rollback |
| **Cross-shard факты** | Минимальные предположения о том, кто производит блоки | Уже в roadmap | CometBFT может изменить тайминг и лидерство |
| **Дизайн абстракций** | Выделение сущностей с состояниями (не более 4 аргументов в интерфейсах, избегание глубокого вложения Option/Result). Примеры: `ConsensusDriver` с фазами, `BlockProducer` trait | Sprint 1 + подготовка перед BFT | Будущий ABCI-код должен быть простым и понятным, а не матрёшкой |
| **Раннее прототипирование абстракций** | Создать тонкие трейты/сущности с состояниями уже в preparatory спринтах (даже если они сначала делегируют старому коду) | Перед BFT-спринтом | Позволяет проверить дизайн на практике и избежать больших переписываний |
| **Debug + Profiling instrumentation** | Внедрить interlocked-point-id + отдельную очередь + dedicated writer. Встроить захват wall-time + CPU usage при присвоении point (inter-point benchmarking). JSONL dump по настройке. **Полная возможность включать/выключать через RPC на лету** + учёт стоимости самого измерения. Начать с preparatory работ | Sprint 1 + preparatory перед BFT | Критично для отладки, профилирования задержек и CPU в параллельных путях. Измерение не должно неконтролируемо искажать поведение. |

**Рекомендация:** Перед открытием CometBFT-спринта провести ревью списка выше и либо закрыть, либо явно задокументировать оставшиеся риски. Приоритет — подготовка чистых, лаконичных интерфейсов с состоянием сущности. Прототипы новых абстракций должны проходить review на соответствие принципам дизайна.

Подробная методология отладки параллельного кода (interlocked-point-id, инструментарий, работа с бряками и watches) описана в отдельном документе: [docs/debug/parallel-debugging-methodology.md](../debug/parallel-debugging-methodology.md).

## 3. Пути имплементации (варианты на момент открытия спринта)

Примечание: выбор пути сильно зависит от того, насколько хорошо будут выполнены подготовительные работы из таблицы выше.

На момент утверждения плана спринта доступны следующие основные направления (выбор делается в начале спринта после исследования):

### Путь A: Классический ABCI++ Application (рекомендуемый по умолчанию)
- CometBFT выступает в роли BFT-движка (networking, voting, block production, evidence).
- PWM реализуется как **ABCI application**:
  - `CheckTx` / `CheckTxAsync` — предварительная валидация (mempool).
  - `DeliverTx` — применение транзакции (аналог `apply_tx`).
  - `Commit` — финализация блока, возврат state root.
  - `InitChain`, `EndBlock`, `BeginBlock` — для epoch transitions, rewards, conservation drain и т.д.
- Преимущества:
  - Стандартный путь, много примеров и tooling.
  - CometBFT берёт на себя сложность BFT.
  - Можно переиспользовать существующий `pwm-core` state machine почти без изменений (обёртка), если decoupling из таблицы выше выполнен.
- Недостатки / адаптации:
  - Нужно адаптировать модель продюсера/аттестатора (RFC16) под CometBFT validator set (зависит от работы по validator interface в предыдущих спринтах).
  - Изменение формата заголовка блока, подписей, доказательств.
  - Производительность: overhead ABCI (gRPC / socket) — нужно профилировать (использовать существующий ramp harness).
- Требует: изучения cometbft-rs + ABCI интерфейса + наличия чистых хуков из подготовительных работ.

### Путь B: Тесная интеграция через Rust-библиотеки CometBFT
- Использовать низкоуровневые Rust-компоненты CometBFT (consensus state machine, p2p, mempool) напрямую внутри `pwmd`.
- Не полный внешний процесс, а embedded / библиотечное использование.
- Преимущества:
  - Меньше IPC-overhead.
  - Больше контроля над интеграцией с текущим pipeline (из Sprint 1) и worker pool моделью.
- Недостатки:
  - Меньше battle-tested "из коробки".
  - Больше работы по адаптации (нужно портировать/обёртывать значительную часть логики) — сильно зависит от качества decoupling в предыдущих спринтах.
  - Риск расхождения с upstream CometBFT.

### Путь C: Гибрид / поэтапная миграция
- Сначала перенести только same-shard консенсус на CometBFT.
- Cross-shard / federation оставить на текущем bridge-протоколе (или адаптировать).
- Использовать CometBFT только для валидатор-сета и блочной финальности, а часть логики (reward, policy) оставить в PWM.
- Преимущества: снижает риск, позволяет итеративно мигрировать.
- Недостатки: сложнее поддерживать два пути, возможны инвариантные проблемы.

### Путь D: Custom BFT (альтернатива CometBFT)
- Разработка или доработка собственного BFT-движка на Rust (на базе текущего кластера + улучшения).
- Рассматривается, если ADR покажет, что CometBFT не подходит по производительности / модели (sharding, account-based и т.д.).
- В плане спринта должен быть явный сравнительный анализ с CometBFT.

### Ключевые вопросы для выбора пути (должны быть закрыты до/в начале спринта)
- Какая Rust-реализация CometBFT наиболее зрелая на момент старта (cometbft-rs, informal-tendermint-rs и др.)?
- Насколько глубоко нужно менять `BlockHdr`, `SignedTx`, snapshot формат? (Зависит от decoupling в предыдущих спринтах — см. таблицу выше.)
- Как интегрировать staking-based validator set (V6) с CometBFT validator updates?
- Сохранять ли элементы RFC16 (attestation) как дополнительный слой или полностью заменять?
- Требования к rollback / fork-совместимости с текущим devnet.
- Степень готовности preparatory работ из таблицы "Зависимости и подготовительные работы".

## Следующие шаги после утверждения плана (ориентир)

1. Выбор пути имплементации (A/B/C) + обоснование.
2. Исследование выбранной Rust-библиотеки + прототип ABCI-обёртки.
3. Определение точек интеграции (`apply_tx` → `DeliverTx`, epoch logic → `EndBlock` и т.д.).
4. Миграция / адаптация текущего `Chain` и `pwmd` lifecycle.
5. Тестирование (e2e, fork-compat, performance сравнение с текущим путём).
6. Обновление документации, ADR/RFC, runbooks.
7. План миграции devnet / testnet.
