# Review: sync console progress slice (`pwmd::sync`)

**Ticket:** `tasks/20260513-slice-sync-console-progress.json`  
**Scope:** русскоязычные операторские INFO на target `pwmd::sync` с троттлингом; поля `SyncPeerState` (`sync_log_*`); вызовы из `sync_live.rs` (`on_tip`, успешный apply batch, `on_cup_chunk`, `on_cup_done`); юнит-тесты чистых хелперов.

---

## 1. Scope recap

Тикет требовал видимый прогресс same-shard sync на консоли без спама: отличать канал от `pwmd::peer` (консоль/main intentionally режут peer-target), оценка догона (процент и остаток блоков), троттлинг по времени и/или изменению процента, вызовы из live/catch-up после обновления известного tip. Реализация добавляет хелперы `sync_prog_snap` / `sync_prog_tick`, асинхронный `maybe_log_sync_prog`, константу интервала `SYNC_PROG_MIN_MS` (7 s), состояние троттла на peer в `SyncPeerState`.

Ссылочные документы из тикета (`logging.rs`, RFC sync v1, MVP v2 sprint) проверены точечно на согласование с политикой таргетов; MVP checklist в JSON пустой — формальная трассируемость только через brief/references.

---

## 2. Requirements fit

**Соответствует цели:** сообщение оператору на русском, только процент и остаток блоков (без хешей и без `node_id` в строке `pwmd::sync`), target не начинается с `pwmd::peer`, поэтому проходит консольный и main-file слой с фильтром `!is_peer_target`.

**Троттлинг:** комбинация минимального интервала и шага процента ≥ 1 плюс одноразовое событие «догнал» (`done_now`) и повтор после регресса (`lag_resume`, когда снова есть отставание после завершённой синхронизации). Это разумно согласуется с формулировкой тикета.

**Хуки:** `on_tip` (после известного peer head ≥ local), после успешного `apply_blk_batch` в потоке блоков, после chunk catch-up и при завершении CUP — покрывают основные моменты обновления локального tip относительно известного peer ceiling.

**Зазоры:** интеграционного теста, что строка реально попадает на консольный слой при типичном `RUST_LOG`, нет (ожидаемо для лаб-слайса); поведение при очень малом `peer_tip_h` (грубые проценты) не специфицировано в тестах отдельно.

## 4. Safety

**Утечки секретов:** в событии `pwmd::sync` нет ключей, адресов, полных хешей блоков или идентификаторов пира — только агрегированные числа; риск случайной эксфильтрации через этот канал низкий.

**DoS / спам:** интервал 7 s и порог процента ограничивают частоту; состояние на peer сериализуется через одну запись в `handshake`, гонки между двумя вызовами для одного peer упираются в mutex и приводят к последовательному обновлению троттла, а не к двойному логу без проверки.

**Panics:** горячие пути используют saturating-арифметику; обёртка логирования не добавляет `unwrap` на данных от сети.

**Lock ordering:** на всех просмотренных путях (`on_tip`, apply batch, `on_cup_chunk`, `on_cup_done`) перед `maybe_log_sync_prog` блокировки `handshake`/`inner` уже отпущены; внутри `maybe_log_sync_prog` берётся только краткая `handshake.write`. Явной инверсии порядка относительно типичного «сначала inner, потом handshake» здесь не видно — взаимная блокировка маловероятна при существующей дисциплине.

---

## 5. Tests

Покрыто: граничные случаи `sync_prog_snap` (нулевой tip, почти догнал, локальный уже выше peer); сценарий троттла по времени, игнор повторного лога при малом dt, финальный 100%, затем повтор при новом отставании (`lag_resume`).

Не покрыто явно: первый лог при «ровно истёк интервал без смены pct» при очень медленном росте высоты (зависит от трактовки `pct_ok`); это скорее наблюдение, не блокер для лаб-слайса.

## 6. Verdict

**PASS_WITH_NITS** — функционально соответствует тикету, безопасность и троттлинг адекватны; замечания ниже механические/улучшение наблюдаемости тестами.

**Nits (не блокирующие):**

1. Юнит-тест можно расширить отдельным кейсом «lag_resume»: после `sync_log_done == true` и `rem == 0` снова выросший peer tip должен вызвать событие без ожидания полного интервала (ветка уже реализована в коде — тест только закрепит регрессию).
2. При желании единообразия с англоязычными трассами в том же бинарнике стоит позже свериться с практикой остальных INFO для оператора (не политика `logging.rs`, а стиль сообщений).
