# ADR 0006: Address flags and non-disableable profiles

## Status

**Accepted as V5 spec-only contract.** Runtime enforcement is explicitly deferred to V6. V5 must not add an `address_flags` field to `Account` and must not enforce these flags in `validate_tx_shape` or `state::apply_tx`.

## Context

PWM addresses already carry domain and flag-like semantics in the address bytes generated by HD derivation/bruteforce. V4 implemented policy state in accounts, but some future protection profiles must be tied to address identity itself rather than removable account state.

Examples:

- a corporate address that always requires cosign for protected actions;
- a custody/whale address whose outgoing transfers enter a conservation delay;
- addresses where ordinary policy transactions cannot disable baseline protection.

## Decision

Define the lower bits of the existing address flag field as protocol predicates:

```text
bit 0: COSIGN_NON_DISABLEABLE
bit 1: CONSERVATION
bits 2..7: reserved for future accepted ADR/RFC
```

The bits are part of the address representation. They are selected during address generation and verified by decoding the address, not by reading account state.

No new `Account.address_flags` field is introduced.

## Flag Semantics

### `COSIGN_NON_DISABLEABLE`

When V6 enforcement is active:

- `cosign_required` is treated as a mandatory baseline policy for protected actions.
- Ordinary `PolicyTx` cannot deactivate or weaken the required cosign posture.
- Attempts to remove the mandatory profile must be rejected with a stable policy error.
- Emergency routing and rescue flows may still exist, but they must satisfy the mandatory cosign requirement unless a later ADR defines a narrower exception.

### `CONSERVATION`

When V6 enforcement is active:

- outgoing `Transfer` from a conservation address is not executed immediately;
- it enters a delayed execution window, with the V5 design target of 24 hours expressed by chain-height parameters in V6;
- during the window, owner/rescue/cosign-authorized recovery actions may redirect or cancel before final execution, subject to a future ADR;
- incoming transfers are not delayed by this flag unless a later ADR explicitly extends the rule.

V5 does not implement this queue, mempool behavior, seal behavior, or cancellation model.

## Validator Behavior

V5 validator behavior:

- validators may decode and display the bits;
- validators must not enforce `COSIGN_NON_DISABLEABLE` or `CONSERVATION`;
- transaction validation and apply paths must not branch on these bits in V5.

V6 validator behavior, after a separate implementation ADR/RFC:

- decode flags from the address;
- enforce mandatory cosign profiles and conservation delay in consensus-critical paths;
- reject transactions that attempt to bypass or disable non-disableable profiles.

## Compatibility

Because the flags live in the address bytes, accounts created before V6 keep their original flag posture. There is no migration that writes flag state into accounts.

Wallet and CLI tooling may expose flag generation/inspection before enforcement, as long as UI copy clearly marks enforcement as future V6 behavior.

## Non-Goals

- No new account field.
- No V5 runtime enforcement.
- No delayed transfer queue in V5.
- No policy DSL.
- No mutable "upgrade" of address flags after address creation.
