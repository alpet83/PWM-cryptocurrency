# Review: wait `init.is_ready()` before initial peer wire exchange

## 1. Scope recap

- **RCA / ticket context:** `tasks/20260517-attester-sync-stall-at-4pct-debug-round2.md` — гонка: входящая сессия принималась во время `LoadingSnapshot`, до готовности `app.init` шли обмен и sync; затем snapshot loader перезаписывал цепочку, оставляя wire-состояние и ожидания удалённой стороны «от genesis».
- **Заявленный минимальный срез:** после handshake, до `send_cross_shard_facts`:
  - `crates/pwmd/src/transport/peer_session/inbound.rs`
  - `crates/pwmd/src/transport/peer_session/seed/session/initial_exchange.rs`
- **Цель среза:** не выполнять начальный обмен фактами/вьюхами/кластером и не входить в фазу, где применяется sync, пока `App::init` не в фазе готовности по `is_ready()`.

## 2. Requirements fit

**Соответствует заявленному минимальному срезу.** В обоих файлах добавлен цикл опроса с `app.init.read().await.is_ready()` и `sleep(200 ms)` непосредственно перед первым `send_cross_shard_facts`, так что пост-handshake исходящая «первая волна» не стартует до готовности init.

**Частичное расхождение с полной формулировкой RCA (на будущее, не как блокер этого среза):** в отладочном отчёте отдельно рекомендовано по возможности ставить барьер **до** построения локального `HelloAck`, чтобы `chain_tip_height` в ack отражал уже восстановленную из snapshot цепочку. Текущая правка оставляет построение `local_hello` / запись принятого `HelloAck` **до** ожидания; устраняется основная угроза (ранний sync/merge до конца load snapshot), но кратковременное рекламирование «старого» tip в ack теоретически сохраняется на время загрузки snapshot.

## 3. Style and module shape

- Дублирование небольшого цикла ожидания с флагом `wait_logged` — в духе существующего `run_seed_session` (ожидание до connect), отдельной вспомогательной функции нет — приемлемо для минимального патча; при росте числа call sites имеет смысл вынести в один helper (как советовал RCA).
- **`python scripts/check_rust_fn_name_segments.py`** на указанных путях: нарушений политики имён нет (`violations`: пусто).
- `//!` в файлах уже есть; wire-версия протокола не затронута.
- Комментарии на английском, по делу.

## 4. Safety

- **«Deadlock», если init никогда не станет ready:** не классический взаимный lock, но **неограниченный poll**: задача на каждое входящее соединение может вечно крутиться в цикле (как и внешний цикл seed при «вечно не ready»). Риск нагрузки: много принятых TCP при зависшей инициализации → много висящих задач. Это согласовано с текущим паттерном ожидания в кодовой базе, но не добавляет верхней границы или отказа с явной причиной.
- **Лог-шум:** одна строка `info!` на сессию при первом входе в ожидание (`wait_logged`) — разумно, не спамит на каждый тик.
- **Handshake timeout:** таймаут `handshake_timeout_ms` применяется к чтению удалённого `Hello` и записи `HelloAck`. **Период ожидания `is_ready()` к handshake-таймауту не привязан:** после успешного ack сессия с точки зрения handshake уже «завершена», а пауза может длиться столько, сколько длится snapshot load. Удалённая сторона может упереться в свои idle/read таймауты или накопить данные в сокете, пока локальная сторона спит и **не читает** из stream — для типичных задержек в секунды обычно терпимо, для аномально долгой инициализации стоит держать в голове как операционный риск.
- **ReadyDegraded:** `InitState::is_ready()` в `crates/pwmd/src/state.rs` возвращает true для `Ready` и `ReadyDegraded` — поведение согласовано с ожиданием «можно обслуживать транспорт в деградированном ready».

## 5. Tests

- Автотеста на сценарий «inbound при `LoadingSnapshot` не маршрутизирует / не применяет sync до ready» в диффе не видно. RCA явно просил регрессию; для полного закрытия риска полезен сфокусированный тест (или harness), без опоры на длинные sleep в проде.

## 6. Verdict

**Approve with nits.**

Приоритетные nits:

1. (RCA-depth) Рассмотреть перенос ожидания **выше** построения локального `HelloAck` на inbound, если нужна строгая согласованность рекламируемого tip с post-snapshot цепочкой.
2. Явная **верхняя граница** ожидания или корректное закрытие сессии с метрикой, если init застрял, чтобы не копить неограниченно задачи на accept.
3. Добавить **регрессионный тест** по мотивам RCA.
4. При очень долгой паузе стоит оценить **чтение/дрейн** или явно задокументировать допущение, что peer не забьёт TCP-буфер до блокировки отправителя до выхода из ожидания.
