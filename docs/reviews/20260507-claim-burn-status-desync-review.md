# Review: рассинхрон статуса Claim/Burn в TUI (node-1)

## Scope

Исследование симптома: до F5 в таблице ~996 marks; после F5 баланс marks не меняется, в нижней строке «Claimed 0 marks»; после burn 1 mark и закрытия формы marks «прыгают» до ~2495, при этом нижний статус остаётся «Claimed 0 marks (none matured)».

Проверены: логи runtime node-1 (`terminals/1.txt`), ветка F5 и обновление UI в `pwm-tui`, `submit_claim` / `submit_burn_mark`, семантика Claim/Burn в `pwm-core`, путь обработки `POST /v1/tx` в `pwmd` (очередь vs немедленный seal).

Прод-код не изменялся.

## Reproduced timeline (логи + код)

**Журнал node-1** (фрагмент вокруг сценария Claim → Burn):

- `08:39:44.728` — `tx routing guard` для локальной account-op (типичный prelude к claim).
- `08:39:45.924` — `tx commit delta: kind=claim` для отправителя `2cfb…`; в строке delta отражаются только **PWM balance** и **nonce** (marks в эту строку не попадают — поэтому по одному логу нельзя считать зачисленные marks).
- `08:39:58.825` — routing guard для cross-domain burn.
- `08:39:59.918` — `tx commit delta: kind=burn_mark`; nonce уходит 8→9.

Интервал ~14 с между commit claim и commit burn согласуется с тем, что пользователь успевает открыть форму, выполнить burn и дождаться следующего включения транзакций в блок.

**Цепочка в TUI (F5):**

1. Синхронный `submit_claim` → при HTTP-success функция возвращает **`Ok(0)`**, не число реально материализованных marks (`tx_submit.rs`).
2. В `tui_loop.rs` при `Ok(n)` полагаются на `n`: при `n == 0` всегда формируется текст **«Claimed 0 marks (none matured)»**, даже если узел принял успешный claim с ненулевым эффектом на цепочке.
3. Сразу вызывается **`poll_snapshot`** и перезаписываются `ui.rows`. `/v1/accounts` отражает **уже применённые** к tip состояния.

**Очередь mempool (`pwmd`):**

Для тел типа Claim/Burn (не Export/Import) обработчик помещает tx в **mempool** (`pool.push`) и отвечает **204 No Content** без тела с суммой claim — см. ветку `_ =>` в `handlers_tx.rs`. То есть успешный ответ RPC **не гарантирует**, что следующий `poll_snapshot` уже увидит новые marks; это возможно только после seal очередного блока.

**После burn:**

- Отправка burn асинхронна через `RpcTask::SubmitBurnMark`; по `SubmitDone` снимается inflight и ставится **`RpcTask::Poll`** (`tui_loop.rs`).
- Периодический Poll каждую 1 с также подтягивает актуальное состояние.

Итоговый «прыжок» marks после burn и следующего Poll объясняется тем, что к этому моменту в tip уже попали **и отложенный claim, и burn** (или хотя бы claim, если burn ещё не применён — но в описанном кейсе рост до ~2495 означает доминирующий вклад claim минус единичный burn относительно отображённых ранее ~996).

## Root cause

**Primary (определённый дефект UX в клиенте):**

`submit_claim` при `status.is_success()` всегда возвращает **`Ok(0)`**. Логика F5 считает это «зачислено 0 marks» и показывает **ложное** сообщение «Claimed 0 marks (none matured)». Это не следует из состояния цепочки и не следует из тела ответа RPC (204 без счётчика).

**Secondary (естественная задержка отображения таблицы):**

Claim попадает в mempool и попадает в состояние аккаунта только после seal; **немедленный** `poll_snapshot` после приёма tx может вернуть **старые** marks. Пользователь видит неизменную колонку Marks при уже «успешном» claim — это **рассинхрон отображения с моментом включения tx в блок**, а не обязательно ошибка начисления.

**Tertiary (липкий статус в футере):**

`action_note` выставляется один раз при F5 и **нигде не сбрасывается** (единственное присваивание в `tui_loop.rs`). Даже после успешного burn и обновления строк таблицы зелёная строка в футере может продолжать показывать устаревший текст claim.

## Correctness bug или UX/state-sync?

- **Ядро (`pwm-core` state):** Claim добавляет `effective_units` к `marks`, BurnMark уменьшает `marks` при достаточном остатке — для описанного сценария это **согласуется** с наблюдаемым ростом после того, как обе операции попали в учётную запись RPC.
- **Вывод:** это **UX/state-sync bug в TUI** (неверная интерпретация результата submit + опционально отсутствие ожидания/повторного poll), а не указание на некорректную арифметику marks на цепочке по имеющимся данным.

Ложное «none matured» особенно вводит в заблуждение: пользователь может решить, что claim не сработал, хотя tx принят и позже материализуется.

## Concrete fix list (для pwm-coding)

1. **`crates/pwm-tui/src/tx_submit.rs` — `submit_claim`**  
   - Убрать семантику «вернуть количество marks»: при 204 **не возвращать `Ok(0)` как счётчик** (например `Ok(())` или отдельный enum успеха). Либо, если API расширят JSON-телом с `claimed_units`, парсить его — до расширения API счётчик из клиента **недоступен**.

2. **`crates/pwm-tui/src/tui_loop.rs` — ветка F5**  
   - После успешной отправки claim не выводить «Claimed 0 marks (none matured)» на основе фиктивного нуля; использовать нейтральную формулировку вроде «Claim tx accepted; marks update after seal» или «Claim queued; refreshing…».  
   - Опционально: короткий **retry poll** (несколько попыток с небольшим backoff) до изменения `marks` или `nonce` выбранного owner или до таймаута — чтобы таблица чаще совпадала с ожиданием после приёма tx.

3. **`action_note`**  
   - Сбрасывать или перезаписывать после ключевых событий (успешный burn flow, новый Poll с подтверждением), чтобы не показывать устаревший claim-текст рядом с уже актуальными marks.

4. **(Опционально, контракт)**  
   - Если продуктов нужен точный счётчик без polling-diff: расширить успешный ответ `POST /v1/tx` для Claim (нарушает текущий «204 пустое тело» — отдельное решение по совместимости).

## Tests / наблюдаемость

- Юнит-тест на `submit_claim`: при успехе ответа не трактовать возвращаемое значение как число marks (после смены сигнатуры).
- Интеграционный или UX-тест сценария: submit → до seal marks прежние → после seal обновились (можно мок RPC или узел с контролируемым seal).

Критичность для пользователя: высокая с точки зрения доверия к интерфейсу (ложное «0 marks» и липкий футер). Исправления локализованы в TUI и не требуют менять экономику marks в core.
