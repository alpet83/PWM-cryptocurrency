# S15-S3.15.2 — архитектурный концепт: снапшоты при длинной цепочке

## Scope recap

Слайс **S15-S3.15.2** рассматривается как **архитектурный концепт** без обязательства по коду. Контекст: в `crates/pwmd/src/snapshot.rs` структура **`SnapshotData`** содержит **`blocks: Vec<Block>`** и **`state: ChainState`**. При тысячах блоков старт ноды может быть медленным из‑за полной десериализации JSON и пикового потребления RAM. Цель ревью — зафиксировать наблюдения, направления оптимизации, риски и разумный MVP.

## 1. Цель

- **Сократить время до состояния ready** после рестарта при наличии длинной истории блоков в снапшоте.
- **Снизить пик RAM** при загрузке и удержании данных, необходимых для нормальной работы ноды (валидация, RPC, синхронизация), без требования держать «всё сразу» в памяти в том виде, как сегодня задаёт монолитный JSON.

## 2. Наблюдения (что дорого сегодня)

- **Полная десериализация блоков**: весь массив `blocks` читается из JSON и материализуется как `Vec<Block>` — линейно по числу блоков и размеру тел транзакций. Это одновременно CPU (парсинг, аллокации) и память (живые структуры).
- **Размер файла снапшота**: один крупный артефакт усугубляет время чтения с диска и работу сборщика мусора при распределении объектов.
- **Отсутствие инкрементальных чекпоинтов**: если семантика операций «полный снимок = genesis-подобное состояние + вся история», то каждый рестарт повторяет ту же тяжёлую загрузку; нет промежуточного «закреплённого» состояния с отрезанной или вынесенной историей по политике хранения.
- **Смешение ролей в одном артефакте**: то, что нужно для **консенсусно валидного состояния** (`state`), и то, что нужно для **полной истории блоков**, оказывается в одном потоке загрузки — даже если для текущей высоты часть старых тел не нужна в RAM постоянно.

*(Точные профили по времени и памяти в этом слайсе не измерялись; при необходимости их стоит зафиксировать отдельным benchmark до выбора формата.)*

## 3. Варианты оптимизации (концепты, не финальный RFC)

### 3.1 Periodic state checkpoints

Идея: периодически фиксировать **закоммиченный `ChainState`** вместе с **высотой** и **криптографическим якорем цепочки** (например, хеш последнего включённого блока или согласованный идентификатор «конца отрезка»). Старую историю блоков либо **архивировать**, либо **подрезать** по **retention** (политика хранения: сколько высот или сколько мегабайт истории обязательно для узла данного класса).

Плюсы: рестарт от «последнего чекпоинта» сводит объём replay к окну от чекпоинта до tip. Минусы: нужна чёткая спецификация того, что считается «достаточным» состоянием для участия в сети и ответов API.

### 3.2 Headers vs full bodies

Разделить то, что **онлайн-нода обязана иметь под рукой** для валидации новых блоков и ответов на типовые запросы, и то, что можно **подгружать по запросу** (lazy fetch, отдельное хранилище, peer).

- **Заголовки и минимальные связки** (высота, родитель, корни, подписи по модели консенсуса) — обычно компактны и нужны для проверки цепочки и fork-choice.
- **Полные тела блоков** — тяжёлые; для исторических диапазонов может быть достаточно хранить их в сегментированном виде или выдавать через API «по диапазону» без полной загрузки всего вектора в RAM при старте.

Граница зависит от того, какие RPC и какие гарантии даёт нода (full history vs pruned).

### 3.3 Lazy segments (файловые сегменты блоков)

Хранить блоки **по диапазонам высот** в отдельных файлах или записях; при старте — не десериализовать всё в `Vec`, а открывать **сегменты** и при необходимости использовать **memory-mapped** или **потоковое чтение** для конкретного диапазона. В RAM держать только «горячий хвост», индекс высоты → местоположение сегмента и смещение, метаданные для целостности сегмента.

Когда допустимо не держать все тела в RAM: когда протокол и оператор согласны с **pruning**, **архивным узлом отдельно**, или когда полная история доступна через внешнее хранилище и индекс достаточен для точечных запросов.

### 3.4 Связь с S15-S4 (snapshot abstraction: JsonFile vs Db)

В спринтовом плане уже заложена абстракция хранилища снапшотов (**`JsonFile` как baseline** и интерфейс под **`Db`**). Логичное размещение артефактов:

- **Индекс высоты → расположение блока** (файл сегмента, ключ в БД, offset, опционально размер и версия кодека) — в слое абстракции хранилища, а не размазанным по ad-hoc JSON.
- **Метаданные снапшота** (версия схемы, высота чекпоинта, хеш цепочки, политика retention, признак «полный архив / усечённый») — рядом с корнем хранилища или в отдельной таблице/файле конфигурации снапшота.
- **`JsonFile`** остаётся эталоном для простоты и детерминированного replay там, где это требуется политикой; **`Db`** даёт индексацию, частичное чтение и TTL без разбора гигантского одного файла.

Так S3.15.2 (устранение узкого места старта) стыкуется с S15-S4: новые индексы и сегменты — это поля и методы backend’а, а не только форма одного JSON.

## 4. Риски и инварианты

- **Replay и детерминизм**: любое усечение истории или отложенная загрузка тел не должны приводить к расхождению **валидного состояния** с тем, что ожидает консенсус и тесты parity. Нужны явные правила «от какого чекпоинта можно продолжать» и как верифицируется целостность.
- **Автоснапшот каждые N блоков**: снижает окно replay, но добавляет IO и консистентность при сбое посередине записи; нужны атомарная замена файлов или журналирование на уровне backend’а.
- **Cross-shard roaming в снапшоте**: в `SnapshotData` уже присутствуют связанные поля (например, roaming и cross-shard в wire-форме). При разбиении хранилища нельзя потерять согласованность между **состоянием цепочки**, **роумингом** и **cross-shard** — либо единая транзакция записи чекпоинта, либо явные версии и откат.
- **Политика «что является источником правды»**: если часть блоков вынесена в архив, узлы разных классов (full / pruned) должны иметь документированное поведение при запросах истории.

## 5. MVP vs later

**MVP (маленький шаг без полной перестройки)**

- Зафиксировать **метаданные чекпоинта** (высота + якорь цепочки) и путь к последнему успешному снапшоту; опционально **двухфазная запись** (временный файл + rename) для безопасности.
- Ввести **конфигурируемый retention** на уровне политики: что попадает в «горячий» снапшот при сохранении (даже если пока всё ещё один JSON — подготовка контракта).
- **Профилирование** загрузки: разделить время на JSON parse, десериализацию `blocks` vs `state`, чтобы следующий шаг был данными, а не интуицией.

**Later**

- Разнесение **headers / bodies** по файлам или таблицам, **сегменты по высоте**, mmap.
- Полная интеграция с **Db** backend и индексы высоты из S15-S4.
- Операторские режимы **archive node** vs **pruned** с разными SLA по RPC.
