## 1) Точное текущее поведение (последовательность)

**Условные обозначения:** «пир» — установленная TCP-сессия (исходящий seed в steady-loop или inbound после handshake).

### Исходящая сторона (отправитель)

1. В **steady** для seed: каждые `heartbeat_interval_ms` (минимум 200 ms в коде цикла) узел шлёт heartbeat, затем опционально cross-shard facts, account views, затем вызывает `send_sync_tx_batch`.
2. В **inbound**: на каждый входящий `PeerWireMsg::Heartbeat` после ответа `HeartbeatAck`, cross-shard facts и account views вызывается тот же `send_sync_tx_batch`.
3. `send_sync_tx_batch` **рано выходит**, если: другой `cluster.domain_hi`; у пира нет `supports_sync_v1()`; у пира нет или нулевой `sync_profile.max_txs_per_msg`; мемпул пуст после `pool.snapshot(SYNC_TX_SCAN_CAP)` (до 256 элементов сканирования).
4. Иначе формируется список до `min(remote.max_txs_per_msg, SYNC_TX_OUT_CAP)` (константа **32**) транзакций: обход снимка мемпула в порядке снапшота, для каждой tx проверяется «уже отправляли этому **node_id** за последние **30 s**?» (`mempool_gsp.tx_sent_peer_ms`).
5. Если список непустой — инкремент `seq_no`, сериализация `PeerWireMsg::SyncTxBatch { hdr, txs }` на поток (JSON payload + длина, как у прочих wire-сообщений).

### Входящая сторона (получатель)

6. Любой `SyncTx*` кадр на p2p попадает в `route_sync_stub` (в т.ч. из steady multiplexer или initial exchange).
7. Учёт метрик: `sync_v1_msg_seen_total`; для sync-tx кадров — прибавление `sync_tx_seen_total` на число элементов (tx или id).
8. Отсев по `shard_id` ≠ локальный `domain_hi` или по `!full_v1 || !same_shard` — дроп с метриками; для tx-кадров дополнительно `sync_tx_drop` с reason `profile_mismatch`.
9. `SyncTxBatch`: `ingest_sync_tx_batch` — если длина > `SYNC_TX_IN_CAP` (**64**), весь батч отбрасывается (`rate_limit`); иначе по одной tx: prune окна 30 s для `tx_seen_ms`; если **hex(tx_hash)** уже в `tx_seen_ms` — счётчик `duplicate` без записи в пул; иначе вставка в окно, проверка формы/цепочки/`pool.push`.
10. `SyncTxAnnounce` / `SyncTxReq`: **не обрабатываются** — лог «ignored», `sync_tx_drop` с reason **`unsupported`** (полные тела не запрашиваются и не анонсируются по смыслу протокола).

### Ретрансляция по сети

11. Нода **не** имеет отдельного «broadcast на всех»: ретрансляция возникает так — tx, принятая в мемпул, попадает в следующий `pool.snapshot` и может быть **снова запушена** по другим TCP-сессиям к другим `node_id`, пока для каждого получателя не сработает 30 s окно suppression.

Текстовая «диаграмма»:

```text
[Локальная tx или пришедший SyncTxBatch]
        → pool.push (если прошли проверки)
        → при следующем heartbeat-цикле с пиром P:
              send_sync_tx_batch читает pool.snapshot(≤256)
              фильтр: не слали P этот tx_id в последние 30s
              → write SyncTxBatch (≤ min(peer_cap, 32) tx)
На приёмнике:
        SyncTxBatch → dedup по tx_seen_ms (30s) → validate → pool.push
        SyncTxAnnounce / SyncTxReq → unsupported (только метрика+лог)
```

## 2) Классификация: push vs pull

- **Фактически:** **push-ориентированная схема** с полными телами транзакций: отправитель **сам инициирует** `SyncTxBatch` на регулярных событиях heartbeat-цикла, без ожидания запроса получателя.
- **Pull:** **нет**. Сообщения уровня «запроси недостающие id» (`SyncTxReq`/`SyncTxAnnounce` в wire) **не реализованы** на приёме — только заглушка с дропом `unsupported`.
- **Итог:** на транспорте объявлен **гибридный** набор типов (`Announce`/`Req`/`Batch`), но **живой путь данных — один: периодический push батчей**. Это **не** классический epidemic broadcast по одному событию «получил tx — немедленно разошли всем»; это «на каждом heartbeat с каждым пиром — до 32 новых для этого пира из снапшота мемпула».

**Соответствие абзацу RFC 15 §4.1 / §6.1:** нормативно заложены announce + request + batch и «bounded relay fanout». В коде Slice 2 реализован по сути **упрощённый batch-push**, без announce/request пайплайна и без отдельного нормативного fanout-лимита на реле (см. §4 и §5 ниже).

## 3) Где dedup и rate-limit; насколько это эффективно

| Механизм | Где | Эффект |
|----------|-----|--------|
| **Повтор к одному пиру** | `MempoolGspState.tx_sent_peer_ms` + `SYNC_TX_RECENT_MS` (30 s) в `send_sync_tx_batch` | Снижает повторную отправку **того же tx_id тому же node_id** в окне 30 s. |
| **Повтор при приёме** | `tx_seen_ms` (то же окно после prune) в `ingest_sync_tx_batch` | Снижает повторное принятие в пул **по id** в окне; после истечения окна та же tx теоретически может снова быть принята с сети (окно не бесконечное). |
| **Размер батча в** | `SYNC_TX_IN_CAP = 64` | Жёсткий потолок на **одно сообщение**; избыток → полный отказ батча. |
| **Размер батча out** | `min(peer.max_txs_per_msg, SYNC_TX_OUT_CAP=32)` | Потолок на исходящий батч на пира. |
| **Скан мемпула** | `SYNC_TX_SCAN_CAP = 256` | Ограничивает работу на снимке, не весь мемпул. |
| **Несовместимый пир / шард** | `route_sync_stub` | Отсекает трафик не того шарда и legacy / cross-shard для v1 tx path. |
| **Метрики** | `TransportState.snapshot`: `sync_tx_seen_total`, `sync_tx_accept_total`, `sync_tx_drop_total`, `sync_tx_drop_reason_total` | Видимость причин: `duplicate`, `invalid`, `rate_limit`, `profile_mismatch`, `unsupported`. |

**Эффективность:** dedup **пер-пир на отправке** и **глобальный по процессу на приёме (в пределах окна 30 s)** заметно режут шум, но **не ограничивают число рёбер графа**, по которым tx «растечётся» за счёт новых push с каждого узла к его соседям. Ограничение скорости **по байтам/сек на пира или на весь узел** в этом слое **не выставлено** — только косвенно через частоту heartbeat и размеры батчей.

## 4) Риск усиления трафика (качественно)

- **Хорошо:** нет немедленного «взрывного» fan-out на всех при одном событии; есть cap на размер батча и пер-пир suppression 30 s; приём дублей по id в окне дешевле полной валидации пула.
- **Плохо (интуиция worst-case):** в плотном same-shard кластере с **степенью D** и **P** установленными сессиями каждая новая tx может быть доставлена по многим путям: каждый узел, попавший в снапшот, пушит соседям, пока граф связности не покроет идёмностью «кто кому ещё не слал 30 s». В худшем случае оценка масштаба исходящих **батчей** от одной tx за интервал порядка **O(P × D / batch_cap)** в терминах ребёр heartbeat-циклов, плюс объём **полных тел** tx в JSON на каждом ребре (а не только id), что тяжелее, чем announce/request модель из RFC.
- **Дополнительно:** `max_msg_bytes` и прочие нормы RFC §8 в этом пути завязаны на общий wire; явного enforcement 4 MiB в просмотренном фрагменте slice 2 как отдельного guard для sync tx не разбиралось глубже — при очень крупных tx риск крупных кадров сохраняется.

## 5) Конкретные смягчения для Slice 3/4 **без изменения кода сейчас** (рекомендации владельцу / спринт-плану)

1. **Эксплуатация топологии:** ограничить **степень** same-shard peering (мало жирных full-mesh), использовать **иерархию или звезду** до стабилизации announce/pull в RFC.
2. **Параметры времени:** увеличить `heartbeat_interval_ms` на тестнете при наблюдаемом flood (меньше циклов push/sec); согласовать с SLA латентности sync.
3. **Профили пиров:** выставлять консервативный `max_txs_per_msg` в handshake для высокостепенных узлов (уже участвует в cap out).
4. **Наблюдаемость:** мониторить `sync_tx_drop_reason_total` и размер/частоту кадров; пороги алертов на рост `duplicate` + рост трафика без роста accept.
5. **Спецификация следующих срезов:** в Slice 3/4 (live chain / catch-up) **не смешивать** тяжёлый batch-tx push с той же частотой, что критический header/block трафик, без приоритизации каналов (контроль на уровне плана/приоритетов очередей — за рамками текущего кода).
6. **RFC / backlog:** зафиксировать явное отступление от §6.1 до внедрения `TxAnnounce`/`TxRequest` или переписать interim «минимальный профиль Slice 2» как сознательный профиль **batch-only push**, чтобы не ожидать от операторов pull-модели.

## 6) Прямой ответ владельцу (простым языком)

Сейчас нода **сама периодически пушит соседям батчи полных транзакций** (`SyncTxBatch`) в рамках обычного heartbeat-цикла TCP-сессии, а не ждёт, пока сосед **запросит** конкретные id. Сообщения «анонс» и «запрос» на wire есть, но **входящие такие кадры никак не обрабатываются** — это заглушка. Ретрансляция по сети получается **цепочкой пушей**: узел положил tx в мемпул, и на следующих обменах с другими пирами эта tx снова может уйти им в батче, пока для каждой пары узлов не отработает краткое окно «уже слали». Это **упрощает реализацию**, но в **плотной топологии** те же тела tx могут многократно гулять по рёбрам, поэтому **риск избыточного трафика средний и растёт со степенью связности**, пока не появится модель ближе к RFC (короткий announce, выборочный pull, явный fanout cap).

## 7) Вердикт ревью

**INFO** — поведение в коде однозначно **push-batch**, pull **не реализован**; это выглядит как сознательный узкий подсрез Slice 2, а не случайный дефект. **Критического несоответствия безопасности** в просмотренном транспортном пути не выявлено; **спекулятивные доработки** (RFC §6.1 полностью, fanout, байтовые лимиты) — предмет следующих срезов/RFC-примечаний, не блокер «понять топологию сейчас».
