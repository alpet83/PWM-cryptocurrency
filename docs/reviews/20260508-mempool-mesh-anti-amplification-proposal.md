# Proposal: анти-амплификация mempool gossip в смешанной mesh-топологии

**Дата:** 2026-05-08  
**Агент:** pwm-review (документ-предложение, без правок прод-кода)  
**Тикет:** `tasks/20260508-mempool-mesh-anti-amplification-proposal.json`  
**Контекст:** RFC 0015 Slice 2 даёт **push-baseline** (`SyncTxBatch`, дедуп, caps). Ниже — целевая политика для будущей сети: плотные внутрикластерные кварталы, разрежённые межкластерные рёбра, периферия за NAT.

---

## 1) Допущения и модель угроз

**Топология и поведение сети.**

- Узлы одного шарда образуют **граф с ядрами** (высокая степень внутри «кластера»: та же L2, низкая задержка; опционально локальная L2/broadcast-достижимость) и **разрежённую периферию** (NAT, асимметричная связность, длинные RTT).
- Между кластерами — **узкие мосты** (ограниченный fanout, конкурирующий uplink, возможные политики провайдера).
- Идентичность шарда и возможности пира известны после handshake (как в RFC 0015: same-shard, `full_v1`).

**Угрозы (не исчерпывающе).**

1. **Амплификация relay:** один исходный `tx` через наивный flood даёт \(O(\text{рёбра} \times \text{сообщения})\) трафика; в плотном кластере локальный «эхо-камин» множит объём без добавления охвата.
2. **Шторм дубликатов:** полные тела в каждом hop при плохой координации; даже при дедупе на приёме uplink уже перегружен.
3. **Eclipse / региональная изоляция:** если почти весь mempool-трафик идёт через узкий срез пиров, атакующий или сбой сегмента задерживает видимость tx для остальной сети; периферия без pull-компенсации долго остаётся отстающей.
4. **NAT-асимметрия:** исходящие соединения стабильнее входящих; push-only к периферии даёт односторонние очереди и head-of-line blocking; разные пути IPv4/IPv6 меняют видимость соседей.
5. **DoS на приёмнике:** частые мелкие батчи, уникальные невалидные тела (обход простого дедупа по хэшу до валидации), попытки раздуть таблицы дедупа/блумов памятью.

*Неизвестные без измерений:* реальный PD внутри L2-кластеров, доля symmetric NAT, профиль tx (размер батчей, частота).

## 2) Рекомендуемая архитектура gossip по зонам

Принцип: **внутри кластера — агрессивный охват с жёстким локальным потолком; между кластерами и на периферии — pull-уклон с малым адаптивным push.**

| Зона | Режим | Обоснование |
|------|--------|---------------|
| **Intra-cluster** (same shard, та же «локальная вселенная»: низкий RTT, много пиров) | **Push-first гибрид:** короткие batched push (`SyncTxBatch` или эквивалент) + редкий **локальный** pull (анти-энтропия при подозрении на разрыв). | Плотный граф: чистый pull даёт лишние round-trips; контролируемый push с низким fanout на соседа и коротким TTL-rebroadcast достаточен при локальном дедупе. |
| **Inter-cluster** (мосты между плотными областями, длинные рёбра) | **Hybrid, уклон в pull:** push только **сводки** (короткие id + опционально sketch), тела — по запросу; push-батчи малой ширины и с **экспоненциальным подавлением** повторов вдоль того же ребра. | Снижает байты на ребро; сдерживает амплификацию при симметрии «мостовых» узлов. |
| **Edge / NAT** (периферия, ограниченный inbound) | **Pull-heavy:** периферия **инициирует** периодический `SyncTxReq` / анти-энтропию к известным «хорошим» пирам (ядро кластера или явные bootstrap); входящий push — с **жёстким per-peer budget** и приоритетом уже-известных id. | Согласует с асимметрией NAT; избегает зависимости от стабильных inbound в море домашних узлов. |

**Связь с RFC 0015:** уже заложены announce/request/batch (§4.1); Slice 2 реализует batch-push baseline. Зональная политика — **надстройка политики отправки/частоты**, не обязательно новый wire-тип на первом шаге.

## 3) Конкретные рычаги управления

**Адаптивный fanout**

- Базовое значение \(k_\text{base}\) (например 4–8 соседей на тик для cluster-core).
- **Увеличение** fanout только при сигналах «отстаю»: рост очереди mempool vs median пиров, рост `pull` miss-rate, низкий `unique_tx_per_min` при высокой активности сети (прокси-метрика).
- **Снижение** при congestion: рост RTT, packet loss (если доступно), превышение локального egress budget, триггеры алертов ниже.

**Per-peer budgets**

- Лимиты: **байт/сек** и **сообщений/сек** на пира отдельно для mempool-класса.
- Приоритетная очередь: системные/собственные tx выше relay (опционально, продуктово).
- Отдельный **мягкий** бюджет на «новых» пиров первые N минут (репутация позже — вне RFC v1).

**Дедуп: окна, идентификаторы, sketch**

- **Скользящее окно по времени + по объёму** для `tx_id` на приёме (как в baseline); верхняя граница записей и **периодический prune** обязательны.
- **Локальный bloom / counting filter** (опционально) для «видел ли недавно» перед полным разбором батча — экономит CPU на заведомых повторах; **ложноположительные** допустимы только как путь к раннему отбрасыванию (не как единственный критерий принятия).
- Для **межкластерного** push: передавать **только id** (или id + короткий checksum) до подтверждённого интереса — снижает байты при совпадающем множестве.

**Правила подавления rebroadcast**

- **TTL по hop-или по времени:** после \(h\) релеев или \(T\) секунд с первого локального seen — не слать тот же id дальше по тому же классу рёбер (cluster vs bridge).
- **Удалённые подавители:** если пир уже прислал тот же id в окне W — не echo обратно.
- **Случайная задержка (jitter)** перед relay на bridge-edge: размывает синхронные штормы из L2-кластера.

**Anti-entropy раунды**

- Период \(T_\text{ae}\) (десятки секунд на периферии, реже в ядре): обмен **скомпактированным снимком** недавних id (sorted truncated set или MinHash/sketch) + дозапрос недостающих тел.
- После **реконнекта** или **скачка tip** — внеочередной короткий раунд pull к N выбранным пирам (staggered).

## 4) Ожидаемое поведение трафика (качественно и масштаб)

- **Intra-cluster:** трафик близок к \(O(\text{новых tx} \times k_\text{eff})\), где \(k_\text{eff} \ll \text{степень вершины}\) за счёт подавления; пиков при всплеске tx сглаживаются jitter и batched push. Локальный broadcast (если когда-либо включён) требует **отдельного cap** на уровне интерфейса, иначе риск L2-шторма.
- **Inter-cluster:** байты масштабируются с **числом мостовых рёбер × rate новых tx**, а не с произведением размеров кластеров; pull добавляет **редкие прикладные раунды** порядка «малый список id + точечные body», что даёт почти линейное по числу **дыр в знании**, а не по полному mempool.
- **Edge:** средняя нагрузка **ниже пиковой push-сети**, ценой задержки доставки на уровне \(T_\text{ae}\) и RTT pull; при здоровых ядрах периферия всё ещё **в пределах секунд** до первой видимости популярных tx.

## 5) Путь миграции от текущего Slice 2 push baseline

1. **Фаза A (без смены wire):** включить метрики зональности (эвристика «cluster-like» по RTT/ручной тег конфигурации); adaptive fanout + per-peer byte/msg rate; усилить rebroadcast suppression и jitter **только на исходящем relay**.
2. **Фаза B:** использовать **существующие** в контракте RFC кадры announce/request для **редкого pull** на периферии и мостах; batch-push остаётся для intra-cluster при сохранённом cap.
3. **Фаза C:** опциональный **sketch/id-only** межкластерный режим после мини-дописи RFC (см. §7).
4. На каждой фазе — канареечный профиль (доля узлов или явный флаг `gossip_profile=v1_dense|v1_sparse` в handshake extension *после* согласования в RFC).

## 6) Минимальный набор метрик и пороги алертов

**Метрики (counters/gauges/histograms).**

- `mempool_gossip_tx_relayed_total` / `mempool_gossip_tx_received_total` (по зоне: intra / bridge / edge — лейбл после внедрения классификации).
- `mempool_gossip_bytes_out_per_peer_bucket` (гистограмма или rate по перцентилям).
- `mempool_gossip_dedup_hit_total` vs `…_miss_total`.
- `mempool_gossip_pull_round_duration_ms`, `mempool_gossip_pull_ids_fetched` (когда pull включён).
- Очередь: глубина **pending outbound** mempool-кадров на транспорт.

**Алерты (начальные ориентиры, под настройку под тестнет).**

- **Egress p95** на узел mempool-класса > **X МБит/с** в течение **5 мин** при стабильном `tx_inject_rate` — investigate fanout/suppression.
- **Dedup miss ratio** резко падает при росте входящих сообщений — возможный шторм дубликатов или атака.
- **Pull fail rate** или таймауты **> Y%** за окно — периферия/мосты теряют анти-энтропию.
- **Рост `invalid` / drop по rate_limit** пер пира **> порога** — пер-пировый бан или снижение приоритета (операционально).

Конкретные числа X, Y фиксировать после первой недели замеров тестнета; в документе намеренно оставлены как плейсхолдеры.

## 7) Что внести в RFC сейчас vs позже

**Сейчас (короткая нормативная надстройка или «Implementation guidance» к RFC 0015):**

- Явное разделение **ролей зон** (операционно): dense relay vs bridge vs edge; рекомендуемые **default caps** по зонам.
- Требование **bounded relay** уже есть — дописать, что реализации **должны** применять **per-peer и глобальные** бюджиты mempool-класса и **подавление повторной отправки** по id+ребро/окну.
- Указать, что **announce/request** не optional на длинной дистанции для совместимости с NAT-heavy профилем (даже если Slice 2 их ещё не реализует).

**Позже (отдельная ревизия RFC или RFC «sync v1.1»):**

- Нормативный формат **anti-entropy snapshot** (размер поля, предел id, частота).
- Опциональный режим **id-only / sketch-first** на wire для межкластерных мостов.
- Handshake-поле `gossip_profile` или расширение `sync_profile` с версионированием.
- Взаимодействие с **репутацией** пиров и кросс-протокольными лимитами (вне текущего scope v1).

---

## 8) Краткая рекомендация владельцу (практический профиль по умолчанию)

Держать **Slice 2 batch-push в плотных кластерах** с умеренным \(k\) и обязательным suppression+jitter; **не расширять blind fanout** при росте числа пиров в L2. Для любых узлов с нестабильным inbound или заметно большим RTT к большинству пиров — **включать периодический pull** к 2–3 доверенным по конфигурации «якорным» пирам как первый анти-NAT шаг без тяжёлой крипты. Все новые рычаги сначала за **фичефлагами и метриками**, с канареечным rollout; числовые алерты калибровать на тестнете до прод-репликации. Следующий нормативный шаг — **короткое обновление RFC 0015**, чтобы edge-pull и зональные лимиты не оставались «тихой» фактической вилкой между реализациями.
