## 2. Requirements fit

**Strengths**

- **Burn v2 `purpose` path:** CLI optionally calls `SignedTx::set_burn_purpose_signed` after `sign_body`; omission keeps the existing built-in `"default"` from `sign_body`, with a clear stderr note — consistent with core’s `normalize_burn_purpose` / length gate.
- **ClaimTx surface:** CLI wires `TxBody::Claim` with `ClaimMode` parsed from `free|paid` and posts like other signed txs.
- **Reject UX:** Both CLI and TUI attempt RFC-like one-line hints (`code`, `response_class`, `phase`, `tx_kind`, optional `trace_id`, `message`) for JSON error bodies.
- **TUI F5:** Replaces the previous “burn→CLI” stub with an actual modal matching the sprint brief; integrates with existing RPC worker patterns.
- **Tester guide / CHANGELOG** describe `tx-claim`, `--purpose`, F5 modal, and RFC 0014 hints — aligns with integration expectations.

**Gaps / mismatches**

- **RFC 0014 completeness (client-facing):** The minimal reject shape for `tx_kind=claim` **requires `claim_mode` (`explicit|auto`)**. The summarizer ignores this field entirely, so operators lose mandatory context that RFC 0014 calls out for claim failures (especially auto-claim rejects). Integrators relying on CLI/TUI copy will not see it.
- **E-3 “deprecation guardrails” (handoff §3):** The diff strengthens v2-first behavior (default purpose, docs) but does not add explicit **client-visible** deprecation or version messaging beyond existing serialization (e.g. no dedicated warning path for producers still targeting legacy wire). If guardrails were meant as “docs + default v2 payloads only”, coverage is partial; if they required explicit deprecation signals, this slice under-delivers.
- **`tx_claim` client validation:** Mode/fee invariants are enforced server-side via `validate_tx_shape`; acceptable, but UX will hit the network before obvious `free`+`fee>0` mistakes — optional preflight locally (not strictly required by RFC).

## 3. Style and module shape

- **`reject_wire.rs`:** Short module `//!`, single public function — fits micro-modularity; English comments consistent with repo rules for touched files.
- **Identifiers:** No systemic violation of the ≤5 underscore-segment naming rule spotted in newly introduced symbols (e.g. `summarize_pwmd_tx_reject_json` — five segments — at the stated ceiling; acceptable unless project tightens policy).
- **`tui_loop.rs`:** Large synchronous growth for modal rendering is expected for Ratatui; factored helpers (`burn_form`, `submit_burn_mark`) reduce the worst layering issues. Minor nit: modal rendering inlined as a large function — consistent with adjacent `render_send_modal` pattern, not a regression.
- **`parse_claim_mode_cli` error message** references wrong flag name (**see Severity**).

---

## 4. Safety

- **Trust boundaries:** Parsing untrusted HTTP bodies with `serde_json` and echoing `error.message` into status lines — acceptable for a CLI/TUI debugger surface; messages are not bounded in length (minor annoyance / oversized terminal noise, not a consensus risk).
- **Panics:** No new naked `unwrap` in the reviewed hot RPC paths beyond existing `response.text().unwrap_or_default()` pattern already used elsewhere in `tx_submit`.
- **Magic string `"default"` for purpose:** Matches `SignedTx::sign_body` baseline in `pwm-core`; TUI defaults align. Users cannot distinguish “omit purpose” from literal dedication `"default"` without reading code — acceptable dev default, document clearly (tester guide partially does).
