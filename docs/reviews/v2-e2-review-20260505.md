## 1) Scope recap

E-2 по handoff: стабильный reject-wire (`ok=false`, `phase`, `tx_kind`, `response_class`, вложенный `error` с `code` / `message` / `trace_id`), единый mapping `TxError` → стабильные `E_*` и `response_class` для claim/burn/import в покрытых путях, симметрия вердикта preflight vs apply на одном snapshot для ключевых негативов. Зона **не** включает полную CLI/TUI адаптацию (E-3).

---

## 2) Requirements fit

**Выполнено относительно handoff и фокуса слайса**

- В `tx_reject_json` собирается согласованный JSON: перечисленные поля присутствуют; `trace_id` заполняется детерминированно от хэша tx (приемлемо как коррелятор; не обязан совпадать с UUID из примеров RFC).
- Централизованный `tx_err_wire` задаёт пары (`error.code`, `response_class`) для согласованных вариантов `TxError`; для явных claim/burn/import кейсов в тестах нет подмены на произвольный internal-текст без структуры — ответ остаётся JSON с классом.
- `handlers_tx`: `validate_tx_shape` и tip-precheck (`precheck_apply_with_ctx`) отклоняются через `tx_reject_json` с фазой `preflight`, что согласуется с тем, что клиент видит при раннем отказе до постановки в mempool.
- Import fee ниже минимума: `enforce_import_provenance_prefilter` использует тот же `tx_reject_json` с `TxError::ImportFeeTooLow` — вровень с ожиданиями RFC 0014 по коду и классу.

**Зазоры относительно RFC 0014 (и частично полной матрицы Slice D)**

- **RFC 0014, minimal reject JSON:** для `tx_kind=claim` нормативно указано обязательное поле `claim_mode` (`explicit|auto`). В текущем `tx_reject_json` оно **не эмитится**; тесты parity его не проверяют. Slice D в примерах §5 этого поля не перечисляет — но при конфликте приоритет у явного требования RFC 0014 в составленном пакете V2-1. Рекомендация: аддитивно расширить сериализацию и assert’ы для explicit-claim (и отдельно проработать auto-claim surface, когда он появится в API).
- **Полная таблица Slice D / RFC 0013:** в `pwm_core::TxError` на момент ревью нет отдельных вариантов для `E_FEE_POLICY_REJECT`, `E_BURN_UNITS_INVALID`, `E_ANCHOR_STATE_UNAVAILABLE`, `E_REORG_STATE_MISMATCH` и т.д.; они физически не могут быть отражены 1:1 в wire до появления семантики в core/API. Fallback `_ => (E_SCHEMA_INVALID, VALIDATION_ERROR)` остаётся точкой **потенциального** «сглаживания» специфичных сбоев, если они когда-либо начнут приходить как другие варианты `TxError` — сейчас это скорее технический долг, чем регрессия E-2.
- **Фаза `mempool` в JSON:** HTTP-ответы при отказах на рассмотренных путях используют `preflight` (до приёма в pool). Явных HTTP-reject’ов с `phase: mempool` в этом срезе нет; полное покрытие mempool-phase reject-wire (если потребуется наружу) не демонстрируется — в рамках E-2 это допустимо, если контракт интеграторов = ранний preflight.

---

## 4) Safety

- Новый wire не добавляет panics в горячих путях; JSON строится из известных строк и хэша tx.
- Границы доверия: reject JSON не раскрывает секретов; `trace_id` привязан к id транзакции (учитывать конфиденциальность tx-id в публичных логах — общий продуктовый вопрос, не специфика E-2).
- Пути submit/mempool: для транзакций, уходящих в mempool после успешного precheck, по-прежнему возможен drift state до seal — это ожидаемо по RFC; регрессий в порядке блокировок/локов по диффу не видно.

---

## 5) Tests

- `assert_preflight_apply_parity` проверяет совпадение `error.code`, `response_class`, `tx_kind`, `phase` (preflight vs синтетический apply), непустой и совпадающий `trace_id` — хороший интеграционный шаблон.
- Покрыты три представительных класса: burn schema (`E_BURN_SCHEMA_INVALID` / `VALIDATION_ERROR`), free-claim day limit (`E_FREE_CLAIM_DAILY_LIMIT` / `POLICY_REJECT`), import fee (`E_IMPORT_FEE_TOO_LOW` / `POLICY_REJECT`). Этого достаточно как **дымового** гейта E-2, но **не** как полной матрицы RFC 0013 §Error Semantics.
- Отдельно стоит добавить тесты на обязательные поля RFC 0014 (в первую очередь `claim_mode` для claim) и по мере расширения `TxError` — на отсутствие падения в generic fallback для новых стабильных кодов.
