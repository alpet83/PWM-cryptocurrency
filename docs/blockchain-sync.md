# Same-shard blockchain sync (pwmd): логика, состояния и приёмка

Нормативное описание для операторов и разработчиков: как **одна нода** догоняет **совместимый peer** в том же шарде, какие есть **режимы**, что хранится в памяти на peer-сессию, и как отличить **здоровую «тишину»** после догона от **бесконечного catch-up**.

Кодовая ось: `crates/pwmd/src/transport/peer_session/sync_live.rs`, состояние: `SyncPeerState` в `crates/pwmd/src/transport/handshake_state.rs`. Спецификация: [`docs/rfc/15-same-shard-sync-v1.md`](rfc/15-same-shard-sync-v1.md). RCA по зонам режимов: [`docs/debug/20260513-sync-mode-zones-rca.md`](debug/20260513-sync-mode-zones-rca.md).

---

## Термины

| Термин | Смысл |
|--------|--------|
| **lag** | Разрыв до известного tip peer: `head_h - local_h` (где `head_h` — высота tip с peer, `local_h` — локальный `chain.tip_h()` на момент обработки события). |
| **Peer tip** | Объявлённый peer’ом конец цепочки (`head_h`, hash). Обновляется по wire (в т.ч. через `on_tip`). |
| **Live short-tail** | `lag > 0`, но политика **не** переводит сессию в epoch catch-up: догон через очередь **hdr → blk** (порциями). |
| **Epoch CUP** | Catch-up по эпохам: активная фаза с `cup_active == true`, отдельные сообщения chunk/done, **живая** поставка hdr/blk из того же peer-соединения блокируется до очистки CUP. |
| **live_stall** | Счётчик «залипаний» live-пайплайна (рост при плохих hdr, несоответствии высоты, сбоях apply, NACK, части ошибок CUP). Сбрасывается при успешном live-apply, успешном chunk/done CUP. Без «затухания» со временем. |
| **Консольный прогресс** | Строки с target `pwmd::sync` вида `Sync progress …% rem=… goal=…` — оценка догона до `goal` (max из peer tip и `persisted_h` для отображения дискового хвоста). Не FSM-состояние; см. раздел «Прогресс и тишина». |

## Ключевые константы (реализация v1)

Имена из `sync_live.rs` (значения могут меняться — сверяйте с исходником):

- **`SYNC_CUP_LAG_MIN`** (256): глубокий отставание — **всегда** кандидат на epoch CUP при прочих условиях.
- **`SYNC_CUP_SHORT_TAIL_MAX`** (32): **короткий хвост** по `tip_lag` — приоритетный **live** пайплайн hdr/blk (в т.ч. цепочка `ask_hdr` после неполного батча и доп. раунд заголовков после успешного `apply`, пока очереди blk пусты). **Новый** epoch CUP из `on_tip` здесь не включается «из сталла»; глубокий откат — только при **`lag >= SYNC_CUP_LAG_MIN`** или при повторе уже начатого CUP (**`cup_on`**).
- **`SYNC_CUP_WIN_CAP`**: ограничение окна одного CUP-запроса по высотам (связано с `cup_req_range` и границами эпохи).
- **`SYNC_HDR_REQ_CAP`**, **`SYNC_BLK_REQ_CAP`**, **`SYNC_INF_CAP`**: лимиты параллельных запросов hdr/blk и «in-flight».
- **`SYNC_PROG_MIN_MS`**: минимальный интервал между строками прогресса при **незавершённом** догоне вне «тихого хвоста».
- **`SYNC_PROG_LIVE_TAIL_MS`** (реализация): при здоровом **live short-tail** (`tail_quiet`) интервал между **кандидатами** строки `Sync progress` увеличен. Для **`SealRole::Standby`** в зоне **`tail_quiet`** строка на вывод **не эмитится** (только **`sync_prog_tick`** обновляет внутреннее состояние); вне этой зоны Standby снова печатает прогресс при догоне.
- **`STANDBY_SYNC_FLUSH_BLK_IV`** (`lifecycle.rs`): периодический сброс снапшота на диск для **`SealRole::Standby`** на высоте **1** и далее каждые **N** блоков; в лог — строка **`standby sync checkpoint`** с актуальным `flush_iv`.

## Ведомые узлы (`SealRole::Standby`)

Для **standby / attester** в CY-кворуме:

- Строки **`Sync progress`** (**`pwmd::sync`**) **подавляются только в коротком live-хвосте** — тот же смысл, что функция **`sync_prog_tail_quiet`** в коде: нет активного **epoch CUP**, известен положительный peer tip, **`tip_lag < SYNC_CUP_SHORT_TAIL_MAX`** (независимо от **`rem`**: несколько блоков до tip всё ещё «короткий хвост» для тишины Standby). В этом режиме достаточно peer-log и периодических **`standby sync checkpoint`**.
- При **докачке** (большой **`rem`**, большой **`lag`**, **`cup_active`**) строки **`Sync progress`** снова печатаются, чтобы было видно прогресс догона.
- Операторский сигнал о сохранении на диск: **`standby sync checkpoint range=… flush_iv=…`** с интервалом **`STANDBY_SYNC_FLUSH_BLK_IV`** (см. исходник; на момент описания — **100** блоков).

## Режимы и условия перехода

### 1. Idle / tip-aligned

**Идея:** локальный tip **согласован** с peer: нет догона (`lag == 0` после проверок hash/divergence) или peer не впереди.

**Выход:** следующее объявление tip с `head_h > local_h` снова включает догон.

Персистируемого бита «sync off» нет — «синхронизация остановилась» в операторском смысле означает **устойчивое** отсутствие отставания и отсутствие бурного catch-up в логах (см. приёмку).

### 2. Live pipeline (short-tail и не только)

**Вход:** `on_tip` видит `lag > 0`, и epoch CUP **не** стартовал в этом заходе (`maybe_start_cup` не взял управление на себя).

**Поведение:** запросы заголовков с `local_h + 1`, очереди `pend_blk` / `wait_blk`, apply блоков, сброс `live_stall` на успехе. Пока до peer tip остаётся мало блоков (`tip_lag < 32`), после успешного apply и пустых очередей blk может сразу уйти следующий **`ask_hdr`** (не ждать следующий `on_tip`); в **`on_hdr_batch`** при неполном батче заголовков следующий диапазон всё равно запрашивается, если **`next_h <= tip_h`**.

**Политика CUP-запроса** (упрощённо, из `on_tip`):

- `cup_req = cup_on || lag >= SYNC_CUP_LAG_MIN`
- Здесь **`cup_on`**: peer уже в mid-catch-up по таймеру повтора (`cup_active && now >= cup_next_ms`) — ветка **всегда** допускает вызов `maybe_start_cup` (ранние выходы внутри).

**Короткий хвост:** при `lag < 256` новый epoch CUP **не** стартует только из-за роста **`live_stall`**; догон остаётся на приоритетном live-пути. Глубокая яма **`lag >= SYNC_CUP_LAG_MIN` (256)** — кандидат на CUP; мелкий разрыв и стагнация лечатся живым hdr/blk, а не фоновым CUP.

### 3. Демоция CUP в коротком хвосте

**`try_demote_cup_tail`:** если **`cup_active`** и **`tip_lag < SYNC_CUP_SHORT_TAIL_MAX`**, CUP **принудительно сбрасывается** (`cup_clear`), счётчики try/timer обнуляются, метрика **`TransportSnapshot::sync_cup_demote_tail`** (в сериализованном снапшоте JSON ключ по-прежнему `sync_cup_demote_short_tail_total`, см. `serde(rename)` в `metrics.rs`).

Это лечит «залипший» CUP, когда peer tip уже близко, но не заменяет общую диагностику: прогресс в консоли может всё ещё колебаться из-за live-пайплайна или диска.

### 4. Epoch CUP (`cup_active`)

**Вход:** успешный сценарий `send_cup_req` / продолжение catch-up внутри эпохи.

**Пока активен:** `on_hdr_batch` и `on_blk_batch` для **live** часто **ранний return** — hdr/blk от peer не обрабатываются как в обычном live, пока не очищен CUP.

**Выход:** `cup_clear` на успешном done, ошибках, nack, части mismatch; см. RCA-диаграмму.

## Прогресс (`pwmd::sync`) и «тишина»

Функции **`sync_prog_snap` / `sync_prog_tick` / `maybe_log_sync_prog`**:

- **`goal`:** максимум из peer tip и `persisted_h` (чтобы отразить отставание диска standby).
- Троттлинг: время **`SYNC_PROG_MIN_MS`**, шаг процента, особые случаи `lag_resume` и **дедуп 100%** для того же `goal` (`sync_pct100_goal`), чтобы не спамить повторными «100%» при одном и том же выравнивании.

**Важно:** частые `Sync progress 99%/100%` у **активного** sealer **не доказывают** сами по себе, что транспорт застрял в CUP — это может быть **live short-tail** на 1–2 блока, смена `goal` при росте tip proposer, или догон памяти vs диска. У **Standby** в **коротком хвосте** эти строки **намеренно скрыты**; при отставании на десятки/сотни блоков прогресс снова виден.

### Операторский критерий «синхронизация остановилась»

Важно различать:

- **Догон закончился и узел в live:** proposer продолжает печатать блоки; attester в том же шарде **обязан** на каждый новый tip выполнять **live short-tail** (`lag` часто 1). Это **не** «бесконечный catch-up» и **не** залипший CUP. У **активного** узла в консоли мог бы отображаться `Sync progress`; у **Standby** — только peer-log и периодические **`standby sync checkpoint`**. Подтверждение: в peer-log есть `on_tip live_hdr` → `apply ok`, нет `cup_started` / `catchup` / ретраев CUP. См. [`docs/debug/20260514-blockchain-sync-quiet-rca.md`](debug/20260514-blockchain-sync-quiet-rca.md).

- **Реальное «не затихло» (патология):** растущий транспортный хвост (`rem` не сходится к нулю), `cup_on=true` при коротком хвосте без прогресса, бури NACK/`catchup fail`, диск **навсегда** сильно ниже tip при выключенном нормальном checkpoint-ритме.

Одновременно для **здоровой** приёмки:

1. **Высота:** attester **догоняет** proposer: по peer-log `lag` стабильно мал (1–несколько блоков), `apply ok` регулярны.
2. **Режим:** нет застревания в CUP там, где ожидается live (см. RCA по шаблонам строк).
3. **Опционально — UX:** снижение шума `Sync progress` при здоровом live-following — зона продуктовой политики логирования (`pwm-coding`), а не обязательный признак «sync off».

**`-RequireQuietTail`:** для **Standby** ожидается **`maxPct == 0`** при успешном `snapshot ready`; ветка «тишины» смока это учитывает. Для **Active** — эвристика по числу строк `Sync progress` в хвосте; на живой сети с постоянным sealing возможны ложные схватки — сверять peer-log. Скрипт не должен содержать `>=` в двойных кавычках под Windows PowerShell 5.x (разбор как перенаправление потока).

**Базовый `SMOKE_PASS`:** attester дошёл до **`snapshot startup load ok`** / **`ready (snapshot loaded)`**, proposer — **`pwmd listening on http://`**; либо (legacy) **`Sync progress` ≥ 5%**, если ещё встречается старая сборка.
