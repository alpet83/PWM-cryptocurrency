# Архитектурная записка: дистрибуция хвостовых блоков (pull) и необходимость push — MVP v2

**Дата:** 2026-05-22  
**Тип:** прагматичная архитектурная memo-записка (прослеживаемость к операторским документам и коду без ревью диффа).  
**Нормативные опоры:** [docs/rfc/15-same-shard-sync-v1.md](../rfc/15-same-shard-sync-v1.md), [docs/blockchain-sync.md](../blockchain-sync.md), операторские детали [docs/runbook-same-shard-sync-v1.md](../runbook-same-shard-sync-v1.md), путь реализации [crates/pwmd/src/transport/peer_session/sync_live.rs](../../crates/pwmd/src/transport/peer_session/sync_live.rs).

## 1. Контекст и scope вопроса

**Вопрос владельца (три нити):**

1. Как **сейчас** в сценарии **same-shard follower** (attester / standby позади активного пропозера или другого узла с цепью) организована доставка **«хвостовых»** блоков: цепочка tip → заголовки → тела блоков; fallback epoch catch-up (CUP) при большом lag; где проходит граница между RAM tail и диском.
2. **Плюсы и минусы** текущей **request/pull** модели для латентности, нагрузки на пропозера, устойчивости к «неохотной» отдаче, лишним round-trip, взаимодействия с mesh и (позже) с cluster-attestation трафиком.
3. Стоит ли **в текущем контексте MVP v2** добавлять **proactive push** от ноды, выполняющей **seal** (broadcast уведомления + блок или компактный заголовок), чтобы **уменьшить суммарный трафик** — с учётом scope `mvp_v2.md`, семантической версии wire (`PeerWireMsg` / RFC 0015 §5–6), топологии **мало peers** против **CY lab**, рисков amplification / дубликатов / нагрузки на standby.

**Scope ограничен:** синхронизация цепи **внутри одного шарда** по контракту RFC 0015; межшард, репутации и полный finalized-протокол вне задачи.

## 2. Текущая модель («как есть» в реализации и для оператора)

### 2.1 Нормативная карта (RFC 0015 §6.2 и §6.3)

RFC фиксирует таксономию **live**:

- **`TipAnnounce`** — объявление `head_height` / `head_hash` и синхробаундаря `finalized_height` (и у реализации — хеш финализируемого уровня, когда доступен).
- **`HeadersRequest` / `HeadersBatch`** — выравнивание по высотам пачками.
- **`BlocksRequest` / `BlocksBatch`** — догрузка тел по наборам идентификаторов.
- При глубоком отставании — **epoch catch-up**: `CatchupRequest` → `CatchupChunk` → `CatchupDone` (§6.3).

Раздел §6.4 нормативно требует сопоставлять ответы с активным локальным **request context** и отбрасывать stale/late без побочных эффектов на fork-choice.

### 2.2 Конкретный пайплайн в `pwmd` (`sync_live.rs`)

Живое следование строится вокруг **объявления tip** и последующих **explicit pull** сообщений от follower к выбранному peer.

**Отправитель цепочки** периодически публикует tip через `send_sync_tip` (`PeerWireMsg::SyncTipAnnounce`): поднимаются `head_height`, `head_hash`, `finalized_height` как «penultimate anchor» аппроксимации локального settled prefix (`head_h.saturating_sub(1)`).

**Приёмная сторона** — обработчик `on_tip`:

- Обновляется состояние сессии: `tip_h`, `tip_hash`, считается `lag = head_h - local_h`; эмиссия консольного **`Sync progress`** (target `pwmd::sync`) с `goal`, учитывающим и диск standby (`persisted_h`) — см. [docs/blockchain-sync.md §«Прогресс»](../blockchain-sync.md).
- Если **lag равна нулю** и хеш совпадает — «idle / aligned» после проверок расхождения финализируемых якорей.
- Если **lag положительна** — сначала решается **epoch CUP** vs **live hdr/blk**:

  - **Запрос CUP** (`maybe_start_cup` → `PeerWireMsg::SyncCatchupReq`) выполняется, если либо peer уже находится в **mid-catch-up** с триггером повтора по таймеру (`cup_on`), либо **глубина отставания** `lag >= SYNC_CUP_LAG_MIN` (в коде **256** блоков от локального tip до объявленного peer tip).

  - В **«коротком хвосте»** `lag < 256`: отдельно **новый CUP только из счётчика `live_stall` не включают** — догон остаётся на live-пути; это согласуется с описанием в [docs/blockchain-sync.md §2–3](../blockchain-sync.md).

- Если CUP не взял управление или не стартовал, follower шлёт **первый live** **`ask_hdr`** с `from_height = local_h + 1` и ограничением `req_lim`, согласованным с профилем peer и внутренними потолками (`SYNC_HDR_REQ_CAP`, `SYNC_INF_CAP`).

**Ответ заголовков** — `on_hdr_batch`:

- Пока **активен CUP**, live `on_hdr_batch` **ранним выходом игнорируется** (`cup_active` в `HandshakeState`): отдельный поток блоков только через chunks CUP (`on_cup_chunk` / done).
- В live-режиме проверяется непрерывность цепи заголовков к локальному tip, заполняется очередь **`pend_blk`**, затем вызывается **`ask_blk`**, которая переносит ожидание в **`wait_blk`** и шлёт `SyncBlocksReq` с парами **`block_hashes` + `block_heights`** для эффективной подстановки ниже RAM tail.

**Приём блоков** — `on_blk_batch`: сверка с ожидаемым `wait_blk`, `apply_blk_batch` (включая standby-periodic checkpoint к диску — см. строки **`standby sync checkpoint`** при `SealRole::Standby`).

**Избыток round-trip в коротком хвосте снижают**:

- После успешного apply и при **малом `tip_lag`** (`lag < SYNC_CUP_TAIL_MAX`, в коде **32**) функция **`live_tail_pull_hdr`** может **немедленно** инициировать следующий `ask_hdr`, **не дожидаясь следующего `on_tip`**, если очереди блоков простаивают (`pend_blk`, `wait_blk` пусты, нет in-flight заголовков). Это важное поведение «реактивное, но всё же pull»: задержку на новый блок не нужно исключительно вешать на частоту tip-сообщений.

**Серверная сторона (отдача):**

- `on_hdr_req` / `on_blk_req`: сначала последовательные заголовки/блоки из **in-memory deque** цепочки; при разрыве с запрошенным `from_height` — fallback на **epoch JSONL** через `load_consecutive_blocks_from_epochs` / `load_block_at_height`; это операционно описано в RFC 0015 §14 (informative) и в [docs/blockchain-sync.md §«Ключевые константы»](../blockchain-sync.md). Опциональные **`block_heights`** на запросе блоков сохраняют обратную совместимость (§14 Compatibility).

### 2.3 RAM tail vs disk (операторский смысл)

- Цепочка держит **ограниченный deque последних блоков в RAM** (`TAIL_BLOCK_CAP` в `pwm_core`, в документе указано как **1000** — сверять с источником при изменении).
- **Персистируемое** дерево высот ниже этого хвоста обслуживается через epoch-файлы; оператор наблюдает рассогласование **mem tip vs persisted_h** через `goal` строки **`Sync progress`** и периодические **`standby sync checkpoint`** для standby follower.

Итого для оператора (same-shard follower): типичное здоровье после догона — **`on_tip`** → один или несколько циклов **`live_hdr`** / **`apply ok`** с малым `lag`; глубокий старт или редкий случай большого провала высот закрывается **CUP** до возврата в live по метрикам `sync_cup_*` ([runbook §3](../runbook-same-shard-sync-v1.md)).

## 3. Плюсы и минусы модели pull (request) в текущей реализации

### Плюсы

| Аспект | Почему это плюс в текущей реализации |
|--------|--------------------------------------|
| **Контроль нагрузки на источник** | Сервер отвечает на явные запросы; легче сопоставить с caps RFC 0015 §8 и локальными `SYNC_*_CAP`/`SYNC_INF_CAP`. Follower сам регулирует параллелизм in-flight hdr/blk. |
| **Дедуп и stale safety** | §6.4 и код ветвления `wait_hdr_from`/`wait_blk` связывают ответ с ожиданием; при текущем дизайне «опоздавшие» пуш-пакеты фактически не создавались бы как отдельный параллельный контур без запросного контекста. |
| **Прозрачная диагностика** | Счётчики `sync_hdr_req_total`, `sync_blk_req_total`, `sync_apply_*` дают понятную картину «кто попросил / что вернулось» без разделения unsolicited vs requested. |
| **Ортогональность к mempool §13** | RFC 0015 §13 нормативно касается **mempool** storm guard; цепочные sync сообщения там **explicitly unchanged** — pull-модель chain sync меньше риска пересечься с push-suppression mempool путём. |
| **Слабее «flooding amplification» по mesh** | Каждый follower запрашивает только свой диапазон; нет встроенного широкого fan-out блоков «ко всем соседям сразу» на каждый новый sealed блок. |

### Минусы

| Аспект | Ограничение / затраты |
|--------|-------------------------|
| **Латентность и round-trip depth** | Минимум **две фазы сообщений** после tip: Headers → Blocks (плюс сами анонсы tip). При неполных батчах `on_hdr_batch` уже и так цепляет следующий диапазон при `next_h <= tip_h`, но полный блок всё равно приходит только после **`SyncBlocksReq`**. Push теоретически убрал бы один или оба запросов на «счастливом» пути. |
| **Нагрузка на sealing / reference peer при N followers** | Каждый follower инициирует свои req; при топологии fan-in на один активный узел суммарные ответные байты масштабируются как **O(N)** на блок (с политическими ограничениями batch размера push не устранил бы полностью, но изменил бы форму bursts). |
| **«Неохотная отдача» peer** | Pull не гарантирует качество сервиса: peer может медленить ответы, NACK-ить диапазоны, иметь узкий uplink — follower увидит рост **`live_stall`**, возможные переходы CUP при большом lag. Push не решает доверие, но изменит чувствительность к каждому round-trip. |
| **Взаимодействие с будущим cluster attestation трафиком (V2-9)** | Дополнительные служебные каналы (RFC 16) на том же узле добавят конкуренцию за bandwidth/CPU кодированию JSON без изменения того, что **sync и attest — разные trust boundaries**. Комбинировать push блоков без rate policy рискованнее на shared TCP session, если multiplexing не продуман. |

## 4. Опции push (кратко) и сравнение

| Вариант | Идея | Потенциальный выигрыш | Основная цена / риск |
|---------|------|------------------------|---------------------|
| **A. Push только compact header после seal** | Sealer после локального **`apply`** рассылает tiny frame (hash, height, parent) помимо уже существующего tip-пульса | Меньше ожидания «осознания» нового блока удалёнными узлами; но pull всё равно нужен для body | Новый тип сообщения или расширение `SyncTipAnnounce`; дубль семантики с tip; нужны лимиты |
| **B. Push полного блока подписчикам** | Одно сообщение заменяет hdr+blk round-trip для подписанта | Наименьший RTT для «теплого хвоста» | Серьёзный **fan-out** и возможное **Nx duplication** если несколько связей; нужен explicit subscription / segment policy; semver wire |
| **C. Hybrid: push-block только в cluster segment ID** | Как mempool §13 «segment», но для блоков — выход за рамки текущего frozen RFC §13 («chain sync unchanged») | Трафик экономится в CY lab топологии | Нужна **RFC revision** или отдельный профиль версии (`sync_wire_version` bump §5.4), операторские правила классификации peer_segment |
| **D. Отложено: использовать out-of-band (OOB) lab bus** | В lab не трогать wire, использовать локальный файл/буфер (как упомянутые в документации к RFC 16 OOB паттернам) для измерений | Нулевое влияние на semver | Не является продуктовым p2p решением |

**Сводка:** без изменений RFC и политики сегментов любой заметный push блоков конфликтует с аккуратным «cluster mesh» моделированием и требует **новые anti-amplification правила**, иначе «один блок × K соединений» быстро становится дороже, чем сегментированный pull с batch.

## 5. Рекомендация для MVP v2

**Ответ для текущего scope MVP v2: «нет как обязательного инкремента; отложить до измерений / V2-9»** при следующих условиях осмысленного revisit:

### 5.1 Согласование с `mvp_v2.md`

- **Sprint V2-8 (same-shard sync v1)** в плане помечен **завершённым по слайсам 0–5**; **автоматическая приёмка wave-pack** сознательно перенесена из-за pivot к single proposer + attestation (**V2-9**, RFC 16).
- Основная ближайшая продуктово-консенсная работа — **кластер и ведомые вне кластера**, где sync v1 уже «база доставки», а корректность ролей seal/attest важнее микрополировки транспортного паттерна.
- Экономический слой v2 (PWM/marks/emission клиентский путь) **не опирается** на блок как push-vs-pull.

**Вывод:** встраивать новый proactive block push **во frozen wire контракт** ради абстрактного «меньше байт» **не является** лучшей ставкой ресурсов **до стабилизации V2-9** и сбора профилей.

### 5.2 Стоимость wire / semver

- RFC 0015 §5.4: **backward-compatible добавления допустимы optional**; **ломающее** изменение потребует **bump `sync_wire_version`** и отдельного compliance gate между поколениями пиров — это целый слайс (кодинг, регрессия, документация), больший чем экономия RTT при **2–3 peer** топологии **CY lab / devnet quorum**.

### 5.3 Малый fan-out vs практический эффект

- На прогретом хвосте follower часто живёт при **lag около одного блока**. Текущий код уже делает **`live_tail_pull_hdr`** между tip-тиками, снижая «залипание» только на анонсе.
- Серьёзный выигрыш push масштаба **общего транспортного счёта байт по сети** проявился бы при **десятках–сотнях** одновременных pull к одному источнику продакшена; в MVP v2 target topologies этого пока явно не фиксируют.

### 5.4 Риски, из-за которых push «по умолчанию» невыгоден сейчас

- **Amplification:** каждый sealed блок становится возможным unsolicited broadcast ко всем full neighbors вместо узких batch pull.
- **Duplicate delivery:** при mesh без строго дерева множественные источники пуша воспроизводят блоки многократно; потребовались бы ключи `(height,hash)` suppression и лимиты на unsolicited apply.
- **Standby CPU / IO:** unsolicited полные блоки увеличивают давление decode/apply именно там, где оператор **намеренно притушил noisy `Sync progress`** в коротком хвосте — наблюдаемость улучшается только при аккуратных метриках «unsolicited_accepted».

**Исключение (когда пересмотреть):**

- Если после профилирования V2-9 на реальной топологии (кворум аттестаторов + внешний follower на том же железном сегменте) **sync_hdr/blk станет топ-1 bottleneck** узкого звена перед lat-sensitive attest path **и** есть чёткая граница **segment-only push** без выхода в публичный mesh — имеет смысл оформить **отдельный RFC revision** или `sync_wire_version=2` с нормативными лимитами unsolicited payload.

## 6. Что бы измерить перед реальной реализацией push

1. **Per-peer байты и ms** между событиями: локальный **`seal`/apply** у источника → первое **`apply ok`** у standby на том же L2-сегменте; сравнить с вкладом **attest traffic** если флаг активен (V2-9).

2. **Frequency distribution** числа активных **`in_hdr` / `in_blk`** слотов одновременно на proposer под CY lab смоками — понять, упираются ли они в **`SYNC_INF_CAP`** или в сеть.

3. **Стоимость unsolicited пути без спама:** сколько unsolicited блоков секунду выдерживает узел standby до роста `sync_apply_fail` / лаг mempool при конкуренции за тот же event loop (`tokio`/JSON decode).

---

## Verdict / рекомендация оркестратору и владельцу (**не gate кода**)

**Рекомендация:** **не добавлять** обязательный proactive block/header push поверх текущего same-shard sync **в рамках текущего приоритетного MVP v2 контекста**; **зафиксировать как backlog / future RFC** только после профилирования **V2-9** топологии. Аккуратный **расширяющий** optional frame **возможен в принципе**, но экономия не оправдана ценой **wire bump + anti-amplification** до наличия измерений.
