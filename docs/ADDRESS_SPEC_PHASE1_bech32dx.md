# Address Spec Phase 1: bech32DX

Статус: draft для реализации Phase 1 (MVP-concept).

Этот документ задает пользовательский формат адресов Phase 1 и правила совместимости с текущим `AccountId` (32 bytes).

---

## 1) Цели формата

- Читаемый и узнаваемый адрес с префиксом `pwm1`.
- Явное присутствие в адресе:
  - доменной зоны,
  - поля `flags`,
  - хвоста `subaccount-id`.
- Совместимость с текущим бинарным `AccountId` в ядре (`[u8; 32]`).
- Поддержка нового класса `witness` адресов.

---

## 2) Формы отображения (Phase 1B)

Primary UX (CLI/TUI, strict):

`pwm1-<DOMAIN_HINT>-f<FLAGS8HEX>-t<TAIL52HEX>`

Пример:

`pwm1-CY/4B-f8A31C02-t57A9C1A4D3B9E00112233445566778899AABBCCDDEEFF0011`

Где:

- pretty-вид является основным пользовательским форматом;
- pretty-вид строго не содержит embedded canonical части (`|pwm1...` не допускается);
- pretty-вид содержит полный `TAIL52HEX` без усечения;
- канонический `bech32DX` по-прежнему поддерживается как отдельная форма ввода и вывода;
- для известных country-доменов используется однозначный вид `LABEL/LO_HEX2` (например `CY/4B`);
- для неизвестного домена используется Pascal HEX с суффиксом `!` (например `$BF10!`), как fallback.

## 3) Канонический вид

`pwm1<bech32dx_payload>`

Где payload логически содержит:

1. `version` (для эволюции формата),
2. `domain_field` (основной профиль: 16 бит = 2 байта),
3. `flags_field`,
4. `subaccount_tail` (алфанумерный идентификатор),
5. `checksum`.

### Что наследуется от bech32

- Префикс `pwm1` (HRP + узнаваемость),
- символика/читабельность,
- checksum-like слой обнаружения ошибок.

### Что расширяется (DX)

- В адрес внедряются домен и `flags` как смысловые поля.
- Домен в Phase 1 фиксируется в основном 16-битном профиле (2 байта) с байтовой семантикой.
- Отдельный диапазон для witness-адресов.

---

## 4) Domain field (16-bit, split by bytes)

В основном профиле Phase 1 домен кодируется как `domain_raw` в диапазоне `0x0000..0xFFFF` (строго 16 бит).

Семантика байтов:

- старший байт (`domain_hi`) задает класс/зону домена;
- младший байт (`domain_lo`) задает подтип внутри класса.

Распределение `domain_hi` (256 значений):

- `195` значений — страновые домены (без регионализации в primary user scenario);
- `16` значений — корпоративные сектора;
- `16` значений — резерв;
- `29` значений — witness-диапазоны.

Правила использования `domain_lo`:

- для страновых `domain_hi`: `domain_lo` зарезервирован под будущую регионализацию и в primary flow не используется;
- для корпоративных `domain_hi`: `domain_lo` выбирает конкретную компанию;
- для witness/резервных диапазонов: `domain_lo` интерпретируется policy-правилами соответствующего диапазона.
- `domain_lo = 00` является валидным значением и не подлежит отдельному бизнес-запрету.

---

## 5) Практический профиль поиска (Phase 1 baseline)

Для обычных non-custodial/non-state/non-commercial wallet в baseline-policy:

- используются только 10 младших бит поля `flags`;
- домен выбирается в 16-битной схеме с приоритетом странового сегмента.

Практическая оценка brute-force для regular users:

- эффективное пространство поиска порядка `~18` бит;
- это приемлемо для однопоточного linear scan на типичном CPU;
- дополнительно остается запас ускорения при будущем переходе к multithread.

---

## 6) Flags field

`flags` в Phase 1 задает адресный профиль и назначение.

Минимальные требования:

- сохранить место под расширение без смены базового синтаксиса адреса;
- явно различать active и witness-классы;
- не допускать интерпретацию witness-адреса как spendable.

---

## 7) Стратегия форматирования адреса (domain index)

Формирование человекочитаемого адреса в Phase 1 выполняется через индекс доменов.

### 7.1 Domain index

- `domain_raw` извлекается из payload адреса.
- Далее выполняется проверка попадания `domain_raw` в один из разрешенных диапазонов domain index (country, corporate, reserve, witness) по семантике старшего/младшего байтов.

### 7.2 Валидный адрес

Если `domain_raw` попадает в допустимый диапазон, адрес считается валидным:

- в user-facing выводе используется strict pretty-форма:
  - `pwm1-<label/lo_or_$hex!>-f<flags8hex>-t<tail52hex>`;
- канонический `bech32DX` (`pwm1<encoded_payload>`) доступен как отдельная техническая форма для совместимости.

### 7.3 Невалидный адрес (domain miss)

Если `domain_raw` не попадает ни в один диапазон domain index:

- адрес считается невалидным в policy-смысле;
- при выводе поле домена показывается целиком в HEX после знака `$` (Pascal HEX);
- формат вывода должен явно сигнализировать проблему домена.

Пример представления домена:

- `domain = $00AF` (16-bit).

Требования к Pascal HEX:

- префикс `$`,
- верхний регистр (`A..F`),
- ведущие нули сохраняются по 16-битной разрядности профиля.

---

## 8) Witness addresses

Новая сущность Phase 1:

- witness-адрес не хранит средства;
- witness-адрес не участвует в обычной отправке монет;
- подписи witness валидны только в мультисиг/дополнительных сценариях защиты;
- поле `flags` для witness не влияет на возможность хранения/отправки (в этих сценариях она всегда запрещена).

### Зачем

Снизить вычислительную нагрузку brute-force на слабых устройствах (например, hardware wallet):

- активные адреса могут генерироваться в доверенной и более мощной среде;
- устройство может генерировать witness-адрес существенно быстрее (в среднем 16 попыток) и использовать его как второй слой подписи, не разглашаемый аппаратным кошельком. 

---

## 9) Совместимость и миграция

Phase 1 (compat-first):

- `pwmd` API пока может оставаться hex-centric,
- CLI/TUI показывают `pretty` как primary UX, но в runtime input-paths приоритетен canonical bech32DX (checksum-валидация обязательна); strict pretty остаётся UX-формой без запрета `domain_lo=00`,
- `address_book` хранит canonical-only записи (`bech32dx`) и не использует pretty как источник истины,
- legacy ввод (hex/`PWMv0-`) допускается на переходный период.

---

## 10) Policy для recipient в пользовательском tx-flow

Для `tx-send` и `tx-burn-mark` в обычном пользовательском потоке:

- получатель с неизвестным (`unknown`) доменом отклоняется;
- получатель из `reserve`-диапазона отклоняется;
- получатель из `witness`-диапазона отклоняется;
- допускаются только распознанные regular-домены (regulatory/TNC) из domain index.

---

## 11) User-profile policy: bruteforce + wallet init

Phase 1 user-profile фиксирует практический путь:

- `addr-bruteforce` принимает домен только как label из domain index (для user-profile — country labels);
- numeric raw-domain ввод для этого сценария отклоняется;
- используется `--expected-flags` (alias `--expected-result` для совместимости);
- policy-фильтр: только low-10 bits `flags` (`0x03FF`);
- matching домена — по high-byte для country-класса.

`wallet init` в user-flow:

- запускается через `wallet init --country <LABEL> --wallet-out <PATH>`;
- автоматически выполняет bruteforce первого совпадения по user-profile policy;
- сохраняет derivation path и страновой label в wallet-файл.

---

## 12) Критерии готовности спецификации (Sprint 1A)

- Зафиксированы поля `version/domain/flags/subaccount/checksum`.
- Зафиксирована 16-битная (2-byte) модель домена и распределение `domain_hi`.
- Зафиксирована witness-модель и ограничения.
- Зафиксирован baseline policy для `flags` (10 младших бит) и практический критерий brute-force (`~18` бит для regular users).
