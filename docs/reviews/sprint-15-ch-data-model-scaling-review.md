# Sprint 15 — ClickHouse snapshot data model: горизонтальное масштабирование

**Scope:** Анализ дизайна `row_key` в таблице `pwm_snapshots.node_snapshot` применительно к горизонтальному масштабированию нод внутри одного shard/cluster domain. Ревью-only; продакшн-код не правится.

## 1. Scope recap

Текущая DDL (`tools/docker/sql/clickhouse_pwm_snapshots.ddl`):

```sql
CREATE TABLE IF NOT EXISTS pwm_snapshots.node_snapshot
(
    row_key String,
    inserted_at DateTime64(3) DEFAULT now64(3),
    snapshot_json String
)
ENGINE = MergeTree
ORDER BY (row_key, inserted_at);
```

`row_key` формируется в `pwmd_snap_row_key` (`crates/pwmd/src/snapshot/ch_http.rs:44-76`) по шаблону:

```
{network_id}|0x{cluster_domain_hi:02x}|{cluster_id}|{node_id}|{genesis_digest}
```

Задача: оценить, какие компоненты ключа избыточны при горизонтальном масштабировании (несколько нод одного шарда пишут в общий ClickHouse), и предложить минимальный корректный ключ.

## 2. Requirements fit

**Текущее поведение:** каждая нода одного шарда (одинаковые `network_id`, `cluster_domain_hi`, `cluster_id`, `genesis_digest`) пишет снимок с **уникальным** `row_key` из-за различающегося `node_id`. Данные в `snapshot_json` при этом **идентичны** — все ноды шарда видят одну цепочку блоков и одно состояние (детерминистическая репликация).

**Проблемы:**

- **Дублирование хранилища.** N нод × размер снимка при каждой записи. Для продакшн-сценария с 3-5 нодами шарда и снимками ~10-50 MB это кратное увеличение данных без информационного выигрыша.
- **Отсутствие каноничного ключа для внешних потребителей.** Explorer или аналитический сервис не знает, какой `node_id` запросить; ему нужен один канонический снимок на cluster domain.
- **Ложная семантика уникальности.** `row_key` с `node_id` создаёт иллюзию, что данные от разных нод могут отличаться. На уровне протокола это не так — все ноды шарда разделяют общую truth.

**Вывод:** текущий ключ **не удовлетворяет** сценарию горизонтального масштабирования. Включение `node_id` — архитектурное несоответствие.

## 3. Анализ компонентов ключа

### 3.1. `network_id` — **необходим**

Изоляция сетей (devnet / testnet / mainnet) на общей БД. Без него снимки разных сетей невозможно разделить. **Сохранить.**

### 3.2. `cluster_domain_hi` — **необходим**

Уникальный идентификатор регуляторного домена (1 байт, `0x10`, `0x20`, `0x2C` и т. д.). Один ClickHouse может обслуживать несколько доменов. `cluster_domain_hi` является **основным дискриминатором шарда** в модели identity (см. `RuntimeIdentityMode::Explicit` → `storage_namespace` возвращает `domain-hi-0x{hi:02x}`). **Сохранить.**

### 3.3. `cluster_id` — **избыточен при наличии `cluster_domain_hi`**

`cluster_id` — человекочитаемая метка кластера (`"compat-shard-a"`, `"test-cluster-CY"`). В режиме `Explicit` (целевой продакшн-режим) она назначается оператором и не несёт протокольной уникальности — уникальность обеспечивает `cluster_domain_hi`. Два кластера с одинаковым `domain_hi` и `network_id` — конфигурационная ошибка, а не валидный сценарий.

Ситуация, когда `cluster_id` **разный** при одном `domain_hi` — некорректная конфигурация, которую ключ не должен маскировать.

**Рекомендация:** убрать из ключа. Если нужен для диагностики — хранить как отдельное поле строки (не в ключе).

### 3.4. `node_id` — **избыточен, вреден**

Это центральная проблема. `node_id` отличает экземпляры нод внутри одного шарда, но:

- Данные всех нод шарда **идентичны** (детерминистический консенсус).
- Включение `node_id` приводит к N-кратному дублированию.
- Explorer / аналитик не может запросить «текущий снимок шарда» без знания конкретного `node_id`.
- При scale-out / scale-in набор `node_id` меняется; ключи становятся мусором.
- Единственный теоретический аргумент «за» — диагностика расхождений между нодами — решается отдельным механизмом аудита, а не основной snapshot-таблицей.

**Рекомендация:** убрать из ключа.

### 3.5. `genesis_digest` — **необходим**

Digest genesis state (`state0`) меняется при hard fork (новые параметры, валидаторы, genesis accounts). Разные genesis = несовместимые цепочки. Ключ **должен** различать их, иначе при обновлении genesis старые снимки неверно интерпретируются (и `validate_snapshot` будет падать при несовпадении `genesis_accounts`).

**Сохранить.** Более того, это единственный защитный механизм, гарантирующий, что загруженный снимок соответствует текущей конфигурации genesis.

## 4. Proposed key format

### Минимальный ключ

```
{network_id}|0x{cluster_domain_hi:02x}|{genesis_digest}
```

Три компонента:

| Компонент | Назначение | Пример |
|-----------|-----------|--------|
| `network_id` | Изоляция сети | `testnet-qa` |
| `cluster_domain_hi` | Изоляция домена/шарда | `0x2c` |
| `genesis_digest` | Версионирование genesis | `a1b2c3d4...` |

### Обратная совместимость через `--snapshot-store-key`

Механизм override (`--snapshot-store-key` / `PWM_SNAPSHOT_STORE_KEY`) уже существует и позволяет задать произвольный ключ. Это страховка: оператор может задать любой формат ключа, в том числе с `node_id`, если диагностический сценарий того требует. Рефакторинг затрагивает **только** дефолтное поведение.

## 5. Migration path

### 5.1. DDL

DDL **не меняется**. Таблица принимает любой `row_key: String`. Старые строки с длинным ключом остаются доступны.

### 5.2. Runtime код

Изменения в `pwmd_snap_row_key` (`ch_http.rs:44-76`):

1. Убрать `cid` (cluster_id) и `nid_s` (node_id) из `format!`.
2. Обновить docstring `/// Stable row identity: ...`.
3. Обновить unit test `row_key_derived_fmt` — ожидаемый ключ меняется с `"devnet|0x11|c1|n1|abc123"` на `"devnet|0x11|abc123"`.
4. Проверить test `row_key_default_alias_node_ok` — он просто проверяет `.ends_with("deadbeef")`, пройдёт без изменений.

### 5.3. CLI bin `ch_snap_import`

`--node-id` и `--cluster-id` перестают влиять на дефолтный ключ, но **не удаляются из CLI**: они нужны для `RuntimeIdentity` (логирование, другие подсистемы). Документация (`sprint-15-slice-6-bench.md`) обновляется.

### 5.4. Миграция данных (существующие строки)

Два варианта:

- **Мягкий:** старые строки со старым ключом остаются в таблице; новые ноды пишут по-новому. `ch_load` запрашивает только новый ключ и не видит старых дублей. При необходимости одноразовый `INSERT ... SELECT` перекопирует последний снимок из старого ключа в новый.
- **Жёсткий:** `ALTER TABLE ... DELETE WHERE row_key LIKE '%|%|%|%|%'` (5 сегментов vs 3). Но это необязательно — MergeTree не страдает от неиспользуемых строк.

**Рекомендация:** мягкая миграция. При первом `ch_save` по новому ключу актуальный снимок уже на месте; старые строки можно удалить в удобное время.

## 6. Safety

### 6.1. Риск одновременной записи (write contention)

При новом ключе N нод пишут **одинаковые данные** по одному ключу. MergeTree допускает дубли — каждый INSERT создаёт новую строку с тем же `row_key` и новым `inserted_at`. `ch_load` выбирает `ORDER BY inserted_at DESC LIMIT 1`, поэтому корректность не нарушается. Побочный эффект — N строк за один цикл записи вместо одной. Это **меньше**, чем текущие N строк с разными ключами (тот же объём), и потенциально может быть оптимизировано:

- На уровне приложения: leader election для записи снимка (одна нода пишет).
- На уровне DDL: `ReplacingMergeTree(inserted_at)` — при merge ClickHouse оставит только последнюю версию. Это **не срочно**, но полезно на перспективу.

### 6.2. Потеря данных при неправильном genesis_digest

Нет риска: `genesis_digest` вычисляется детерминистически из `GenCfg.state0()`, одинаков для всех нод одного genesis. Hard fork → новый digest → новый ключ → старые данные не перезаписываются.

### 6.3. Коллизия ключей между разными шардами

Невозможна: `cluster_domain_hi` гарантирует уникальность между шардами/доменами.

### 6.4. Обрезка genesis_digest

Текущий код использует полный hex-digest, обычно 64 символа для SHA-256. Обрезка не применяется — коллизии невозможны.

### 6.5. Обратная совместимость

Override через `--snapshot-store-key` сохраняется. Оператор, явно задавший ключ, не затронут. Автоматически сгенерированный ключ меняется; ноды с новой версией не увидят снимков со старым ключом, если не сделана миграция (см. 5.4). При rolling upgrade кластера это нужно учесть в документации.

## 7. Verdict

**Request changes — medium priority.**

Текущий `row_key` с `node_id` создаёт ненужное дублирование данных и не соответствует модели «snapshot = shared truth per cluster domain». Изменение минимальное (одна функция, ~5 строк кода), обратно совместимое через override, без изменений DDL.

**Приоритизированный список:**

1. **(HIGH)** Убрать `node_id` из дефолтного `row_key` — основная проблема масштабирования.
2. **(MEDIUM)** Убрать `cluster_id` из дефолтного `row_key` — не несёт уникальной информации при наличии `domain_hi`.
3. **(LOW)** Рассмотреть `ReplacingMergeTree(inserted_at)` для дедупликации записей от N нод.
4. **(LOW)** Добавить опциональные метаданные (`cluster_id`, `node_id`) как отдельные столбцы таблицы для диагностики (не в ключе).
