# Обзор кодовой базы pwm-protocol (review-only, 2026-04-18)

## 1. Scope recap

По `docs/MVP-checklist.md` репозиторий нацелен на **devnet-MVP**: ядро `pwm-core` (крипто, HD/brute по домену, состояние, блоки, PoA, mempool, genesis `dev_net()`, оффчейн-заглушка), нода `pwmd` (REST `/v1/*`, фоновый seal), CLI `pwm-cli`, TUI `pwm-tui`.

- **MATRIXCHAIN_SPEC_v0.md** — зафиксировано намеренное упрощение: одна цепь, «матрица» в основном в идентификации (домен × счета), не полный whitepaper.
- **WHITE_SPEC_v0.md** — целевые типы tx (`INIT`, `TRANSFER`, `STAKE`, `UNSTAKE`, `BURN_MARK`), Account, PoA; часть пунктов помечена как вне v0.
- **TUI_SPEC_v0.md** — минимум публичного UI: таблица счетов + опционально Debug JSON; целевой дизайн с двумя панелями, Tab, F5/F6, подсказки F1–F10 — отложен.

Чеклист явно отмечает несделанное: **persist цепи**, **CLI-флаги ноды**, **tx-stake/unstake/burn-mark в CLI**, **единый `--rpc` / `PWM_RPC`**, **расширенные тесты state**, **согласование human-адреса `PWMv0-…` с кодом**, **панели TUI и F5/F6 по §2 TUI_SPEC**.

## 2. Requirements fit

**Соответствует заявленным целям MVP (ядро + демо-нода + базовый CLI + табличный TUI):**

- Крипто: BLAKE3, Ed25519; заголовок блока и Merkle tx — в духе спеки.
- Состояние и ветки tx в `state::apply_tx` покрывают типы из WHITE_SPEC на уровне логики балансов/стейка/марок/INIT.
- `pwmd`: маршруты из чеклиста, seal каждые 2s, до 64 tx из пула.
- CLI: `key-gen`, `addr-derive`, `tx-init`, `tx-send`, `off-demo`.
- TUI: таблица по `GET /v1/accounts`, выбор строки, детали, опрос ~1s, `q`/F10, Debug через `PWM_TUI_DEBUG`.

**Зазоры / частичное покрытие:**

- **Спека vs подпись tx:** в WHITE_SPEC §3 указано хэширование *канонического тела*; в коде подпись идёт по **ручному** `signing_message()` с префиксом `PWMv0/TX`, не по отдельной serde-сериализации «тела без подписи». Для MVP это согласовано внутри кода, но **документ и реализация расходятся** по формулировке «canonical body».
- **Человекочитаемый адрес `PWMv0-…`:** в CLI/TUI везде **hex `AccountId`**, пункт чеклиста §1 не закрыт.
- **MVP-checklist §4–6:** persist, флаги `pwmd`, stake/unstake/burn CLI, унификация RPC, панели TUI — **не реализованы** (ожидаемо по чеклисту).

## 3. Style

- Крейты логично разделены (`pwm-core` / `pwmd` / `pwm-cli` / `pwm-tui`).
- Имена в основном короткие (`st`, `g`, `mpool`); модульные комментарии в `lib.rs`, `mempool`, `offchain`, `chain` — на **английском**; в `hd`, `types`, `state` встречаются **русские** комментарии/doc-строки — смесь языков.
- **`.gitattributes` в репозитории не найден** (infer: политика EOL не зафиксирована в VCS).

## 4. Safety

**Крипто:** Ed25519-dalek, проверка ключей/сигнатур в `verify`; префиксы доменов для разных контекстов (`PWMv0/TX`, `PWMv0/BLOCKHDR`, оффчейн) — разумно.

**Паники / `unwrap`:** в бинарниках CLI/TUI/`pwmd` много `.expect`/`unwrap` на ошибках ввода и HTTP — для dev-утилит приемлемо; в ядре `digest`/`hdr_hash` — `bincode::serialize(...).expect(...)` (практически не падает при типичных структурах).

**Границы доверия:**

- `pwmd` слушает **жёстко** `127.0.0.1:3030` (без CLI-флагов) — сеть по умолчанию не открыта наружу.
- **CORS permissive** — для локального dev ок; в проде требовало бы ограничений.
- `POST /v1/tx`: проверяется только **`verify_sig()`** до попадания в пул; полная **`validate_tx_shape`** (в т.ч. domain) — при **seal** в `apply_tx`. Несостоятельные по состоянию tx всё равно могут занимать пул.

**Лимиты ресурсов:**

- Mempool: **cap 4096**, блок до **64** tx — явные лимиты.
- **Ограничения размера тела HTTP** в Axum по коду не видно — риск больших JSON (DoS по памяти при открытии порта шире localhost).

**DoS / логика пула (важно):** при `seal` список tx **изымается** из `Mpool::take(64)`, затем `Chain::seal` применяет tx последовательно. Если **любая** tx падает на `apply_tx`, весь `seal` возвращает `Err`, блок **не** добавляется, **но tx из пула уже не возвращаются**. Итог: пакет с одной «плохой» (например, неверный nonce) tx **безвозвратно выкидывает до 64 tx из мемпула** — удобная точка для нарушения доступности чужих транзакций в devnet (уточнить при приоритизации).

## 5. Tests

**Фактически (`cargo test`, выполнен локально):** в `pwm-core` **2** юнит-теста — `hd::tests::brute_finds_i0_for_derived_domain`, `chain::tests::seal_empty_block`. Остальные крейты — **0** тестов.

**По чеклисту и здравому смыслу не покрыто или слабо:**

- `state::apply_tx`: happy-path INIT→TRANSFER, **неверный nonce**, insufficient, domain mismatch (часть через `validate_tx_shape`).
- Граничные случаи mempool + seal (см. раздел Safety).
- Интеграционные тесты `pwmd` (HTTP) — отсутствуют.

---

## 6. Verdict

**Request changes** (для продолжения как «готовый MVP» с приоритетом):

1. **Высокий:** поведение **мемпула при ошибке seal** (повторная постановка tx или отдельная очередь «подозрительных», либо поштучное изъятие с возвратом остальных) — иначе предсказуемый DoS/потеря пользовательских tx.
2. **Средний:** расширить тесты **`state` / `validate_tx_shape`** как минимум по пунктам чеклиста; при необходимости — один интеграционный сценарий против `pwmd`.
3. **Средний:** явный **лимит тела запроса** для `POST /v1/tx`, если нода когда-либо слушает не только localhost.
4. **Низкий / документация:** выровнять **WHITE_SPEC** с фактическим `signing_message` / определением `tx_hash` или изменить код под спеку; закрыть или формализовать gap по **`PWMv0-` human address**.
5. **Низкий:** единый **`PWM_RPC`** / `--rpc` в CLI и согласование с TUI — по чеклисту.

**Замечания без блокировки merge для чисто devnet-прототипа:** смесь RU/EN в комментариях, отсутствие `.gitattributes`, CORS permissive.

---

*Ограничения проверки: кроме `cargo test` и статического чтения кода **runtime-нагрузочных сценариев не выполнялось**; поведение мемпула при ошибке seal — вывод из чтения `pwmd` + `Chain::seal` + `Mpool::take`.*
