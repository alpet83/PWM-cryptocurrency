# Оффчейн batch в MVP (as-implemented)

Этот документ фиксирует текущее (MVP-заглушка) поведение оффчейн batch в `pwm-core` и демо-вызов в `pwm-cli`.

## Где реализовано

- `crates/pwm-core/src/offchain.rs`
  - `batch_preimage(batch_id, root)` — формирует payload для подписи;
  - `merkle_root(leaves)` — считает Merkle root по 32-байтным листам;
  - `sign_batch(sk, batch_id, root)` — подписывает payload провайдерским ключом.
- `crates/pwm-cli/src/main.rs`
  - команда `pwm off-demo` демонстрирует полный путь: root + подпись + JSON в stdout.

## Доменные префиксы и криптопримитивы

В текущем коде используются следующие domain separation префиксы:

- `PWMv0-OFFBATCH` — в payload подписи batch (`batch_preimage`);
- `PWMv0/OFFNODE` — для каждого внутреннего узла Merkle-дерева;
- `PWMv0/OFFEMPTY` — для корня пустого дерева.

Криптопримитивы в MVP-стабе:

- хэш: `blake3` (32 байта);
- подпись: `Ed25519` через `ed25519-dalek`;
- `sign_batch` использует `pwm_core::crypto::sign` (сырой `message -> [u8; 64]`).

## Точное поведение `merkle_root`

`merkle_root` работает поверх входа `&[[u8; 32]]` и делает попарное хэширование:

1. Для пары `(left, right)` считается `blake3("PWMv0/OFFNODE" || left || right)`.
2. Если в уровне нечётное число узлов, последний лист дублируется:
   `right = left` (odd-leaf self-pairing).
3. Для пустого списка листов возвращается:
   `blake3("PWMv0/OFFEMPTY")`.

Итого:

- odd-leaf поведение: последний элемент пары хэшируется сам с собой;
- empty-tree поведение: корень фиксирован и детерминирован префиксом `PWMv0/OFFEMPTY`.

## Модель подписи провайдера и доверительные допущения

Текущий MVP рассматривает внешнего провайдера как доверенный источник агрегата:

- провайдер формирует список листов и считает root;
- провайдер подписывает `batch_preimage(batch_id, root)` своим Ed25519 ключом;
- подпись подтверждает только `(batch_id, merkle_root)`, но не заменяет ончейн-валидацию.

Ключевые trust assumptions в текущем объеме:

- корректность состава листов и порядка в дереве доверена провайдеру;
- защита от подмен/пропусков на уровне runtime пока не обеспечена;
- это dev/demo модель, а не финальный bridge security model.

## Как это использует `pwm-cli off-demo`

Команда `pwm off-demo` выполняет демонстрационный сценарий:

1. Берет два фиксированных листа: `[1u8; 32]` и `[2u8; 32]`.
2. Считает `merkle_root(&[a, b])`.
3. Деривит демонстрационный `SigningKey` из seed `[5u8; 32]`.
4. Подписывает batch с `batch_id = 1` через `sign_batch`.
5. Печатает JSON в stdout.

Ожидаемые поля JSON:

- `batch_id` — `u64`, в демо фиксирован как `1`;
- `merkle_root_hex` — hex-строка 32-байтного root;
- `sig_hex` — hex-строка 64-байтной Ed25519 подписи.

## Границы текущего MVP

Сейчас это только оффчейн-демо контур:

- нет ончейн bridge-механизма принятия/финализации batch;
- в runtime нет конвейера inclusion proof + verifier;
- отсутствует end-to-end путь "оффчейн пакет -> проверка в ноде -> ончейн эффект".

Документ описывает исключительно dev-состояние и предназначен для согласования текущей реализации.

## Известные ограничения и следующие шаги расширения

Ограничения:

- `pwm off-demo` использует фиксированные данные и демо-ключ;
- нет стандартизованного формата leaf payload (только 32-байтные leaf hash);
- нет versioned схемы сообщений и проверки совместимости;
- отсутствуют bridge-правила анти-реплея/финализации на стороне chain.

Следующие шаги для интеграции с bridge:

1. Зафиксировать canonical leaf schema (поля, кодирование, порядок).
2. Добавить формат inclusion proof и verifier API в runtime/CLI.
3. Определить bridge-транзакцию/сообщение для коммита batch root на chain.
4. Добавить replay/finality правила (`batch_id`, domain, окно валидности, signer rotation).
5. Согласовать спецификацию и кодовую валидацию, затем обновить этот документ из статуса "stub" в "bridge-ready".
