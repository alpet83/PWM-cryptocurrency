# Slice F — Bridge trust adaptation + peer log isolation + reconnect noise (2026-05-04)

Scope: один слайс для конвейера `pwm-coding → pwm-testing → pwm-review`.  
Нормативная база: `docs/WHITE_SPEC_v0.md` §7.5, `docs/rfc/9-crossdomain-roaming.md` Appendix A.6, `docs/GEO-SHARDING-EXPLANATION.md` §8.

## Цели

1. **Адаптировать спецификацию** отказа в федеративном доверии (level-2) и закрытия one-window в поведение рантайма (флаги, гейты, обмен с пирами).
2. **Изолировать шум транспорта**: отдельный rotating-файл с **префиксом имени `pwmd-peer`**, без записи этих событий в **консоль** (stdout/stderr основого потока).
3. **Снизить частоту и объём** логов при отвалах TCP/handshake по предложениям pwm-review: backoff уже есть в конфиге — проверить применение; агрегация/сэмплирование; логировать смену состояния сессии, а не каждый тик.

---

## Часть A — Bridge federation trust (продукт + протокол поверх MVP)

### A.1 Bridge commitment

- Определить **канонический дайджест** только по мостовым структурам (level-2): минимальный состав полей зафиксировать в коде + короткий комментарий в RFC (follow-up к A.6).
- Исключить полный `state_root` цепочки из определения «мостового» коммитмента (см. WHITE_SPEC §7.5).

### A.2 Обмен и сравнение

- После успешного trust gate (`network_id`, `genesis_hash`) добавить обмен **bridge commitment** с foreign peer (расширение wire hello / отдельное сообщение — выбрать минимальный дифф к существующему протоколу).
- При **несовпадении** с доверенным peer: перевести рантайм в **`bridge_federation_trust_refused`** (имя уточнить в типах), зафиксировать причину (`detail` для оператора).

### A.3 One-window closure

- Заблокировать клиентские маршруты, которые отдают **наблюдаемость чужого шарда / балансы** «как при здоровой федерации» (список эндпоинтов и семантика — инвентаризация в pwm-coding по роутеру + roaming/relay).
- Разрешить безопасные ответы: `503`/`409` с кодом причины, поля в `/v1/status` (`bridge_federation_trust`, `bridge_refusal_reason`).

### A.4 Консенсус и реплики

- Документировать в слайсе (и в комментарии к PR): на нескольких нодах одного шарда все должны получить **одинаковый** исход сравнения commitment при одной высоте и одном наборе пиров; иначе операторский рассинхрон реплик остаётся вне автоматического исправления.

### Testing gate (часть A)

- Юнит-тесты на вычисление commitment (детерминизм, стабильный порядок полей).
- Интеграционный сценарий: два процесса / harness wire — mismatch ⇒ refusal + закрытие one-window маршрутов (минимум один маршрут smoke).

### Acceptance (часть A)

- `/v1/status` отражает доверие моста; при refusal клиент не получает «зелёный» foreign balance через one-window.
- Поведение согласовано с §7.5 / RFC A.6 (без противоречий в доках).

### Risk (часть A)

- Ложные refusal при временной недоступности peer — описать политику retry/debounce отдельно от консенсуса цепочки.

## Часть B — Логирование `pwmd-peer` в отдельный файл, не в консоль

### B.1 Tracing target

- Ввести единый **`tracing` target** для транспорта, например `pwmd::peer` (или `pwmd_peer`), и перевести события из `crates/pwmd/src/transport/**` и смежных мест (handshake, reconnect, tcp) на этот target.
- Оставить в общем потоке только события **вне** `pwmd::peer` (или понизить до отдельной политики).

### B.2 Два независимых sink-а

- **Консоль + основной log file** (как сейчас): фильтр **исключает** `pwmd::peer` (например директива `pwmd::peer=off` для этих layers), чтобы консоль не засорялась.
- **Отдельный rotating file**: шаблон по умолчанию с префиксом имени **`pwmd-peer`**, например  
  `{date}/pwmd-peer-{node_id}-{time}.log`  
  в том же `log_dir`, ротация те же `rotate_*`, что и основной файл (или отдельные поля в `LoggingConfig` — решить в код-ревью с минимальным диффом).

### B.3 Конфиг / CLI

- Флаги или поля конфига: включение peer-file (`on|off`), шаблон пути peer-log (по умолчанию с префиксом `pwmd-peer`).
- Документировать в `docs/pwmd.md`: переменные окружения / CLI зеркально основному логу.

### Testing gate (часть B)

- Тест инициализации логгера (temp dir): при включённом peer file — строка с target `pwmd::peer` попадает только в `pwmd-peer-*.log`, не в «консольный» writer в тестовом registry (или проверка через mock writer).

### Acceptance (часть B)

- При типичном reconnect шторм события transport видны в `pwmd-peer-*.log`, **консоль** оператора не заполняется ими.
- Префикс имени файла **`pwmd-peer`** соблюдён по умолчанию.

### Risk (часть B)

- Дублирование фильтров с `RUST_LOG` — документировать приоритет (PWM_* vs env).

## Часть C — Снижение шума переподключений (поведение + логи)

### C.1 Backoff и политика

- Проверить, что **все** пути reconnect используют `transport_retry_base_ms` / `transport_retry_max_ms` и jitter (если jitter ещё нет — добавить в рамках слайса).
- Убедиться, что **runaway** guard (`transport_runaway_*`) логируется **кратко** (одна строка при входе в cooldown), без спама.

### C.2 Агрегация и уровни

- **`healthy_session_skip`**: не чаще N раз в окне времени на seed на INFO; остальное TRACE или сэмплирование (например 1 из K).
- **`peer reconnect decision` / `tcp connect`**: логировать при **смене** состояния (нет сессии → попытка → установлена / таймаут), либо rollup раз в T секунд с счётчиками попыток.
- **`peer session close`**: оставить INFO, но сжать повторяющиеся причины за окно (первая строка + счётчик дублей).

### C.3 Места кода (ориентиры)

- `transport/lifecycle.rs`: `record_reconnect`, `record_peer_close`.
- Циклы seed/inbound: `transport/spawn.rs`, `peer_session/**/*.rs`.

### Testing gate (часть C)

- При необходимости unit-тест на helper «rate limited log» или ручной прогон soak с лимитом строк/сек (описать в отчёте pwm-testing).

### Acceptance (часть C)

- При симуляции обрыва соединения объём **консольного** выхода существенно ниже baseline слайса до F; peer-детали при этом полностью в `pwmd-peer-*.log`.

## Глобальный acceptance (Slice F)

1. Спецификация §7.5 / A.6 отражена в рантайме (статусы + гейты one-window).
2. Транспортные события — в файле с префиксом **`pwmd-peer`**, не в консоль основного потока.
3. Реконнект-шум снижен по измеримому критерию (отчёт pwm-testing).

## Зависимости и порядок

Рекомендуемый порядок внутри слайса: **B → C → A** (сначала изоляция логов и шум, затем поведенческая логика моста — чтобы отладка A шла уже на чистых логах). Допустимо параллелить A1 (commitment pure fn) с B.
