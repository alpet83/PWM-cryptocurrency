## 2. Requirements fit

**Детерминированный baseline P0 (ожидаемый блок-пропозер):**

- RFC §7.1 задаёт ровно одного ожидаемого пропозера на высоту, детерминированно из **фиксированного набора валидаторов и высоты**, без слотового голосования; неканонический подписант на той же высоте не предпочитается канону.
- Это **согласует** высокоуровневое требование gate о детерминизме для канона и противоречит владельческой эвристике вида UTC % avg_peer / «кто первым в чат» **как норме для ожидаемого блок-пропозера** (см. pretest gate).
- **Разрыв:** в §7.1 **нет явного отрицания** производных источников (moving peer aggregates, wall-clock modulo, first-seen ordering) для именно **вывода ожидаемого пропозера**. Это затрудняет однозначное закрытие спора «что именно запрещено» без чтения всего §7.2–7.3.

**`finalized_height` (семантика для сравнения веток):**

- §7.3 нормативно вводит кортеж fork-choice (`finalized_height`, `head_height`, `head_hash`) и трактует `finalized_height` как **сигнал синхронизационной границы**, не новый финалити-протокол; дальнейшие механизмы финализации отнесены к наследию PoA.
- Кортеж и tie-break по `head_hash` **закрывают** часть нита nits-register про tie-break при ветвлении.
- **Разрыв относительно P0 из nits-register:** для операторски предсказуемого поведения всё ещё не зафиксированы явно **источник значения `finalized_height`** в сообщениях/представлении цепочки и требование **монотонности** вдоль валидного представления состояния. Без этого разные узлы теоретически могут по-разному интерпретировать «что считать finalized» до уровня wire-полей и заголовков.

**Границы зон / сеть до automated waves:**

- §13 задаёт операторские **same-shard segments**, `local_segment_id`, классификацию ingress (`p2p` / `local_broadcast` / `unknown`), подавление intra-segment push и egress-first паттерн; §13.6 профилирует ручки по умолчанию.
- Согласовано с рекомендацией gate: **нет требования** полного LAN UDP или full mesh в MVP; полная реализация fast-path — отложенная эволюция.
- **Небольшая лакуна текстом:** нет короткой нормативной формулировки уровня «**v1 network zone = `local_segment_id` + peer policy classes; обязательное wire-поле net-zone в конверте §6 не требуется**» — смысл выводим из §13, но не одной строкой для читателей плана/CI.

**Связка с `mvp_v2.md` (правки Slice 6 / waves в этом документ-слайсе):**

- Slice 6 и Wave A/B/C **логично закрывают** нит про регулярные волны (nits-register §6) и связывают приёмку спринта с пост-спринтовой автоматизацией.
- `--debug-stop-height` (test-only) **поддерживает** воспроизводимость остановки по высоте для волн.

## 6. Verdict

**approve with nits** — плановый кусок про Slice 6 и волны согласован с roadmap; RFC в `HEAD` в целом держит P0-детерминизм и модель зон §13, но **не полностью закрывает** формулировки gate/nits по усилению §7.1, явной политике `finalized_height` и одной строке про отсутствие обязательного wire net-zone для v1.

**Приоритизированные ниты для последующего микродопинга RFC (pwm-coding / владелец):**

1. §7.1: явное **MUST NOT** для производных недетерминированных источников ожидаемого пропозера (peer-count aggregates, wall-clock modulo, first-seen ordering там, где они могли бы путаться с канонической моделью).
2. §7.3 или §10: **источник и монотонность** значения `finalized_height`, используемого в кортеже, с явной связью с PoA-наследием (ориентир — bullet в pretest gate).
3. Одна короткая нормативная фраза: **represent network zone операционно через `local_segment_id` и peer policy**, без нового обязательного поля в конверте §6 для interoperable v1.
4. По желанию: термин **Gossip coordinator** (non-consensus test harness only), если практикуется в тест-оркестрации отдельно от §7.1.
