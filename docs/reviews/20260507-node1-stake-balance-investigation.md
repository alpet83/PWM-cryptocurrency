# Расследование: стейк и баланс после рестарта (`node-1.ps1`)

## Scope recap

Инцидент пользователя (симптом): после перезапуска нод «пропал» стейк и на счёт вернулись ~1000 PWM; повторный стейк на 500 якобы «обнулил» баланс при том, что в стейке «не числится 1000».

Рамка среды: `node-1.ps1` (`pwmd` на `127.0.0.1:3030`, `--state-root ./tmp/state-testnet`, `./tmp/state-testnet/pwm-data.json`, `./tmp/genesis-custom.json`). Задача: связать наблюдаемые факты (RPC, логи, трассировка кода **без правок прод-кода**), разделить баг интерфейса / ожидания оператора / неясности персистентности.

Тикет трассируемости: `tasks/20260507-node1-stake-balance-investigation.json`.

## Facts observed

- Также полезно: `GET /v1/accounts`, `GET /v1/status`, `GET /v1/head` (загрузка снапшота / деградация).

Эндпойнты ответа по счёту (тип **`AcctOut`**, см. код): `balance_pwm`, `local_state_balance`, `spendable_on_this_shard`, `staked`, `marks`, `nonce`, признаки чужого шарда.

**Фактический снимок** для активного отправителя из лога стейка (hex id из `tx routing guard` / `tx commit delta`):

- id: `2cfb1e1d7001d108b39e05b194f2d1b126931bbfef38506e34297a5474ddae5e`
- `balance_pwm` / `local_state_balance` / `spendable_on_this_shard`: **500000000** (сырые единицы)
- `staked`: **500000000**
- `marks`: **996**, `nonce`: **7**, `initialized`: **true**

Интерпретация шкалы (как принято в `pwm-core` тестах / отображении): делитель целых PWM через `PWM_RAW_SCALE` (**1e6**), значит:

- после стейка на **500** целых PWM видно **500** PWM ликвидно и **500** PWM застейкано ⇒ **итого актив ~1000** PWM у аккаунта (сумма двух полей), а не «всё 1000 только в `staked`».

Симптом «ожидание 1000 в стейке» **не совпадает** с состоянием цепочки: в состоянии `balance_pwm` — это уже **ликвидный** остаток после списания в стейк; стейк — отдельное поле **`staked`**.

### Log excerpts (терминал + `logs/2026-05-07`)

Из хвоста сессии `terminals/1.txt` и дубля `pwmd-test-node-CY-051017.log`:

- Рестарт: загрузка снапшота `./tmp/state-testnet/pwm-data.json`, предупреждение о рассинхроне саммари и манифеста эпох, полная верификация цепочки, успешное завершение загрузки (~142 с).

- `tx commit delta` для **`stake`**: **bal:1000000000→500000000**, **nonce:6→7**, что согласуется со стейком **500000000** сырых единиц (**500** целых PWM при шкале **1e6**).
- Отдельной строкой в логе: `bal_delta=-500000000` для `tx_kind=stake`.

Наблюдений об **ошибке персиста** после этого рестарта в приведённых фрагментах нет: снапшот поднялся и стейк-транзакция применена.

## Ranked root cause hypotheses

1. **Высокая уверенность — ошибка отображения в pwm-tui (NEED-FIX для pwm-coding)**  
   В `pwmd` поле **`balance_pwm`** в **`acct_out_for_runtime`** берётся из **`ac.balance_pwm`**, то есть из состояния посте применения `TxBody::Stake` это уже **ликвидный остаток** (то же задаётся в **`spendable_on_this_shard`** для локального счёта).  
   В той же цепочке `TxBody::Stake` выполняет **`balance_pwm -= amount`** и **`staked += amount`**.  
   В **`pwm-tui`** функция **`format_balance_cell`** при ненулевом **`staked`** считает «траты» как **`balance_pwm - staked`**, что **повторно вычитает** уже разделённый стейк ⇒ в таблице владельца пользователь видит **0 / 500 staked**, хотя RPC показывает **500** PWM свободно и **500** PWM в стейке. Это напрямую объясняет формулировку «баланс обнулился после стейка 500».

2. **Средняя уверенность — операторская интерпретация рестарта (OPERATOR)**  
   Если пользователь когда-то стейкил в другом **`--state-root`**, после «чистого» `./tmp/state-testnet` или смены генезиса/валидируемой ветви старый стейк **не появится** — это ожидаемо. Симптом «вернулось ~1000 на баланс» совместим с **начальным или восстановленным из снапшота** состоянием без стейка, а не с «разморозкой» старых монет из прошлой сессии.

3. **Ниже уверенности — тяжёлая загрузка и WARN по epoch manifest**  
   Предупреждение **`snapshot summary lags epoch manifest; forcing full chain verification`** означает дополнительную работу при старте; в логе загрузка **успешна**. Без воспроизводимых данных о «пропавшем» стейке **до** текущего снапшота нельзя закрыть кейс данных solely из этого среза; явных признаков обнуления стейка при успешном load нет.

4. **Низкая уверенность — математика консенсуса**  
   Код **`TxBody::Stake`** в **`pwm-core`** согласован с логом (`-500000000` баланса, рост **`staked`**). Противоречий между RPC и консенсусом для наблюдавшегося аккаунта **не видно**.

## What pwm-coding should fix vs operator guidance

**pwm-coding**

- Привести отображение баланса в TUI в соответствие с семантикой **`AcctOut`**: для локальных счетов использовать **`balance_pwm`** или **`spendable_on_this_shard`** как уже-ликвидный остаток **без** вычитания **`staked`** второй раз; при желании явно показывать два числа («ликвидно» / «в стейке») или «всего» как сумму, с подписями.  
- Покрыть регрессией формат строки таблицы владельца при ненулевом **`staked`** (минимальный тест на **`format_balance_cell`** или сборку строки UI).

**Оператор / документация использования**

- Для диагностики всегда смотреть **сырой JSON** `GET /v1/account/<hex>` (`balance_pwm`, **`staked`**, **`spendable_on_this_shard`**), а не только колонку TUI.
- После рестарта убедиться, что тот же **`--state-root`** / **`pwm-data.json`** / **`genesis-file`** что и до остановки; смена пути состояния = **новый мир состояния**.
- Если ожидание было «после стейка в одной строке видно всё 1000 как стейк» — это ошибочное ожидание модели данных (сумма разбита на два поля).

## Requirements fit / Style / Safety / Tests (кратко, по промпту ревью)

- Требование «расследование без изменения прод-кода» выполнено; вывод вынесен в отчёт и тикет.
- По стилю/безопасности среза код не менялся; найденное — **семантический разрыв** между RPC и строкой таблицы TUI.
- Тесты: для предотвращения регрессии достаточно таргетного теста на форматирование баланса при стейке; существующие e2e на `AcctRow` в тестах моков должны быть пересмотрены на предмет допущения «двойного вычитания».

**NEED-FIX** (главное): дисбаланс отображения баланса/стейка в **pwm-tui** при живом **pwmd**.
