# Review: RFC 15 addendum — cluster L2 storm guard (intra-cluster suppression, egress-first)

**Дата:** 2026-05-08  
**Тикет:** `tasks/20260508-rfc15-cluster-l2-storm-guard.json`  
**Агент:** pwm-review  
**Артефакт:** `docs/rfc/15-same-shard-sync-v1.md` §4.3, §10 (доп. метрики), §13

---

## 1. Scope recap

Заявленная цель: зафиксировать в нормативном контракте поведение узлов в **плотном L2/L3-сегменте** (несколько нод одного шарда за одним «локальным вещанием»), чтобы после **локальной доставки** транзакции всем участникам кластера не происходило **повторного flood** по тем же p2p-рёбрам внутри сегмента, при этом сохранялся выход трафика **наружу** (мосты, периферия за NAT) и **анти-энтропия** для отстающих узлов.

Связанные документы: RFC 0008 (`domain_hi`), RFC 0015 §4.1/§6.1 (mempool gossip), предложение `docs/reviews/20260508-mempool-mesh-anti-amplification-proposal.md`.

---

## 2. Requirements fit

**Корректность для запланированной mesh-модели (ядро кластера + разрежённая периферия).** Логика **согласована**: если сегмент действительно получает tx через общий fast path (L2 broadcast или эквивалент), повторный push по внутрисегментным p2p-сессиям **не добавляет охвата**, а только умножает трафик — классический риск «шторма» дубликатов на плотном графе. Политика **подавления внутрисегментного push** при `ingress_kind == local_broadcast` и **приоритет egress relay** к внешним классам пиров соответствует целевой топологии из обсуждений mempool mesh.

**Покрытие запроса владельца.**

- Подавление после local-broadcast receipt — §13.2–13.3 (`T_suppress`, запрет `TxAnnounce`/`TxBatch` на same-segment push).
- Egress-oriented forwarding — §13.4 (разрешён push к external/bridge при сохранении лимитов §8).
- Исключения / анти-энтропия — §13.5 (`TxRequest`, компактные раунды, триггеры reconnect/cold start).
- Метрики и алерты — расширение §10 + операторские подсказки по алертам.
- Практический профиль — таблица §13.6.

**Зазоры.** Разделение «тот же сегмент» остаётся **операторской политикой** (`local_segment_id`); без корректной конфигурации guard не должен включаться (§13.6 `false` по умолчанию на generic testnet). Классификация `local_broadcast` требует **явных транспортных хуков** — это честно отражено в §13.7.

## 3. Style and module shape

Изменения затрагивают только Markdown RFC. Имена идентификаторов конфигурации в **snake_case**, короткие. Противоречий с RFC 0008 (идентичность шарда по `domain_hi`, не по IP) нет: §13.2 явно запрещает вывод сегмента только из адреса.

Код и тесты в этом слайсе **не ревьюились** (только спецификация).

---

## 4. Safety

Спецификация снижает **bandwidth amplification** внутри сегмента. Риск **замедления** или **разделения видимости** при ошибочном включении guard без fast path или при слишком длинном `T_suppress` смягчается: pull/anti-entropy разрешены (§13.5), консервативный fallback для `unknown` (§13.7), метрики для диагностики (§10).

---

## 5. Tests

Нормативный текст; приёмка реализации — по §11 Slice 5 (доп. буллет) и наблюдаемости §10/§13. Рекомендуется в pwm-testing отдельные сценарии: два узла в одном сегменте + один внешний; tx через local path → нет лишнего intra push; отключённый член сегмента восстанавливается через `TxRequest`/AE.

## 7. Для владельца (простым языком)

Если несколько нод сидят в одном «тесном» датацентре и получают транзакцию **одним общим местным рассыльщиком** (условно L2), дальше **не нужно** снова гонять те же объявления по кругу между ними по обычному p2p — это только забивает сеть. Правило: **внутри такого кольца не пушим повторно**, а **наружу** (к мостам и домашним узлам за NAT) — пушим как обычно, плюс **запросами и редкими сверками** подтягиваем тех, кто всё же пропустил локальную доставку. Всё это работает только если оператор **явно** включил режим и пометил «кто в одном сегменте»; иначе узел ведёт себя по старой безопасной схеме.
