# PWM Protocol Fitness Assessment

**Дата:** 2026-07-03  
**Модель:** Fable 5 (claude-fable)  
**Тип:** Дизайн-анализ пригодности протокола (не аудит безопасности кода)  
**Коммит:** fc16364  

---

## Что такое PWM — в двух словах

PWM — это блокчейн, в котором основной «валютой» являются не деньги, а **марки (marks)** — ресурс, который накапливается со временем от застейканных монет и необратимо сжигается (уничтожается) как доказательство намеренного экономического расхода внимания.

Ключевые примитивы:
- **Stake** — заморозить PWM-монеты, чтобы генерировать марки со временем (1 PWM × 1 час = 1 марка, потолок u32::MAX ≈ 4.29 млрд)
- **Burn** — необратимое уничтожение марок с метаданными цели (`burn_purpose`) и Merkle-батч-якорением
- **Conservation flag** — исходящие переводы с помеченных адресов задерживаются на 24 часа (защита для крупных держателей)
- **Policy engine** — «тупые контракты» (чистый Rust enum, без VM/Turing), emergency routing, cosign
- **Domain system** — секторальные/корпоративные namespace (`domain_lo`), аренда ~1 год
- **IPv4-распределение** — ~20 млрд PWM раздаётся держателям адресного пространства интернета
- **Offchain batch API** — компании накапливают burn-события локально, раз в период якорят Merkle-корень on-chain

## G1: Противодействие злоупотреблению ресурсами

### В чём суть

Организация, которая хочет обратиться к защищённому ресурсу (API банка, госпортал, email-сервис), должна предъявить доказательство сжигания марок. Сжигание стоит реальных денег (через стейк+время), что делает массовую автоматизацию экономически невыгодной — не блокируя легитимных пользователей.

### Что сделано хорошо

**Экономика лучше, чем Hashcash.** Hashcash (proof-of-work для email) провалился потому, что ботнеты получают вычислительную мощность бесплатно — узкое место для спамеров не существовало. PWM использует *капитал × время* как основу стоимости: чтобы добыть марки, нужно держать реальные деньги в стейке. Ботнет не может украсть застейканный баланс в чужом кошельке.

**Кастодиальная триада** для институциональных клиентов (банков, корпораций) продумана:
- Conservation-флаг: 24-часовая задержка исходящих переводов — время на остановку скомпрометированной операции
- Non-disableable cosign: нельзя отключить требование второй подписи для привилегированных действий
- Emergency evacuation: при активации маршрутизации к rescue-адресу застейканный баланс тоже эвакуируется (ADR 0012)

**Доменная система** даёт корпорациям identity anchor без KYC on-chain:
- `company_metadata_commitment` — hash корпоративных метаданных с off-chain верификацией (правильный паттерн)
- `domain_lo = 0` — root-слот для организаций без отдельного namespace
- Полномочия держателя домена: whitelist участников, заморозить скомпрометированные адреса, требовать cosign

**Слоистая модель доверия** с отрицательным энергобалансом против самораскрутки — одна из самых тонко проработанных вещей в документации.

### Что не сделано — критические дыры

**1. Верификаторной половины не существует.**  
Весь value протокола создаётся на стороне получателя (банк, API, почтовый сервер), который проверяет доказательство сжигания. Эта половина — спецификации и намерения. Нет:
- Замороженного RFC формата предъявления (X-PWM-Auth / X-PWM-Mark)
- Reference-реализации фильтра (nginx, SMTP)
- Стандарта кодов ошибок

Пока это не сделано, сжигать марки некому и незачем.

**2. Критическое противоречие: stateless verification vs. replay.**  
В документации по UC-2 (защита KII API) описывается «stateless nginx-верификация» — только HTTP-запрос к `/v1/tx/{txhash}`, без локального кеша. Это несовместимо с one-time-use proof: один и тот же burn можно предъявлять бесконечное число раз разным верификаторам или одному и тому же. `burn_purpose = "api_access"` привязывает burn к ресурсу, но не к конкретному запросу.

Решение: либо верификатор хранит множество использованных proof (stateful), либо формат purpose должен включать nonce/hash запроса + временное окно верификации. Без этого весь механизм защиты — иллюзия.

**3. Нет механизма калибровки цены.**  
Сдерживающий эффект полностью зависит от рыночной цены PWM, которая не определена. При цене монеты близкой к нулю — барьер для спамеров тоже нулевой. Нет ни справочного фреймворка ценообразования, ни адаптивной схемы корректировки цены burn по мере изменения курса.

**4. Регуляторный путь для КИИ/государства не проработан.**  
Токен в цепочке аутентификации критической инфраструктуры в большинстве юрисдикций столкнётся с нормативными ограничениями и требованиями сертификации. В документах это частично учтено (позиционирование «proof-of-work, не микроплатёж»), но нет архитектуры для permissioned-развёртывания и юридического анализа по целевым юрисдикциям.

**5. Клиент без марок.**  
Гражданин, зашедший на госпортал, не имеет застейканных PWM. Целевая модель — оператор сжигает от имени пользователя из общего баланса. Это честный ответ, но нужно говорить об этом прямо: развёртывание по факту является «системой квот с blockchain-аудит-трейлом», а не «пользователь сам предъявляет марки».

### Сравнение с существующими решениями

| Решение | Слабость которую решает PWM | Где PWM проигрывает |
|---------|---------------------------|---------------------|
| Hashcash (PoW) | Боты получают CPU бесплатно | Пока что legacy |
| reCAPTCHA | AI решает капчи за копейки | Нулевое онбординг-трение у Google |
| Cloudflare WAF | ML можно обмануть | Cloudflare не требует кошелёк у пользователя |

**Правильное позиционирование:** дополнение к существующим WAF/ML-стекам, не замена. Экономический слой под поведенческим анализом.

## G2: Протокол репутации с нулевым разглашением

### Идея

В итоговой ветке развития важен не отдельный факт сжигания, а *накопленная репутация сжигающего* — доказуемая без раскрытия конкретных действий. «Докажи, что ты сжёг ≥N марок за ≥T времени в ≥k доменах, не раскрывая ни одного конкретного сжигания, ни времени, ни домена».

### Что есть в текущей архитектуре

**Полезный скелет:**
- Каждый burn-событие канонически захешировано и входит в подписанные байты tx — чёткое, committed представление
- Offchain batch API уже якорит Merkle-корни on-chain — именно то, что нужно как публичный вход для ZK-доказательства включения
- Концепция cleanup-chain (линейные архивные commitments с ссылкой на предыдущий) — правильная идея для долгосрочной burn-истории

**Что работает против ZK:**
- `burn_purpose` — **публичная freeform-строка**. Весь burn виден полностью: burner, цель, время, сумма. Добавить приватность поверх этого нельзя — нужно менять то, что идёт в листья.
- Каждый burn публично привязан к `AccountId` с публичным Ed25519-ключом. Анонимизировать постфактум невозможно.
- В целевой кастодиальной модели >99% сжиганий идут с адреса *оператора* от имени пользователей. Цепочка не знает, кто реальный экономический burner. ZK-доказательства от chain-данных аттестуют только репутацию оператора.

### Что отсутствует полностью

| Необходимый примитив | Статус |
|---------------------|--------|
| Hiding commitments в листьях Merkle-батча | Отсутствует |
| Nullifiers (защита от двойного предъявления) | Отсутствует |
| Структурированная taxonomiy purpose (domain_id, action_class) | Отсутствует |
| ZK-дружественное хеширование (Poseidon вместо BLAKE3) | Отсутствует |
| ZK-совместимая привязка идентичности | Отсутствует |
| Epoch-аккумулятор / root-of-batch-roots | Отсутствует |
| Pruning-safe архивные commitments | Контуры, не реализация |

### Конкретно что нужно добавить

**Фаза 1 (без изменений в консенсусе):**  
Операторские анонимные credentials в стиле BBS+ / Coconut — оператор уже видит всё, батчит и подписывает; выдавать selectively-disclosable credentials («этот адрес сжёг ≥N марок класса X в эпохе E») с batch-корнем на цепи. Это не требует изменений консенсуса.

**Фаза 2:**  
- Hiding leaves: `Commit(key_commitment, amount, domain_tag, epoch, salt)` (Pedersen/Poseidon) вместо plaintext
- Nullifiers: `PRF(sk, leaf)` с domain-separation — решает и проблему replay из G1 одновременно
- Structured purpose: `(domain_id: u16, action_class: u8, payload_commitment)` — наиболее высокий leverage, один RFC который помогает G1, G2 и G3

**Фаза 3:**  
Рекурсивные aggregate proofs (Halo2 / Nova / folding) над epoch-аккумуляторами для утверждений «за T времени». STARK-доказательства если команда хочет сохранить BLAKE3-деревья без изменений (крупнее, но без trusted setup).

### Честный рефрейминг Sybil-проблемы

Линейная модель начисления марок (намеренно, анти-фрагментационный принцип!) означает: 1M PWM в стейке на одном адресе = 1000 адресов по 1000 PWM каждый = та же суммарная репутация, одинаковая стоимость. Дробление аккаунтов — **не атака, это возможность**, и она заложена в дизайн (кастодиальная модель = marks-as-a-service).

**Burn-агрегаты доказывают capital×time commitment, не поведение.** Это один вход в reputation score, не сам score. Оставшийся репутационный сигнал живёт в операторском слое (X-PWM-Trust-Metadata, asymmetric trust growth, source-diversity weighting — всё это в post-MVP модели, off-chain, и не поддаётся ZK-доказательству из chain-данных).

## G3: Дополнительные применения

### Email anti-spam (UC-1)

**Математика в пользу легитимных массовых отправителей.** 1 застейканный PWM = 24 марки/день. Рассылка 1M писем/день при 1 марке/письмо требует ~42k PWM в стейке — разовая капитальная позиция, не операционные расходы. Offchain batch API закрывает throughput (76 tx/s на цепи не важно, когда 99% в батче).

**Нерешённые проблемы:**
- Правильная ставка burn не может быть константой протокола — это политика получателя; нужна ценовая инфраструктура
- Ценовой барьер зависит от рыночной цены PWM (в первом цикле «монеты дёшевы» — это касается и атакующих)
- Сетевой эффект верификаторов: SPF/DKIM потребовали десятилетие с поддержкой Google/Microsoft. X-PWM-Mark RFC ещё не существует.

Закрытые экосистемы (корпоративная почта одной компании, svcpool.io) — правильный первый плацдарм.

### AI agent rate-limiting

Сильная идея как **бюджетный/quota-примитив с публичным audit trail**, не как хардовый барьер безопасности.

Что честно и интересно: агент несёт конечный, публично аудитируемый, не пополняемый без капитала ресурс. Угнанный или сбойный агент быстро исчерпывает бюджет. Кросс-провайдерная переносимость без money transmission — реальное регуляторное преимущество перед per-provider billing.

**Атаки которые остаются:**
- Marks-as-a-service: кастодиальная модель позволяет операторам перепродавать burn-ёмкость недобросовестным агентам
- Replay при предъявлении на API-границе (та же проблема что в G1)
- Капитализированный атакующий арендует больше стейка

Честное позиционирование: конкурент API-ключам + биллингу с преимуществами в interoperability и аудите.

### IPv4-дистрибуция — структурная угроза

**Стратегически умно:** ISP, облака, банки, телекомы — именно те, кого PWM нужен как verifier'ы и стейкеры; они же держат IP-пространство. Фазность (5×~4B), разбивка по октетам — реальная проработка нагрузки.

**Структурная угроза:**  
~95% genesis supply (~20 из 21 млрд PWM) проходят через **один централизованный registry** с **единственным `registry_sig`-ключом** на цепи (`state.rs::verify_claim_sig`). Компрометация этого ключа или registry-сервиса — катастрофа целостности supply.

| Проблема | Серьёзность | Минимальный фикс |
|---------|-------------|-----------------|
| Единый registry_sig-ключ | Критическая | Threshold/multisig, ротация per-phase |
| Нет внешнего L1-якорения батчей | Критическая | Обязательное битчейн/эфириум-якорение каждого claim-батча |
| Proof-of-control ≠ ownership | Высокая | Кросс-проверка RIR-данных + multi-window контроль |
| Нет процесса dispute | Высокая | Дизайн до фазы 1 |
| Концентрация у /8-холдеров | Высокая | Sqrt/tier-формула в ADR-0002 критична, не деталь |

Эти пункты — **блокирующие для запуска фазы 1**, не hardening-нотатки.

## Главные выводы

### Что работает хорошо уже сейчас
- Стейк-время как cost basis выигрывает у Hashcash именно там где Hashcash провалился
- Policy engine как pure enum — правильный выбор для security-аудируемой среды
- Кастодиальная триада (conservation + non-disableable cosign + emergency evac) закрывает институциональный prerequisite
- Layered trust model с self-bootstrap negative-energy invariant — нетривиальная экономическая работа
- Offchain batch API с Merkle-якорением — правильный скелет для будущих ZK-доказательств

### Три изменения с максимальным leverage

**1. Structured purpose RFC** — `(domain_id: u16, action_class: u8, payload_commitment)` вместо freeform строки. Один RFC который одновременно: даёт G1 инструмент для ценообразования, даёт G2 domain separation для ZK, решает проблему replay через structured nonce-binding. Наивысший ROI на одно изменение.

**2. Replay-proof presentation RFC** — per-request nonce или nullifier в purpose + временное окно верификации. Без этого весь G1-барьер иллюзорен.

**3. Threshold registry signature + L1-якорение claim-батчей** — условие запуска IPv4-дистрибуции фазы 1. Без этого риск supply-интегритети неприемлем.

## Примечания владельца проекта

### 1. ZK остаётся контуром без RFC

Выводы аудита по G2 корректны в части отсутствия ZK-примитивов, но рекомендация «добавить ZK-RFC» не принимается. Принцип проекта — **простота реализации**; ZK обозначен как долгосрочный контур, не как MVP-требование. Текущий скелет (Merkle batch + offchain anchor) достаточен для G2 на горизонте V7-8. Внедрение hiding commitments, nullifiers и Poseidon возможно позднее поверх уже существующего дизайна без ломающих изменений протокола.

### 2. Replay — Medium, не Critical

Аудит оценил replay как Critical (гэп №2 в сводной таблице). Фактическая серьёзность — **Medium**. Причины:

- TTL доказательства: 1–2 секунды (hardcoded в верификаторе)
- purpose = `hash(URL + method + nonce)` — структурированная привязка к запросу
- Комбинация TTL + nonce-hash делает повтор экономически бессмысленным при нормальной задержке сети

Повтор остаётся теоретически возможным в пределах окна TTL при атаке на одном соединении, поэтому Medium обоснован. Critical — избыточно.

### 3. IPv4 on-chain адрес: многоуровневая защита

Гэп №3 (единый `registry_sig`-ключ для ~95% genesis) описан корректно, но без учёта уже реализованных контрмер:

- **Conservation flag** — 24-часовая задержка перед любым крупным движением; даёт время на реакцию
- **Offline signing** — ключ распределения никогда не находится в hot-wallet
- **Cosign** — обязательная вторая подпись от независимого ключа на каждую эмиссию
- **Emergency evac** — процедура экстренного переноса в случае компрометации

Риск остаётся (одна точка отказа до threshold/multisig), но он управляемый и соответствует текущей стадии проекта. Переход на threshold-подпись запланирован в рамках IPv4-дистрибуции фазы 1.

## Примечания владельца проекта

*Дата: 2026-07-03*

### 1. ZK — правильно оставить контуром, не RFC

ZK-репутация — значимый архитектурный сдвиг, который прямо конфликтует с базовым принципом проекта **«надёжность через простоту»**. Реализация требует отдельного специалиста по ZK-схемам, proving systems и trusted setups — это вне компетенций и ресурсов текущей команды и в рамки MVP не умещается.

Правильная позиция: реализовать структурированный `burn_purpose` (domain_id + action_class) как небольшой, технически простой шаг, который оставляет ZK-возможность открытой на будущее — и явно зафиксировать ZK как **архитектурную перспективу без коммита**. Принятие этого трека будет зависеть от роста сообщества, интереса бизнеса и расширения ресурсов; предположительно потребует найма отдельного специалиста. До этого момента — контур без RFC.

### 2. Replay-уязвимость преувеличена

Оценка «критическая» в разделе гэпов завышена. Проблема решается простыми средствами, не требующими nullifiers или stateful базы данных:

- **TTL 1–2 секунды** на предъявляемый proof — стандартное скользящее окно, реализуется in-memory структурой в несколько тысяч записей (то, что любой backend уже делает для rate-limiting)
- **Структура purpose для критических ресурсов:** `hash(URL + HTTP-method + salt/nonce + timestamp)` — привязывает burn к конкретному запросу, делая повторное использование бессмысленным

Это не «stateless verification несовместима с one-time-use proof» — это проектирование правильного формата purpose. Правильный уровень серьёзности: **Medium**, решается одним RFC на структуру purpose.

### 3. On-chain адрес раздачи защищён слоями

Опасение Fable 5 насчёт «единственного registry_sig-ключа» относится прежде всего к *off-chain registry-сервису* (принимает заявки, верифицирует контроль IP, рассчитывает аллокации) — это операционный риск, требующий организационных мер.

On-chain адрес раздачи (через который проходят allocation-батчи) в действительности защищён всеми доступными слоями протокола:

- **Conservation flag** — любой transfer задерживается на 24 часа и может быть остановлен
- **Offline подписание** — ключ никогда не касается сети; все транзакции подписываются изолированно
- **Полный cosign** — multi-party подпись, ни один участник не может действовать в одиночку
- **Emergency evacuation** — rescue-адрес может эвакуировать баланс при компрометации

Практически реализуемо: генерировать по одному такому адресу на каждую фазу раздачи и вносить их в genesis-блок — прозрачно, аудируемо, проверяемо заранее. Это сильнее, чем threshold-подпись на горячем ключе, которую рекомендовал анализатор.
