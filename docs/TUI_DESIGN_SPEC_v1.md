# PWM TUI Design Spec v1

Этот документ задает единый baseline визуального и интерактивного поведения UI/TUI для форм и модальных диалогов в `pwm-tui`.

Связанный документ продуктового уровня: `docs/TUI_SPEC_v0.md` (что должно быть в TUI).  
Этот документ фиксирует как это должно выглядеть и работать на уровне UX-паттернов.

## 1. Scope и приоритет

- `TUI_SPEC_v0`: продуктовые требования и целевые сценарии.
- `TUI_DESIGN_SPEC_v1` (этот файл): правила отрисовки, фокуса, редактирования, ошибок, модалок и читаемости.
- При конфликте по UX-деталям для форм/модалок приоритет у этого документа, если это не ломает продуктовую логику из `TUI_SPEC_v0`.

## 2. Layout baseline

- Основной экран: контентные панели + нижняя status/help строка.
- Модалки: centered popup поверх контента с четким заголовком и границей.
- Текст в модалке идет сверху вниз блоками: контекст -> поля/данные -> статус/валидация -> подсказки клавиш.
- Footer на основном экране всегда однострочный и содержит минимальный набор горячих клавиш.

## 3. Focus model

- В каждый момент времени активен только один интерактивный контекст:
  - основной экран, или
  - конкретная модалка.
- При открытой модалке клавиши обрабатываются только ей (modal lock).
- В форме активно только одно поле ввода (active field).
- Активное поле визуально отличимо от неактивных.

## 4. Editable vs fixed fields

- `fixed` поле:
  - не редактируется пользователем,
  - может показывать lock hint (`[fixed]`, `[fixed from receiver]` и т.п.),
  - не получает editable background.
- `editable` поле:
  - поддерживает inline editing (см. раздел 5),
  - подсветка применяется только к value-области, не к label (`amount:` и т.п. остаются без фона),
  - может иметь active-variant (например желтый foreground + editable background).

## 5. Cursor и inline editing

Для всех editable текстовых полей (включая однострочные поля в модалках):

- Видимый caret: `|` внутри значения активного editable-поля.
- Навигация курсора:
  - `Left` / `Right`
  - `Home` / `End`
- Редактирование:
  - вставка символа в позицию курсора,
  - `Backspace` удаляет символ слева от курсора,
  - `Delete` удаляет символ справа от курсора.
- Операции должны быть корректны на границах строки (без panic/no-op где нужно).

## 6. Color semantics

- `Error` (блокирующая ошибка/валидация): красный (`Red`).
- `Warning` (неблокирующее, но важное состояние): желтый (`Yellow`).
- `Info/neutral` (обычный статус): базовый стиль без warning/error акцента.
- Editable value area: `DarkGray` background, label без editable background.
- Не использовать только цвет как единственный сигнал: добавлять текстовый префикс/формулировку (`status:`, `warning:`).

## 7. Modal patterns

- Заголовок короткий и по действию (`Send`, `Save to address book?`).
- `Esc` закрывает/пропускает текущую модалку, если не оговорено иначе.
- Критичные действия подтверждаются `Enter` в явном контексте.
- Последняя строка модалки содержит краткий key help для этого контекста.
- После успешного действия допускается chained modal, если это логическое продолжение (например append address book после send).

## 8. Footer/help conventions

- Основной footer показывает:
  - краткие hotkeys (Tab/F5/F6/F10 и т.д.),
  - источник RPC/окружение при необходимости,
  - короткие runtime предупреждения (например fallback mode).
- Текст footer компактный, без многострочных блоков.

## 9. Validation message style

- Формат: коротко и по полю (`amount must be > 0`, `confirm must be 'yes'`).
- Ошибка валидации не должна очищать пользовательский ввод.
- Ошибка submit/IO отображается в статусной строке формы/модалки.
- Успех и ошибка должны быть визуально различимы (как минимум цвет + текст).

## 10. Accessibility и readability для терминала

- Не перегружать один экран длинными абзацами.
- Избегать цветовых сочетаний с низким контрастом.
- Важная информация должна быть читаема в моноширинном шрифте и при узком терминале.
- Все ключевые действия должны быть доступны с клавиатуры, без мыши.
- Формулировки подсказок короткие, с однозначными глаголами (`append`, `skip`, `close`, `submit`).

## 11. How to use with agents

Для задач по UI/TUI в `pwm-coding` передавать минимум:

- Контекст: экран/модалка и пользовательский сценарий.
- Ограничения: что нельзя ломать по hotkeys и flow.
- Блок из этого документа:
  - `Focus model` (раздел 3),
  - `Editable vs fixed fields` (раздел 4),
  - `Cursor и inline editing` (раздел 5),
  - `Color semantics` (раздел 6),
  - `Modal patterns` (раздел 7).
- Ссылку на `docs/TUI_SPEC_v0.md` для проверки соответствия продуктовой цели.

Рекомендуемый шаблон в задаче:

`UI baseline: follow docs/TUI_DESIGN_SPEC_v1.md sections 3-7, keep product behavior aligned with docs/TUI_SPEC_v0.md; do not break Enter/Esc semantics and existing F-key flows.`
