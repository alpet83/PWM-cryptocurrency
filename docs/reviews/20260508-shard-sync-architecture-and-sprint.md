# Архитектурный обзор и проект спринта: chain sync внутри одной шарды

**Дата:** 2026-05-08  
**База:** `tasks/20260508-shard-sync-sprint-design-info.json`, существующие ревью `docs/reviews/20260507-peer-transport-capabilities.md`, `docs/reviews/20260507-snapshot-summary-manifest-lag.md`  
**Область:** same-shard P2P: mempool sharing, распространение блоков/подписей до включения в цепь, catch-up истории (в т.ч. через epoch JSON).

---

## 1. Current state (as-is)

### Код

- **Транспорт и wire.** В `PeerWireMsg` есть только `Hello` / `HelloAck`, `Heartbeat` / `HeartbeatAck`, `CrossShardFacts`, `AccountViews`. Кадр: length-prefixed JSON, потолок полезной нагрузки одного сообщения **1 MiB** (`wire.rs`). Сообщений для блоков, заголовков, inv/getheaders/getblocks **нет**.
- **Handshake.** Подписанный `NodeHello` (сеть, genesis, кластер с `domain_hi`, capabilities). Классификация native/foreign, защита от replay — по существующим модулям handshake/policy.
- **«Сервис» sync в hello.** В исходящем hello (`dial.rs`) в `services` перечислены строки `mempool` и `sync`, но **поведения sync на проводе нет** — это расхождение заявленных возможностей с фактом (см. обзор 2026-05-07).
- **Консенсус / seal.** По ADR 0001 и коду жизненного цикла блоки формируются **локально** (`spawn_seal_loop` → `chain.seal`), без распределённого упорядочивания между нодами одной шарды. Две ноды с одним `domain_hi` **не** сходятся к одной цепочке автоматически через P2P.
- **Federation / heartbeat.** `chain_tip_height` в heartbeat влияет на **таблицу наблюдаемых высот** шардов, а не на загрузку блоков.
- **Snapshot / epochs.** История на диске: summary, `pwm-epochs-manifest.json`, файлы эпох с **JSONL** (по одному сериализованному `Block` на строку), атомарная запись через `.tmp` + rename (`incremental.rs`). При старте — загрузка через snapshot-пайплайн (`lifecycle`, `absorb_blocks_tail`). **Сетевой** обмен эпохами как протокол **не реализован**.
- **Мемпул.** `pwm_core::Mpool`: локальная FIFO-очередь с лимитом, `push` / `take` / `prepend_block`. **Нет** gossip TX между пирами.

### RFC и документация

- **RFC 8** задаёт идентичность, peering, метрики, acceptance §11 — в основном **про identity/handshake и приоритеты**, не про формат chain-sync и fork-choice. §11 не покрывает передачу блоков.
- **ADR 0001** фиксирует PoA dev-контур; путь к CometBFT — отдельная эпоха; для v1 same-shard sync нужно явно договориться, **чей** блок считается каноническим при нескольких нодах-сейлерах.
- **Известный операционный нюанс:** расхождение `checkpoint_height` в summary и `canonical_h` в манифесте до ~99 блоков в штатном режиме — важно для интерпретации «докачали ли мы диск» и для будущего sync с пира (см. ревью snapshot lag).

**Вывод as-is:** сеть пригодна для идентичности и кросс-шард сигналов; **канал репликации цепочки и мемпула отсутствует**. Catch-up возможен только из **локальных** файлов snapshot, не из P2P.

## 2. Target capabilities (must-have для same-shard sync v1)

Ниже — минимальный набор, без которого «шардовый блокчейн между нодами» остаётся коллекцией независимых сейлеров.

1. **Общий канонический вид цепочки (логически).** Нода, подключённая к сети native-пиров, должна иметь возможность **догнать** известный tip по хешам/высоте: получить блоки (или эквивалентное состояние), проверить связность и правила валидности **в рамках выбранной модели консенсуса v1** (см. open questions).
2. **Безопасный apply входящих блоков.** Проверка подписи валидатора (или иного seal-доказательства), высоты, родительского хеша, лимитов размера; отказ при несовместимости с genesis/network_id.
3. **Живой поток обновлений.** После catch-up — получение **новых** блоков (или заголовков + последующий fetch тел) с native-пиров без полного пересканирования диска.
4. **Mempool gossip (baseline).** Распространение **валидных** подписанных TX между native-пирами с дедупликацией и лимитами (capacity, rate), без обязательной глобальной доставки (best-effort допустим для v1, но критерии — в RFC).
5. **Политика при отставании и сбоях.** Явное поведение: bootstrapping, reconnect, backoff, ограничение параллельных запросов; сигналы в логах/метриках для оператора.
6. **Совместимость с существующим handshake.** Новые сообщения не должны ломать классификацию пиров и genesis-guard; возможность **feature gate** / согласования версии субпротокола sync.

Опционально для v1, но сильно желательно как fallback:

7. **Catch-up крупными кусками (epoch-файлы).** Чтобы не гонять десятки тысяч отдельных P2P-сообщений, peer может отдавать **целый epoch JSONL** (или стрим), совместимый с тем, что уже пишет `incremental` — при условии проверки целостности (манифест, хеши).

## 3. Архитектурные варианты

### Вариант A — wire-level block/header sync protocol

**Идея:** расширить `PeerWireMsg` (или ввести отдельный enum субпротокола в том же TCP-канале после handshake) сообщениями вида: объявление tip / заголовков, get-headers, get-blocks, батчи блоков, при необходимости inv/getdata для блоков.

**Плюсы.**

- Единый транспорт с существующим TCP и JSON-framing; переиспользование heartbeat и политики native-first.
- Пошаговая догрузка: можно начать с **header-first**, затем выборочно тянуть блоки.
- Хорошо стыкуется с «live» обновлением после начальной синхронизации.

**Минусы.**

- Большой объём JSON по сети при крупных блоках; может понадобиться **сжатие** или двоичный альтернативный codec в будущем.
- Нужны чёткие **анти-DoS** правила (размер батча, частота get*, идентификация запросов), иначе 1 MiB/frame и eager peers — риск.

**Риски безопасности.**

- Подделка цепочки: без fork-choice и проверки seal злоумышленный native-компрометированный peer может попытаться скормить ветку; нужны лимиты и **якорение к известному genesis + правилам валидатора**.
- Злоупотребление «тяжёлыми» ответами: ответчик должен ограничивать работу на запрос; запросчик — валидировать до apply.
- Эквивалентность проверок с локальным seal: если несколько нод могут сейлить, нужна явная семантика «кто автор блока» (см. open questions).

**Сложность.** Высокая по объёму кода (state machine sync, буферы, интеграция с `chain`/`snapshot`), средняя по концепции.

**Операционные эффекты.** Настраиваемые лимиты, метрики «sync lag», отдельные алерты; возможное увеличение CPU/IO на сид-нодах.

---

### Вариант B — epoch-file transfer catch-up first, then header/block live sync

**Идея:** первым этапом (или fallback) peer отдаёт **файлы эпох** (или поток JSONL + обновление манифеста), совместимые с `epochs/` и `EpochManifest`; локально нода использует существующие пути `repair`/`load` где уместно; после выравнивания включается **узкий** live-протокол (как в A — заголовки + последние N блоков).

**Плюсы.**

- Меньше чаттера протокола на длинной истории; ближе к тому, как операторы уже представляют **бэкапы эпох**.
- Переиспользование дискового формата и манифеста; проще отладка (можно сравнить файлы).

**Минусы.**

- Большие одномоментные передачи: таймауты TCP, целостность (хеш файла, размер), частичные сбои — нужен **резюмируемый** протокол (offset/chunks) или хотя бы повтор с курсором по эпохе.
- Сложнее **квота** на стороне отдающего (место на диске + одновременные «скачивания»).
- Вариант «только файлы» без live-синка **не** закрывает must-have п.3 — значит B почти всегда **B+A-lite**.

**Риски безопасности.**

- Принятие **целого файла** без строгой привязки к manifest/genesis — риск подмены архива; нужны подписи/хеши на уровне эпохи или цепочки trusted peer policy.
- Долгие соединения на большом потоке — больше окно для RST/DoS; нужны лимиты скорости и idle.

**Сложность.** Средняя на транспорт epoch-чанков, высокая на стыковку с manifest и «не сломать» running node при записи.

**Операционные эффекты.** Явные роли «archive peer» / лимиты исходящего трафика; документация восстановления «скопировал epoch + перезапуск».

## 4. Рекомендованный путь (пошагово, sprint-ready)

1. **Заморозить нормативный контракт (Slice 0):** отдельный RFC или раздел к RFC 8 / новый RFC 00xx: сообщения, состояния синхронизатора, fork-choice для v1 PoA, поведение при нескольких сейлерах, лимиты мемпула gossip, анти-DoS. Уточнить семантику capability `sync`.
2. **Минимальный wire-слой (Slice 1):** типы сообщений + feature flag версии; без полной логики — совместимость «старый peer / новый peer».
3. **Mempool gossip (Slice 2):** inv/tx или компактные объявления + dedup; интеграция только с `Mpool::push` после валидации TX (не сырой десериал в блок).
4. **Header-first + block fetch/apply (Slice 3):** догон tip; переиспользовать внутренние проверки цепочки из core где возможно; явный путь отказа без паники.
5. **Epoch catch-up fallback (Slice 4):** опциональный быстрый путь (chunked), проверка против manifest; не заменяет live, дополняет.
6. **Observability + хаос + операторка (Slice 5):** метрики из RFC 8 §9 дополнить sync-метриками; сценарии обрыва; runbook.

Стратегически: **B как ускоритель начальной догрузки**, **A как обязательный live-каркас** — на практике гибрид, даже если в спринте сначала реализуют только A-minimum, а B — следующим коммитом.

## 5. Проект спринта (слайсы)

### Slice 0: RFC / contract freeze

| Поле | Содержание |
|------|------------|
| **Acceptance** | Опубликован RFC (или ADR+RFC) с диаграммой состояний, списком wire message types (имена, направление), fork-choice v1, правила mempool gossip, matrix capability negotiation; перечень out-of-scope для v1; решение по «один сейлер vs несколько». |
| **Тесты** | Review-checklist: traceability matrix «требование → раздел RFC»; примеры сценариев (happy path, fork, bad header). |
| **Blockers** | Нерешённая семантика консенсуса при N нодах-сейлерах блокирует финализацию fork-choice. |
| **Rollback** | Только документы; откат версии черновика RFC. |

### Slice 1: wire schema + message types + feature gates

| Поле | Содержание |
|------|------------|
| **Acceptance** | Расширенный протокол за feature flag; старые ноды не падают при отсутствии флага; тесты сериализации/лимитов кадра. |
| **Тесты** | Unit: encode/decode; round-trip; ошибка на >1 MiB; отключённый флаг — нет новых веток в handler. |
| **Blockers** | Slice 0 не frozen → неясны имена и обязательные поля сообщений. |
| **Rollback** | Feature flag default off; удалить ветки обработки новых типов. |

### Slice 2: mempool gossip baseline

| Поле | Содержание |
|------|------------|
| **Acceptance** | Native-пиры обмениваются TX; дедуп по хешу; отклонение невалидных; метрики отправки/приёма; лимиты pool и rate. |
| **Тесты** | Integration: два процесса / два in-memory транспорта; флуд маленькими TX; pool full behavior. |
| **Blockers** | Нет общей TX валидации на входе gossip (должна совпадать с RPC path). |
| **Rollback** | Отключение gossip темы; откат к локальному mempool-only. |

### Slice 3: header-first sync + block fetch/apply

| Поле | Содержание |
|------|------------|
| **Acceptance** | Нода без хвоста догоняет peer до общего tip; apply обновляет state и snapshot-пайплайн согласованно; при несовпадении — controlled stall + лог причины. |
| **Тесты** | Integration: «leader» с цепочкой, «follower» пустой/старый tip; свойство связности; негативные тесты bad parent hash. |
| **Blockers** | Fork-choice и seal-валидация из Slice 0; возможная увязка с `snapshot` write policy (см. manifest lag). |
| **Rollback** | Flag: sync client off; нода только локальный seal как сейчас. |

### Slice 4: epoch catch-up fallback

| Поле | Содержание |
|------|------------|
| **Acceptance** | Запрос эпохи N+M, получение чанков, сборка файла, проверка manifest linkage; переход к live sync без ручного копирования файлов оператором. |
| **Тесты** | Тест на прервал соединение mid-epoch; повтор докачки; corrupt chunk отвергнут. |
| **Blockers** | Стабильный disk layout и права записи; согласование с repair.rs. |
| **Rollback** | Отключить epoch-fetch в конфиге; использовать только построчный block sync. |

### Slice 5: observability + chaos tests + operator docs

| Поле | Содержание |
|------|------------|
| **Acceptance** | Метрики: sync_height_lag, sync_bytes, gossip drops, peer role; runbook: bootstrap, «как пон что отстаём», лимиты; chaos: обрыв, медленный peer, ложный tip (детект). |
| **Тесты** | Автоматизированные сценарии в CI или scripted e2e (по политике репо). |
| **Blockers** | Стабильные имена метрик из Slice 0/1. |
| **Rollback** | Документация помечена experimental; метрики остаются no-op exporters optional. |

## 6. Compatibility / migration plan для текущих нод

1. **Capability negotiation.** Новые ноды объявляют версию субпротокола sync / gossip в hello или первом пост-handshake сообщении; старые игнорируют неизвестные типы **без паники** (уже важно при расширении enum).
2. **`services: sync`.** Либо реализовать поведение до релиза, либо временно убрать из default hello до готовности (breaking expectation для внешних наблюдателей минимален, но операторы читают capabilities).
3. **Конфиг по умолчанию.** Все новые пути — за флагом `experimental_sync_v1` или аналогом; оператор явно включает на testnet.
4. **Disk layout.** Epoch catch-up не меняет формат файлов без RFC-миграции; только добавляет **источник** данных.
5. **Постепенный rollout.** Testnet: только native mesh с новой версией; foreign peers без sync остаются на старых типах сообщений.

## 7. Open questions для владельца

1. **Кто может производить блоки в v1?** Один фиксированный валидатор, ротация по списку, или любая нода с ключом — от этого зависит валидация входящих блоков и fork-choice.
2. **Fork-choice:** достаточно longest-work/longest-height при PoA или нужна явная финализация / checkpoint-корма?
3. **Mempool gossip:** pull (inv/getdata) vs push flood — предпочтение для анти-спама?
4. **Строгость genesis_hash** в handshake для production-sync профиля (RFC 8 §12 open question).
5. **Приоритет реализации:** сначала только live block sync (A-min) без epoch-transfer, или параллельно нужен B для testnet с длинной историей?
6. **Отношение к будущему CometBFT:** какие контракты sync должны остаться стабильными, чтобы не выбросить работу?

---

## 8. Verdict

**NEED-RFC** — нормативного описания chain-sync, fork-choice и mempool gossip в текущих RFC **недостаточно**; код и обзоры подтверждают отсутствие протокола блоков на wire. После **Slice 0 (RFC freeze)** траектория переходит в **READY-FOR-CODING** для слайсов wire и выше. Прямой блокер: продуктовое решение по модели сейлинга (вопрос 1 выше).
