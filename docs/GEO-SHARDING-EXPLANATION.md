# GEO sharding и roaming (простое объяснение)

Этот документ объясняет текущую модель простыми словами для оператора/продукта.

## 1) Коротко: как это работает сейчас

- Сеть разбита на доменные кластеры (geo-shards) по `domain_hi`.
- У каждого шарда своё локальное состояние.
- Внутри одного шарда перевод идёт обычным локальным путём.
- Между разными шардами перевод идёт только через `EXPORT` (source) и `IMPORT` (target).

## 2) Genesis trust anchor: где "первичное доверие"

- Базовая точка доверия — genesis-конфигурация сети (validator set, базовые правила).
- Ноды доверяют стартовой конфигурации и проверкам runtime по этим правилам.
- Это не "доверие оператору на слово": operator только запускает процесс, но валидность операций решает протокол/рантайм.

## 3) Как шард отличает честный импорт от фальшивого

В MVP-версии target-шард принимает `IMPORT` только если одновременно верно:
- `export_id` известен в текущем потоке;
- `to`, `amount`, `target_domain` совпадают с сохранённым provenance;
- этот `export_id` ещё не был импортирован ранее (replay guard).

Если условия не выполнены:
- duplicate import -> `409 CONFLICT`;
- unknown/invalid provenance -> `400 BAD_REQUEST`.

## 4) Что хранится по roaming

Минимально хранится:
- `exported_registry` — запись о сделанных `EXPORT` (provenance);
- `imported_set` — уже использованные `export_id` для защиты от повторного импорта.

Это состояние сохраняется в snapshot и поднимается после рестарта.

## 5) Где crypto trust, а где operator process

**Crypto/protocol trust (машина проверяет):**
- проверка структуры и валидности tx;
- проверка соответствия `IMPORT` к provenance;
- replay-защита через `imported_set`.

**Operator process (человек/процедура):**
- перенос import-material между source и target (manual handoff в MVP);
- выбор правильной ноды/домена и корректного RPC endpoint;
- соблюдение runbook и фиксация результатов прогона.

Итог: криптография и runtime защищают от подделок/повторов, но операционные ошибки маршрутизации всё ещё возможны и дают детерминированные reject-ответы.

## 6) Что ещё не реализовано

Пока отсутствует:
- admission/compliance слой сертификатов;
- автоматический relay/handoff сервис;
- продвинутые finality-профили;
- оптимизированный async pipeline вместо синхронного `apply_tx + seal([])` на HTTP пути.

**Уточнение (Sprint 15, closeout S3.12):** режим **«одного окна»** для клиента (упрощённый путь: домашний RPC + roaming intent + при необходимости trusted peer для просмотра чужого шарда) — **временная MVP-модель**. При массовом использовании он **не масштабируется** и может **перегружать сеть** из-за частых опросов и обмена данными между нодами ради UI/балансов. Для зрелых релизов ожидаются **оптимизированные read-сервисы** (условный global explorer) и **подписка клиента** на обновления по адресам, а не бесконечное масштабирование того же механизма на всех нодах.

## 7) Куда идёт развитие (план)

Ближайший практический вектор:
1. стандартизовать machine-readable handoff envelope;
2. добавить лёгкую автоматизацию handoff, чтобы снизить operator error rate;
3. решить профиль async/sealing без поломки текущего API-контракта;
4. постепенно подключить policy/admission слой как additive-расширение.

## 8) Два уровня бухгалтерии и отказ доверия мосту

- **Первый уровень** — обычные балансы и эмиссия **внутри** шарда. Они между шардами **не обязаны совпадать** (рост эмиссии, burn, локальные переводы).
- **Второй уровень** — только **межшардовые перемещения** (что вывезли / что импортировали, какие `export_id` уже потреблены). Именно здесь должна сходиться **федерация**, а не «одинаковая сумма денег на всех шардах».

Если нода видит, что **второй уровень** у неё и у доверенного собеседника (или у другой реплики того же шарда) **не сходится**, это **отказ в доверии по мосту**: подозревается партиция, подстава, битый снимок или атака на наблюдаемость.

В таком режиме **закрывается сервис одного окна** для клиентов: не показываем «как будто всё ок» балансы и обозримость **чужого** шарда через домашнюю ноду — чтобы люди не принимали решения по **ложной** картине федерации. Оператору остаются диагностика и восстановление (repair/backfill по процедуре).

Подробнее нормативно: `docs/WHITE_SPEC_v0.md` §7.5 и `docs/rfc/9-crossdomain-roaming.md` Appendix A.6.

**Уточнение (hello / transport):** сравнение «мостового» дайджеста с **локальным** применяется к пирам с **тем же** `domain_hi`, что и нода (реплики одного шарда). Пиры **другого** шарда используют другой набор level-2 фактов — их дайджест намеренно **не** сравнивается с вашим как условие доверия; иначе любой межшардовый линк был бы в постоянном отказе.

## 9) Post-freeze extension proposal (Sprint 13)

Freeze Sprint 13 (`Slice 0..7`) остаётся фактом и не пересматривается. Ниже — только post-freeze расширение.

### Slice 13.8 (proposal): TUI `EXPORT` screen
- Цель: добавить в TUI короткий guided-flow для `EXPORT` с явным выводом `export_id` и provenance-пакета.
- Acceptance: оператор может выполнить `EXPORT` и скопировать полный handoff-пакет без ручной сборки полей.
- Риск: UI-ошибки/недостаточно явная валидация могут скрыть mismatch до этапа `IMPORT`.

### Slice 13.9 (proposal): TUI `IMPORT` screen
- Цель: добавить в TUI форму `IMPORT` с preflight-проверками и понятной интерпретацией `204/409/400`.
- Acceptance: оператор выполняет `IMPORT` из handoff-пакета и видит однозначный результат с actionable next step.
- Риск: неправильный UX retry может увеличить долю дублирующих попыток (`409`) и операторскую путаницу.
