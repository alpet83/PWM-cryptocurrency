# Sprint 15 — слайс O: плановое ревью чеклиста (группы A/B)

### 1. Scope recap

Проверены цели **группы A** и **группы B** из `docs/reviews/sprint-15-slice-O-checklist.md` относительно публичного контракта и аудита `docs/CODEBASE_REFACTORING.md` (§4.2–4.3, §5.2, §3.1, §7 Phase 1–2). Ревью **по текущему состоянию дерева** (без диффа ветки): что может сломаться при исполнении coding по пунктам A/B.

### 2. Requirements fit (группа A и «контракт»)

| Пункт A | Соответствие контракту / замечания |
|--------|-----------------------------------|
| **TUI:** инлайн `xflow_report()` / `xflow_handoff_help()` | Поведение для пользователя задаётся **литералами строк** в векторах и в тексте help. При сохранении тех же строк контракт UX не ломается. В аудите `xflow_report` назван passthrough к `xflow_terminal_report`, но в коде это **отдельный** форматтер заголовка «Cross-shard flow diagnostics» — инлайн должен **копировать ту же** `format!(...)`, иначе изменится вывод. |
| **pwmd:** `dial_stub_attempt` / `run_transport_tick` под `#[cfg(test)]` | **Частичное несоответствие слепому следованию аудиту §7 п.2.** В проде `run_transport_tick` вызывается из `spawn_transport_loop` (например, вокруг строки 1512 в `transport.rs`). Перенос всей `run_transport_tick` за `cfg(test)` **сломает** минимальный транспортный цикл. Чеклист верно оговаривает «только если все call sites допускают `#[cfg(test)]`» — для текущего кода это **не** допускает полный перенос. Допустимо: оставить прод-обёртку, упростить/инлайнить только тестовые обёртки в `lib.rs`, не трогая цикл. |
| **pwmd:** `hello_stub()` в `federation.rs` | В текущем дереве `hello_stub` уже находится **внутри** `#[cfg(test)] mod tests` (файл `federation.rs`, блок тестов с ~строки 326). Пункт чеклиста для coding может свестись к **подтверждению / синхронизации документации**, а не к переносу из prod. |
| **pwmd CLI:** `#[deprecated]` у `--shard` | Публичный контракт для скриптов и операторов — **флаг остаётся, парсинг и compat-поведение сохраняются** (см. комментарии и `deprecated_shard_arg_was_used()` в `main.rs`). Атрибут `#[deprecated]` на поле `Cli` в первую очередь даёт предупреждения **компилятору при обращении к полю из Rust-кода**, а не конечному пользователю CLI. Имеет смысл уточнить у coding: при необходимости явной депрекации в help — возможности **clap** (версия в workspace) для deprecated arguments. |
| **Док:** политика `// TODO(scope):` | Не меняет бинарный/API контракт; риск только «шума» в ревью, если префиксы не согласованы. |

**Вывод по группе A:** при соблюдении оговорок чеклиста (особенно про **не** уносить `run_transport_tick` целиком в test-only) публичный контракт **не обязан** пострадать. Главная ловушка — дословное следование **Phase 1 п.2** аудита без проверки вызовов из `spawn_transport_loop`.

### 3. Style

Для **ещё не сделанных** правок: при инлайне сохранять короткие имена и не раздувать идентификаторы; новые TODO — по согласованному префиксу из чеклиста.

### 4. Safety

- **Группа A (transport):** ошибочное удаление или `cfg(test)` для **`run_transport_tick`** при живом `spawn_transport_loop` → деградация/отсутствие тиков relay-минималки (зависит от конфигурации деплоя).
- **`--shard`:** изменение логики разбора `A|B`, дефолтов `listen`/`identity` или удаление compat-пути до отдельного слайса — **вне** заявленного A (нарушение политики soft-break из комментариев в `main.rs`).
- **TUI xflow:** только строковые регрессии и диагностируемость cross-shard flow для оператора.

### 5. Tests

После coding по A чеклист требует **`cargo test` по затронутым crate** и при касании transport — прогон сценариев, где задействованы tick/stub. Имеет смысл явно прогнать тесты в `pwmd`/`lib.rs`, которые уже вызывают `run_transport_tick` / `run_transport_tick_with`.

### 6. Verdict

**Approve with nits** для старта coding по **группе A** при условии: не переносить `run_transport_tick` в test-only без замены прод-вызова; трактовать `hello_stub` как уже изолированный; при инлайне xflow сохранить байт-в-байт или осознанно согласовать изменение строк; `--shard` — только deprecation-метки + неизменное поведение.

Для **группы B без отдельного ревью** — см. риски ниже → рекомендуется отдельный проход review или хотя бы ограниченный дифф на задачу.

### 7. Риски группы B без отдельного ревью

1. **Общий `TextInput` (TUI):** общая логика курсора, вставки, маски для passphrase — высокий риск регрессий **фокуса, модификаторов и edge-case** в четырёх модалках и SendForm; чеклист уже требует ручную проверку — без ревью легко пропустить платформенные отличия (терминал).
2. **`pwm-core::display`:** форматирование PWM и decimal — риск **несовпадения CLI/TUI**, округлений и отображения сумм; для денежных/единиц ошибка заметна пользователю и в интеграциях.
3. **`pwm-core::rpc`:** унификация timeout и HTTP client — риск **разного** поведения таймаутов/редиректов между CLI и TUI, трудноуловимые сетевые регрессии.
4. **`wallet_io`:** пути с tilde, home, нормализация — риск **открытия не того файла**, поломки автопоиска кошелька и тонких различий Windows/Linux; чеклист прямо требует сохранения семантики путей.
