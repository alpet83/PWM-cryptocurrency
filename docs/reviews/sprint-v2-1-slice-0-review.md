## Scope recap

Слайс заявляет цель: зафиксировать расхождения между целевой моделью v2 (`mvp_v2.md`: единый `marks`, `marks_quota` как наследие, ориентиры порогов эмиссии PWM/marks — RFC-first) и текущей реализацией **без** продуктовых правок. Основной deliverable — `sprint-v2-1-slice-0-spec-impl-audit.md` плюс практический чеклист и тест-гейт как документация процесса.

## Requirements fit (A: качество входа в кодовый слайс)

- **Решения владельца отражены корректно:** аудит явно противопоставляет цель «burn/spendable = `marks`» фактическому списанию `marks_quota`; статус `marks_quota` как legacy согласован с формулировками `mvp_v2.md`; пороги эмиссии описаны как **config-driven / RFC-first**, без преждевременной фиксации чисел в runtime — это совпадает с планом.
- **Полнота по объёму Slice 0:** есть findings с severity, impacted files, карта burn-ветки, точки эмиссии (`seal`, `accrue_marks`, `reward_producer`), черновик минимальных требований к следующему коду, узкие next slices, открытые вопросы владельцу. Этого достаточно, чтобы следующий слайс (нормативный текст / код) имел зафиксированный gap-list.
- **Критические пробелы:** не выявлено противоречий аудита с `mvp_v2.md` или «молчаливого» игнорирования ключевого риска (двойной учёт marks/quota, API скрывает квоту). Единственный заметный **процессный** разрыв — практический `sprint-v2-1-slice-0-checklist.md` остаётся полностью с неотмеченными `[ ]` при готовом аудите; это уже отмечено `pwm-testing` и создаёт шум на гейте, но не опровергает выводы аудита.

## Findings by severity

### High

_Нет новых высоких находок против содержания аудита._ Ранее зафиксированное в аудите расхождение «`BURN_MARK` → `marks_quota`» подтверждено независимым grep по дереву `pwm-core/src` (совместное присутствие ветки `TxBody::BurnMark` и использования `marks_quota_of` в `state.rs`).

### Medium

1. **Рассинхронизация практического чеклиста с фактом выполнения.** В `sprint-v2-1-slice-0-checklist.md` все пункты scope/evidence/output остаются `[ ]`, тогда как `sprint-v2-1-slice-0-spec-impl-audit.md` содержит закрытый acceptance-блок и ссылку на готовый отчёт. Риск: оркестратор/ревьюер по одному файлу заключает «не готово», по другому — «готово».
2. **Тикет vs output-checklist.** В практическом чеклисте указано ожидание «`delegations[0]`» и обновлённые `notes`; фактически в тикете уже две делегации (`pwm-coding`, `pwm-testing`). Формулировка чеклиста устарела относительно фактического конвейера (нужна синхронизация текста или тикет-шаблон).

### Low

3. **Матрица негативных тестов** для будущего кода описана в `test-report` нарративно и списком — достаточно для старта, но не как единая таблица «вход → ожидание»; приемлемо для Slice 0, стоит явно перенести в Slice 1/отдельный test-plan doc (`pwm-testing` уже рекомендует).
