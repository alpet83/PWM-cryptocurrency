## 1. Scope recap

Ответить на вопрос владельца: в «классических» цепочках нужно ли рвать P2P при первом же расхождении блок-хэша; для текущего MVP — допустим ли временный режим «обнаружили расхождение (heartbeat / сравнение tip) → disconnect peer → backoff переподключения ~60 с», чтобы оператор мог перезапустить корректный узел.

Связанный контекст репозитория: same-shard sync v1 (`sync_tip_announce`, `on_tip` в `sync_live.rs`), метрики `sync_tip_seen_total`, `sync_fork_conflict_total`, учёт закрытий `peer_close_by_reason`, transport backoff и `reconnect_runaway_cooldown_ms` (по умолчанию 60 с). Отдельно зафиксировано наблюдаемое расхождение tip hash при выровненном шарде — см. `tasks/20260508-v2-slice6-hotfix-tip-hash-divergence.json` и диагностику по тому же слайсу: это не «ложный» инцидент сравнения полей артефакта, а несогласованность заголовков/контекста применения.

## 2. Классическое поведение (кратко, практика)

У зрелых PoW/PoS сетей **соединение не разрывают «на первом отличном хэше»** в абстракции:

- **Честный форк / разная высота:** пиры обмениваются заголовками и блоками по разным веткам; клиент держит несколько кандидатных кончиков и выбирает правило ветвления (длина, вес, финализация). Обрыв был бы контрпродуктивен.
- **Тот же height, другой hash:** это либо форк одного уровня, либо ошибка/злонамеренный пир. Типичная реакция — **отклонить блок/заголовок, занизить score пира, BanScore / отказ ретрансляции**, а не мгновенный disconnect при любом расхирении набора возможных состояний; однако при **повторяющемся противоречии canonical-предикатам** многие ноды **разрывают сессию** как нарушение протокола или DoS-сигнал.
- **Итого для сравнения с MVP:** немедленный разрыв **везде** при любом расхождении хэшей **не является нормой**; норма — **ветвление + heal**. Операционно оправдан **целевой** разрыв, когда локально доказано **«несовместимый canonical tip при той же высоте»** или явная поломка континuity (у вас уже есть путь `sync_fork_conflict_total` при разрыве цепочки заголовков).

## 3. Требования к ответу владельцу (fit)

| Вопрос | Ответ |
|--------|--------|
| Рвать ли peer сразу при «первом» расхождении block-hash? | **Нет в общем виде.** Рвать уместно при **строгом** условии: *тот же shard*, *активен full_v1 sync*, *та же высота*, что и локальный tip, но **другой tip hash** (после нормализации hex). Иначе ложные дисконнекты на гонке границы блока и при нормальном отставании по высоте. |
| Временное поведение MVP: detect → disconnect → ~60 s backoff? | **Допустимо как явно помеченный operational safeguard**, пока root-cause расхождений не снят (см. slice6 hotfix/диагностику). Снижает «тихое» смешение контекстов gossip/sync; цена — **нет heal через этот канал**, оператор должен исправить меньшинство узел. |

## 4. Безопасная политика для текущего MVP (given known divergence issues)

Учитывая **известные реальные расхождения tip hash** на same-shard при рабочих инвариантах аккаунтов, политика должна быть **узкой** и **наблюдаемой**:

1. **Гейт активации:** только `full_v1` и успешное согласование same-shard (`sync_profile`/`shard_id` уже отсекаются существующими drop-reason).
2. **Триггер разрыва (рекомендуемый минимум):** на приёме `sync_tip_announce` (или эквивалентного поля в heartbeat-потоке, если tip там дублируется): если `peer_head_height == local_tip_height` и `peer_head_hash != local_tip_hash` (case-insensitive hex, фиксированная длина), считать **consensus divergence at tip** → инициировать graceful close этого peer session.
3. **Не триггерить:** разная высота (пусть sync/catch-up лечит), первый одиночный announce без второго подтверждения — *опционально* см. nits ниже.
4. **Backoff:** после close по этой причине — **не переподключаться к тому же peer identity / seed entry** минимум **60 s** (совпадает с дефолтом `reconnect_runaway_cooldown_ms`; лучше отдельный **`divergence_cooldown_ms`** или отдельный класс backoff, чтобы не смешивать с wire timeout/backoff).

Побочный эффект (принимаемый во временном MVP): при краткой бифуркации на одной высоте «лечение» только через другие пиры или рестарт; это **не** долгосрочная модель финальности.

## 5. Рекомендация для `pwm-coding` (что сравнивать, когда рвать, где cooldown, метрики)

**Где править логику (ориентир):** обработчик tip — функция уровня `on_tip` в модуле same-shard live sync (`sync_live.rs`): сейчас при `lag == 0` выполняется ранний выход **без** сравнения хэша с локальным tip; это естественная точка для guard.

**Что сравнивать:**  
`(head_height == chain.tip_h()) && (canonicalize_hex(head_hash) != hex::encode(chain.tip_hash()))`.

**Когда закрывать:** сразу после детекта (первая же валидная пара при выполнении гейтов выше). Опциональный nit для снижения дрожания на границе блока: потребовать **два последовательных announce** с тем же противоречием в окне `2 * heartbeat_interval_ms` — обсуждается с оператором; для «максимальной громкости» инцидента MVP можно начать с **одного**.

**Cooldown scope:** ключ — **`remote_peer_id` (или node_id из hello)** × **seed/transport slot**, не глобальный runaway-only. Запись в существующем `ReconnectLog`/policy слое transport: время `next_allowed_dial_ms = now + cooldown`. Дефолт **60 s**, конфигурируемый.

**Метрики и наблюдаемость:**

- Счётчик закрытий: например **`sync_tip_divergence_disconnect_total`** (или единый префикс `sync_*` для консистентности с runbook).
- Причина в **`peer_close_by_reason`**: строковый ключ вида **`tip_hash_mismatch`** или **`consensus_divergence`** (новый вариант в enum close reason, отображаемый в snapshot).
- Лог: `warn!` с `node_id`, `local_h`, оба хэша (укороченно), `shard_id` — без утечки лишних PII.

**Связь с существующим:** `sync_fork_conflict_total` остаётся для отказов continuity при загрузке заголовков; новый guard — **ранний** отсекатель по tip announce, когда высота уже равна, но канонический хэш иной.

## 6. Тесты (ожидание от `pwm-testing` / юниты)

- Синтетика transport harness: два «узла», одинаковая высота, разный `head_hash` в `sync_tip_announce` → ожидается close + рост новой метрики + запись backoff.
- Негатив: разная высота → **нет** disconnect по этому правилу.
- Негатив: `legacy_observe` → guard не активен.

## 7. Verdict (для оркестратора)

**READY_FOR_HOTFIX** — узко очерченный операционный safeguard (same height + same shard + full_v1), совместимый с текущей архитектурой sync v1 и существующим backoff-подобным конфигом; не требует отдельного RFC для экономики/consensus-модели, при условии явной маркировки в CHANGELOG/runbook как **временная** мера до снятия root-cause tip divergence.
