# S3: кластерный консенсус vs failover — варианты для упрощённого MVP

Дата: 2026-05-11; **актуализация open questions: 2026-05-12**  
Тикет: [`tasks/20260511-single-sealer-S3-cluster-consensus-design.json`](../tasks/20260511-single-sealer-S3-cluster-consensus-design.json)  
Родительский срез и бэклог: [`tasks/20260509-single-sealer-failover-profiles.json`](../tasks/20260509-single-sealer-failover-profiles.json) (срез **S3**, `recommended_slices[].id === "S3"`).  
Базовый дизайн failover/профилей: [`docs/reviews/20260509-single-sealer-failover-design.md`](20260509-single-sealer-failover-design.md).

## 1. Scope recap

Задача тикета — **design-only**: зафиксировать терминологию, сравнить варианты «несколько нод одного валидатора согласуют блок» с уже описанным и частично реализованным **failover (active/standby + lease)**, отделить **non-goals** от полноценного BFT/PoA-кластера, и рекомендовать, что брать в **следующий implementation slice**, а что оставить на **RFC**.

Связь с [`docs/MVP-checklist.md`](../MVP-checklist.md): **§4** (seal-loop, границы single-proposer MVP) и **§12** (явный defer/backlog по консенсу и протокольным гарантиям) — S3 не должен «тихо» менять контракт финализации без версии протокола и RFC.

**Важно по владельцу:** **Failover** — это *один* активный локальный sealer на validator identity при наличии standby-клонов и координатора аренды; это **не** кластерный консенсус в смысле «несколько узлов коллегиально фиксируют один и тот же кандидатный блок до seal». S2 даёт process-local gate и сигналы; границы смотри в §3.

## 2. Терминология

| Термин | Смысл в PWM MVP |
|--------|-----------------|
| **Validator identity / same-key clone** | Один и тот же ключ/идентичность из validator set; несколько **процессов** pwmd могут представлять её. |
| **Failover topology** | Active sealer + один или несколько standby: в каждый момент **не более одного** разрешённого локального seal для этой identity (цель — HA, не «голосование за блок»). |
| **Cluster consensus (S3)** | Режим, в котором **несколько** узлов **одной** логической роли sealer **согласуют** кандидатный блок (или его хэш/подпись раунда) **до** того, как блок считается принятым локальной цепочкой шарды / до внешней публикации. |
| **Leader / proposer (раунд)** | Узел, формирующий кандидат (транзакции, корни, заголовок) в данном раунде; в PoA с ротацией по высоте «ожидаемый proposer» уже задан правилом цепи — S3 может наложить **дополнительный** шаг согласования между клонами одного proposer. |
| **Attestation / quorum** | Подписи или vote-сообщения peer-ов на кандидат; **quorum** — порог (например 2-of-3 клонов), при котором кандидат считается **валидным для seal**. |
| **Lease / fencing (S2)** | Операторский/runtime механизм **эксклюзии** «кто сейчас active»; не заменяет доказуемый BFT-консенсус между независимыми злоумышленниками. |
| **`multi_sealer_experimental`** | Профиль для хаоса/исследований: конкурирующие seal, fork-choice — **не** acceptance default для testnet. |
| **Finality / fork-choice** | В MVP цепь следует существующим правилам выбора канонической ветки; S3-варианты ниже должны явно говорить, появляется ли новая семантика «финализировано для шарды» или только «локально согласовано клонами». |

## 3. Граница с S2 и лимиты финального ревью S2

Итоговое ревью S2: [`docs/reviews/20260509-s2-lease-fencing-failover-final-review.md`](20260509-s2-lease-fencing-failover-final-review.md) — вердикт **PARTIAL** для цели «строгая защита от split-brain между **двумя независимыми процессами**»: локальная карта аренды **не разделяется** между процессами; криптографического fencing по сети нет; для кросс-процессной HA нужен **внешний координатор** (файл/KV/сервис), как уже намечено в [дизайне failover](20260509-single-sealer-failover-design.md) §«Lease and Fencing Strategy».

**Вывод для S3-планирования:** кластерный консенсус и «внешняя аренда» — **разные оси**: можно внедрить внешний lease (дозрез S2) **без** S3; можно проектировать S3 **поверх** уже стабильного failover, но нельзя путать «кворум клонов подписал кандидат» с «один владелец lease seal-ит».

## 4. Матрица вариантов S3 (pros / cons / MVP fit)

Оценка **MVP fit**: насколько вариант совместим с текущим single-proposer mental model, объёмом wire/протокола и риском скрытой смены семантики.

| ID | Кратко | Плюсы | Минусы | MVP fit |
|----|--------|--------|--------|---------|
| **A. Leader + peer attest (целевой упрощённый сценарий владельца)** | Один узел строит кандидат; peer-клоны проверяют валидность (state transition, roots, policy), дают attest; после порога — **один** seal от имени proposer (или явно назначенного «committer»). | Понятная семантика; близко к «один подписант»; снижает риск разъезда заголовков при общем mempool/tip. | Нужны таймауты, идемпотентность раунда, согласованный round-id; при деградации кворума — застревание или fallback-политика; wire + состояние раунда. | **Средний** — кандидат на **узкий** первый слайс, если зафиксировать non-goals (ниже) и не требовать BFT. |
| **B. Rotating leader среди клонов** | Leader на раунд выбирается детерминированно (например по `node_instance_id`, round-robin при фиксированном membership). | Распределяет нагрузку; меньше «всегда один hot node». | Смена лидера при отказах = снова election/tаймауты; сложнее объяснить оператору; больше состояний гонки. | **Низкий–средний** для первого код-слайса; хорош для RFC и **позднего** слайса. |
| **C. Minimal quorum threshold (k-of-n клонов)** | Жёсткий порог подписей attest **перед** commit; без кворума блок не seal-ится. | Ясная «безопасность от одиночного бага» на кандидате. | При k>2 растёт задержка и операционная сложность; на тестнете часто n=2 → кворум деградирует в «оба живы». | **Средний** при k=2 и n≥2 как **минимальный** порог; иначе **RFC-first**. |
| **D. «Optimistic»: leader seal-ит, peers только репортят расхождение** | Основной путь без блокирующего кворума; post-facto сравнение / алерт при mismatch. | Минимальные изменения; быстрее наблюдаемость. | Не консенсус; не предотвращает split на уровне кандидата; может вводить в заблуждение, если назвать «cluster». | **Высокий** как **observability-only** слой без смены консенсусных гарантий. |
| **E. Chaos / experimental multi-sealer (существующий профиль)** | Явное разрешение конкурирующих seal, метрики fork-choice. | Уже заложено в профильную модель ([failover design](20260509-single-sealer-failover-design.md) §`multi_sealer_experimental`). | Не для production acceptance; не «кластерный консенсус». | **Высокий** как **контур лаборатории**, **низкий** как путь prod MVP. |
| **F. Full BFT / PBFT-lite внутри клона-сета** | Доказуемые раунды, view-change, кворум 2f+1. | Сильные гарантии при Byzantine peers. | Несоразмерно MVP; новая спека безопасности; аудит криптографии и времени. | **RFC-only** для PWM MVP; не следующий маленький слайс. |

## 5. Explicit non-goals (относительно «полного» кластера)

- Не претендовать на **Byzantine fault tolerance** между клонами без отдельной модели угроз и доказательств.
- Не смешивать **кворум клонов** с **кворумом разных валидаторов** шарды — это разные предметы доверия.
- Не переносить lease/fencing **в chain header** без bump `PWM_PROTOCOL_VERSION` и RFC (согласовано с [failover design](20260509-single-sealer-failover-design.md): block-level term — зона S3/RFC).
- Не использовать **mid-second align** или детерминированный timestamp режим как замену согласования ([failover design](20260509-single-sealer-failover-design.md) §«Mid-second Align Boundary»).

## 6. Recommendation: следующий implementation slice vs RFC-only

**RFC-only (сделать в любом случае раньше кода):**

- Точное определение **round identity** (height + round counter vs height-only).
- Что является **vote object** (хэш заголовка, полный блок, только `tx_root`+`state_root`).
- Политика при **partition**: freeze seal vs fallback к single-active lease-only.
- Соответствие **fork-choice**: не создаём ли два валидных канонических блока на одной высоте для внешних наблюдателей.

**Следующий узкий implementation slice (если владелец хочет код раньше «большого» RFC):**

1. **Дозрез операционной базы:** внешний/shared lease для кросс-процессного S2 (см. S2 PARTIAL выводы) — это **не S3**, но снимает двусмысленность «консенсус vs эксклюзия».
2. **Observability / variant D:** согласованные логи/метрики «candidate built / attest received / commit» без обязательного кворума — малый diff, без изменения финальности для сети.
3. **Variant A с k=2-of-2 или 2-of-3** как feature-flag за профилем, **не** default testnet — только после минимального RFC на wire и состоянии раунда.

**Не брать следующим слайсом:** F (BFT-lite), широкий B без жёсткой спеки.

## 7. Open questions (актуализация 2026-05-12)

Ниже — что перенесено в нормативный/проектный контракт [**RFC 16**](../rfc/16-validator-clone-attestation.md) (v0.3+), а что остаётся в бэклоге. Исходный список из §7 (2026-05-11) **закрыт в этой редакции** в пользу разделения.

### 7.1 Закрыто / зафиксировано (см. RFC 16)

| Было в open questions (11.05) | Где зафиксировано |
|------------------------------|-------------------|
| **Membership** — только конфиг vs регистрация | **§4.1** RFC 16: для MVP — **OOB** (списки + peer identity); динамическое расширение кластера и отдельный **регистрационный** протокол — **вне** baseline MVP, итеративный rollout и роли CLI — **Appendix A.2**. |
| **Committer** vs leader и `Chain::seal` | **§8** RFC 16: кто propose/attest/seal, конфликт с lease; **один** committer после кворума. |
| **Mempool** — один view vs расхождения | **§2.1, §6** RFC 16: **один кандидат лидера**; аттесторы валидируют **его** артефакт; без baseline «свой блок vs чужой». |
| **S2 lease** vs кто может attest | **§8.1** RFC 16: **ортогональность** S2 seal lease, кворума и relay pool (отдельные оси). |
| **Wire** — версия vs REST / lab | **§10, §10.1** RFC 16: приоритет **peer/wire** + capability; REST только lab/OOB; **транспорт по фазам** (соседи по TCP сейчас; UDP + anti-echo — отдельно). |
| Round identity, vote object, кворум, таймауты | **§5, §7, §9** RFC 16; **T_block_assembly** в конфиге — **§9.1**; стабилизация **≤3** узлов — **§7.2**; кворум как подмножество **relay pool** — **§7.1** и термины **§2**. |
| Выбор лидера, смешанные сети | **Appendix A.1** RFC 16: не один только IP; `node_instance_id` / имя; рекомендации **VPN/NAT/LAN** для оператора. |

### 7.2 Остаётся открытым (бэклог → в первую очередь RFC 16 §12 / последующие ревизии)

1. **Доказательство кворума в header** для внешних наблюдателей (нужен ли и какой bump протокола) — RFC 16 §12 п.1.
2. **Политика при tx в кандидате, неизвестных standby:** fetch / reject / отложить раунд — RFC 16 §12 п.2; требуется **детерминированный** выбор в профиле.
3. **Соответствие ключей:** attestation key vs validator block signing key (один и тот же / derived) — RFC 16 §12 п.3.
4. **Отбор активных k аттестаторов** из **большого** relay pool (эпохи, слоты, операторский срез) — RFC 16 §12 п.4; **после** стабилизации трёхузлового пути.
5. **Динамическая регистрация** нового участника кластера **подписанным** анонсом (имя, IP, …) как **нормативный** wire-протокол — согласовано с владельцем концептуально, **не** зафиксировано как обязательные поля сообщений в RFC 16 v0.3 (следующий шаг: отдельный подпункт RFC или мини-RFC **cluster join**).

### 7.3 Политика приёмки (продукт / testnet)

- **Acceptance defaults:** пути S3/кластерного консенсуса в testnet **остаются выключенными** по умолчанию до отдельного чеклиста владельца — **в силе**; при появлении флагов ролей (`--allowed-cluster-roles` и т.д.) — явно документировать default **off** в runbook.

### 7.4 Следующий пласт (2026-05-12) — см. RFC 16 Appendix B

Зафиксировано в [**RFC 16** `Appendix B`](../rfc/16-validator-clone-attestation.md) (см. версию в шапке файла): без доказательства кворума в header на MVP; **B.2** — только неформальный seed таксономии расхождений (без полного набора реакций до операционной истории); ключи пропозера и аттестаторов на MVP — совпадение identity; два канала аттестаций (лидер / все участники); динамический join — отдельный слайс (расширение handshake). Политика **поздних tx** при аттестации — **§6.1** RFC (bounded catch-up + лог аналитики).

**Планирование реализации:** [docs/plans/mvp_v2.md](../plans/mvp_v2.md) — **Sprint V2-9** (несколько слайсов: ядро + волны 2–3 узла + ведомые same-shard вне кластера); готовность черновика — **RFC 16 §16**.
