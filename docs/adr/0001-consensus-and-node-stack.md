# ADR 0001: стек консенсуса и ноды (MVP)

## Статус

Принято.

## Контекст

Нужна permissive-лицензируемая база для PWM MVP: учёт, подписи, сеть, RPC, devnet.

Рассматривались:

- **CometBFT + ABCI** (Apache-2.0) — готовый BFT, отдельный процесс, интеграция через сокет.
- **Cosmos SDK** (Apache-2.0) — тяжёлый стек для узкого MVP.
- **Substrate** — мощно, но аудит лицензий и объём кода избыточны для v0.
- **Собственный узел на Rust** — полный контроль; риск ошибок в консенсусе.

## Решение

**Собственный узел на Rust** (`pwm-core` + `pwmd`) с **встроенным PoA dev-консенсусом** (round-robin по списку валидаторов из genesis, подпись блока Ed25519).

## Обоснование

- MIT-стиль итогового продукта без привязки к процессу CometBFT и без Go-цепочки зависимостей в рантайме.
- Быстрее довести до сквозного сценария: genesis → блоки → RPC → CLI → TUI.
- Границы состояния и транзакций изолированы в `pwm-core`; позже возможна **замена движка консенсуса** на внешний BFT (CometBFT) с сохранением формата состояния — отдельный ADR.

## Лицензии зависимостей

Корневой `Cargo.toml` использует только распространённые crates с MIT/Apache-2.0 / BSD-style (см. `cargo license` после установки). Перед релизом рекомендуется CI-проверка `cargo deny`.

## Последствия

- Необходима осторожность при изменении правил форка/сети: devnet ≠ продакшен-BFT.
- Документация должна явно помечать «devnet PoA».
