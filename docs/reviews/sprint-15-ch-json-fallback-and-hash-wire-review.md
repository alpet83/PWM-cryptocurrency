# pwm-review: CH → JsonFile fallback и формат хэшей в snapshot JSON

**Контекст:** запрос оператора на автоматический fallback записи в файловое хранилище при недоступности ClickHouse; параллельно — проверка «пропавшей» оптимизации JSON (hex-строки вместо массивов байт для хэшей).

---

## A. Fallback ClickHouse → JsonFile (набросок реализации)

### Текущее поведение (baseline)

- Выбран ровно один `PersistSnapKind`: **`JsonFile`** или **`ClickHouse`** (`store.rs`, конфиг).
- Ошибка **`save_seal_persist`** после успешного **`seal`** → состояние **`ready_degraded`**, цепь в памяти впереди персистентного слоя; **автоперехода на запись в `pwm-data.json` нет** (`lifecycle.rs`).

### Цели fallback-механизма

1. При временной недоступности CH узел **продолжает персистировать** на диск (минимум sealed-блоки / checkpoint по уже принятому JsonFile контракту).
2. После восстановления CH возможна **реконсилиация** или операторский выбор «источника истины» (см. риски).

### Варианты дизайна (от простого к надёжному)

| Вариант | Идея | Плюсы | Минусы |
|--------|------|-------|--------|
| **F1 — Dual-write (конфиг)** | При `persist_snap=clickhouse` задавать **обязательный** `data_file` как **shadow JsonFile**: каждый успешный seal пишет и CH, и epoch/summary на диск. | Простая модель «файл всегда есть»; при падении CH остаётся только файловый путь. | Удвоенный I/O; нужно согласовать порядок ошибок (CH ok, disk fail и наоборот). |
| **F2 — Failover на ошибке CH** | После `Err` от `ch_save_seal` вызывать **`json_file_seal_persist(data_file)`** если задан **`--snapshot-fallback-json`** / env. | Нет постоянного двойного write. | Риск **расхождения**: CH получил блок N, файл — нет (или наоборот); восстановление ручное. |
| **F3 — Режим «degraded = JsonFile only»** | Флаг/переход: при K подряд ошибках CH переключить **runtime** backend на **только JsonFile** до рестарта. | Предсказуемый один writer. | Сложнее операторский контракт; нужен явный **escape hatch** обратно на CH. |

**Рекомендация для MVP follow-up:** комбинация **F1 (опционально)** для прод-операторов, которым нужен «всегда локальный след», и **F2** как минимальный автоматический запасной путь с **жёстким логированием** и **метрикой расхождения**.

### Минимальные изменения кода (ориентир)

1. **Конфиг:** `snapshot_fallback_json: Option<PathBuf>` (или переиспользовать существующий `data_file` при CH: сейчас путь к файлу нужен для genesis/neutral в любом случае — уточнить в `PwmdConfig`, не конфликтует ли с CH-only деплоем).
2. **`SnapshotBackend`:** не раздувать enum до комбинаторного взрыва — ввести обёртку **`SnapshotPersistLayer`**:
   - `primary: SnapshotBackend`,
   - `fallback: Option<JsonFilePath>` + политика **try primary → on Err try fallback**.
   - Либо метод **`save_seal_persist`** → `join_results(primary, fallback)` с явным правилом успеха (например: успех если **хотя бы fallback** ок при падении CH).
3. **`init_state_path` / degraded:** при успешном fallback в файл выставлять путь к **`pwm-data.json`** для диагностики; при полном провале — как сейчас `ready_degraded`.
4. **Загрузка:** без смены контракта — при старте по-прежнему один `persist_snap` для **чтения**; сценарий «накапали на CH, рестарт без CH» уже частично покрыт **`ch_load` → legacy**; сценарий «накапали fallback JSON + CH отвалился» требует **операторского** выбора backend при следующем старте или автодетекта наличия epoch-файлов (осторожно).

### Риски (обязательно в ADR / runbook)

- **Двойная правда:** блок в памяти есть, CH не записал, JsonFile записал — ок; обратное — хуже.
- **Replay:** JsonFile и CH должны оставаться **одним каноническим wire** (`validate_snapshot`); fallback не должен писать «другой» формат блока.
- **Деградация уже помечена как не блокирующая сервис** — fallback не отменяет необходимость мониторинга `ready_degraded`.

### Тест-план

- Юнит: mock CH Err → assert запись в tempfile epoch/summary.
- Интеграция: поднять CH, несколько блоков, уронить CH, убедиться что файл растёт и статус/лог ожидаемы.

## B. «Пропавшая» оптимизация: хэши hex vs массивы в JSON

### Где сейчас хэши в wire блока

В **`pwm-core`** структура **`BlockHdr`** (`crates/pwm-core/src/block.rs`):

- Поля **`prev_hash`**, **`tx_root`**, **`state_root`** имеют тип **`[u8; 32]`** без кастомного `serde(with = "...")`.
- **`sig`** использует только **`serde(with = "crate::ser_bin::sig64")`**, где **`sig64`** сериализует **64 байта как `serialize_bytes`** → в JSON (serde_json) это по сути **массив чисел**, не hex-строка (`ser_bin.rs`).

Итог: при **`serde_json::to_string`** для **`Block`** заголовочные хэши уходят в JSON как **массивы из 32 элементов 0–255** — компактно для машины, **раздуто для текста** (~2–3× против 64-символьного hex).

### Куда делась hex-оптимизация

По текущему коду **общего модуля hex-для-всех-хэшей заголовка нет**: это не регресс «удалили модуль», а **изначально выбранный тип `[u8;32]` + derive `Serialize`**. Если в старых ветках/прототипах были hex-строки, они могли быть:

- в **отдельном snapshot wire v1** / ручном JSON,
- или в **документации/примерах**, не в текущем `BlockHdr`.

Нельзя утверждать без `git`-археологии; **фактическое состояние репозитория** — массивы в JSON для этих полей.

### Как вернуть компактный wire (без поломки совместимости)

1. Ввести **`serde(with = "pwm_core::ser_bin::hex32")`** (или общий `fixed32_hex`) для **`prev_hash` / `tx_root` / `state_root`** в **`BlockHdr`** (и при необходимости для других `[u8;32]` в теле транзакций в snapshot).
2. **`Deserialize`** должен принимать **и hex-строку, и legacy-массив байт** (мягкая миграция), чтобы старые `pwm-data.json` и epoch-файлы продолжали грузиться.
3. **Новые записи** — только hex (или только массив на переходный период — политика версии снимка `SNAPSHOT_VERSION` / bump minor wire).

### Оценка эффекта

- На блок с типичным числом tx экономия заметна в первую очередь на **повторяющихся полях заголовка**; для больших цепей epoch-файлов выигрыш суммируется.
- Согласовать с **ClickHouse `payload_json`**: там блок сериализуется тем же `serde_json`; унификация формата уменьшит размер INSERT.

## C. Вердикт pwm-review

| Тема | Вердикт |
|------|---------|
| Fallback CH → JsonFile | **Не реализован**; целесообразно проектировать как **F2 минимум** + опционально **F1**; обязательны ADR, тесты на расхождение, правки runbook. |
| Hex хэши в JSON | **Не «пропали»** из кода — текущий **`BlockHdr`** не использует hex для полей хэша; оптимизация возможна через **`serde(with)`** + backward-compatible deserialize. |
