## 3. S3 flow analysis

**F6 send (track_nonce: true):**

1. `SubmitDone` Ok → write journal line with `status: pending`.
2. Insert `pending_nonces`, `pending_files`, `pending_accounts` keyed by submitted nonce.
3. Poll observes on-chain `row.nonce` advanced → append `status_update` with `status: ok` → clear pending maps.

**F5 burn (track_nonce: false):**

1. `SubmitDone` Ok → set `status: ok` on entry → single journal write → no poll tracking.

**Duplicate `status_update`:** prevented by removing nonce from `pending_nonces` after first `nonce < row.nonce` match — satisfies ticket blocker.

## 8. BLOCKERs

None. Nonce condition is `nonce < row.nonce` with removal after processing; wallet reload is process-scoped; poll/account fetch failures leave pending state intact.

## 9. Nits (non-blocking)

1. **NIT-1:** `pending_files` / `pending_accounts` keyed by `nonce` only — concurrent sends from two accounts at the same on-chain nonce could collide (overwrite maps). Rare for single-owner wallet; use `(AccountId, nonce)` key if multi-account concurrency matters.
2. **NIT-2:** On `write_journal` failure during status confirmation, pending entry is still removed — status_update may be lost silently (only stderr log).
3. **NIT-3:** If polled row has `UNKNOWN_INIT_NONCE_SENTINEL` nonce, `nonce < row.nonce` is true for any normal pending nonce → premature false confirmation.
4. **NIT-4:** Extend `make_file_name` sanitization doc/test for `!` and other punctuation if cross-platform paths matter.

## 10. Verdict

**Approve with nits** — S2 nits addressed (full pretty filename, error logging, burn immediate ok); S3 pending nonce tracking and poll-based `status_update` are correct for the single-owner path. No blockers on stale reload or duplicate confirmations.
